# Store 提交与失败语义审计（B02）

日期：2026-10-23。状态：B02 补充审计记录，不宣称已把所有 Store 改成事务。

## 结论

`writeFileAtomic` 只保证单个文件完整替换。下表记录各 Store 在“内存已改、落盘失败”时的当前行为；除展示资料外，本轮没有批量改变它们的提交语义。

| Store | 内存修改时机 | 落盘失败时 | 后续重试 | 备注 |
| --- | --- | --- | --- | --- |
| `AccountDisplayStore` | 不保留独立内存快照；读取→合并→写入后直接返回 | 不发布结果，返回值不产生 | 下一次保存重新读取磁盘 | B02 已接入同账号串行域 |
| `ConfigStore` | 写成功后才替换 `#config`、递增版本 | 内存保持旧配置 | 下一次修改可重试 | 先复制备份再原子替换 |
| `DesiredStateStore` | `set/delete` 先改 Map，再 persist | 内存保留新值，方法抛错 | 同值再次 set 会提前返回，磁盘可能仍是旧值 | 已知不一致；调用方需以抛错为准 |
| `SlotStore` | `save` 先替换数组，再 persist | 内存保留新值，方法抛错 | 再次 save 会重新落盘 | 启动播种依赖 `loaded` |
| `ListeningStore` | `remember/forget` 先改 Map，再 persist | 内存保留新值，方法抛错 | 相同 remember 会提前返回 | 与恢复候选相关，失败时应视为未记住 |
| `AccountJobStore` | 先改 jobs，再 persist | 内存保留新 job，方法抛错 | 下一次 patch 会基于内存新值 | 需后续单独决定回滚或补偿 |
| `AccountMediaStore.delete` | 先删内存索引，再 persist，最后删文件 | 内存已删、磁盘索引和文件可能还在 | 重新加载后可能“复活” | 需后续单独决定补偿顺序 |
| `JsonlStore` | 追加/重写由自身队列控制 | 追加失败不推进已提交 seq；重写失败保留原段 | 由调用方重试 | 不适用普通 JSON 覆盖语义 |

## 已覆盖的约束

- 同一账号的展示资料读改写已串行化；不同账号使用不同键，可并行。
- 展示资料写入失败不会返回“已保存”。
- 串行执行器在失败后继续处理后续任务；`close()` 拒绝新任务并等待已接受任务完成。

## 未解决的边界

- `DesiredStateStore`、`ListeningStore` 的“失败后内存是否回滚”尚未统一，不能把原子写入当成事务。
- 多文件一致性（例如媒体索引与媒体文件）没有通用补偿机制，仍需各模块自行定义。
- 没有增加 fsync 级断电持久性保证。
