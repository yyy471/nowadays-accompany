## 已确认决定

### DL-01 产品中心：Nowadays 是数字生命的载体

- 项目从以 QQ 注入编排为核心，转向以 Nowadays 自身承载数字生命为核心。
- 用户可以在 Nowadays 中搭载或创建不同的角色，与角色进行页面对话，并为角色提供功能和 API 支持。
- 看视频、浏览网页、记笔记，以及通过 Agent 控制电脑，属于已确认能力方向；浏览、视频、桌面协调和笔记的基础原则见 DL-31～DL-34、DL-44，具体技术实现及完整排期仍待确定。
- 插件、Skill 等扩展能力围绕新的角色 Agent 核心接入，通用接入与重写方式见 DL-35～DL-37，不预设直接沿用旧实现。
- QQ、其他社交平台及 SnowLuma 接入作为额外扩展，不再决定角色能否存在、对话或拥有记忆；QQ／SnowLuma 的实施顺序已在 DL-42 确认为后置。
- 角色的记忆、对话历史和活动经历以 Nowadays 为归属中心。

### DL-02 角色实例：一个实例就是一个独立数字生命

- 每个角色实例拥有持续、独立的身份，以及自己的设定、记忆、经历和扩展状态。
- 同一张角色卡可以创建多个独立实例；这些实例各自拥有自己的经历。
- 同一实例可以通过 Nowadays 页面、QQ 或其他入口参与交流，入口变化不创建另一个角色身份。

### DL-03 更新设定：修订同一角色，不重建生命

- 用户可以反复更新角色设定，包括完善初版角色卡。
- 更新后仍是同一个角色实例，保留身份、历史对话、记忆和扩展状态。
- 系统不检测、标记、解决或自动修正角色设定与已有记忆、历史之间的冲突。
- 设定冲突由用户自行处理；不建立冲突待办、不自动清理或改写已有记忆。
- 早期讨论中提出的“当前设定优先、冲突记忆标为待处理”未被采用，以本条用户纠正后的决定为准。

### DL-04 对话组织：多个独立窗口，主界面只展示用户与角色的直接对话

- 同一角色拥有多个独立对话窗口。QQ 私聊、群聊及其他入口的会话分别保存。
- 在角色视角中，这些是它参与的不同对话窗口。
- 用户主聊天界面只呈现用户自己与该角色的直接对话，不把角色其他窗口的消息混入其中。
- 用户进入该角色的“消息与活动日志”一类页面，才能查看其他对话详情和活动记录；页面正式名称与布局尚未确定。
- QQ 等外部平台上的消息属于 Nowadays 中的正式对话历史，保留对应会话并标注来源平台。
- “全部进入 Nowadays 的历史”不等于“把所有窗口合并为一条聊天记录”。

### DL-05 记忆范围：角色共享长期记忆，窗口保留独立上下文

- 同一角色在不同对话窗口之间共享角色层面的长期记忆，由 Nowadays 统一管理。
- 每个窗口保留自己的聊天上下文与原始消息记录。
- 角色可以在主窗口回忆从 QQ 等其他窗口获得的经历，但其他窗口的原始消息不会因此成为主窗口的聊天记录。
- 记忆提取、检索与上下文注入按 DL-16～DL-28、DL-51、DL-87 的已确认原则细化，不将“共享记忆”解释为每次调用都加载全部窗口历史。

### DL-06 Agent 核心：采用 LangGraph TypeScript 编排

- 采用 LangGraph 的 TypeScript 版本构建角色 Agent 核心。
- LangGraph 承担执行流程与运行状态的编排，组织上下文读取、记忆检索、模型调用、工具执行及后续处理。
- Nowadays 自己掌握角色身份、角色设定、对话历史、记忆规则和扩展规则。
- 用户设计的记忆系统作为核心能力接入；不因采用 LangGraph 而强制替换为框架默认的记忆方案。
- 执行检查点与角色长期记忆承担不同职责，不把运行检查点直接等同于角色完整经历的存储。
- 实施方式已修订为 DL-37 的新空分支重写。现有插件、Skill、模型服务与工具执行的设计经验可供评估参考，具体代码复用不作为前提；Skill 按 DL-36 的通用规范重新设计接入。
- 正式实现前，先以小范围原型验证集成，首轮范围以 DL-60、DL-85～DL-88 为准；检查点分文件与身份映射已在 DL-65、DL-66 确认，具体依赖、驱动与执行接口仍待 P0 验证。
- 网页操作、视频处理和电脑控制需要具体能力实现，再由 Agent 调度；采用框架本身不代表这些能力已经具备。

### DL-07 自主活动：属于核心设计目标

- 自主活动是本次方向调整的重要能力，不限于收到消息或用户分配任务后才行动。
- 角色在没有新消息时也可以产生并开展活动。
- 自主活动形成的经历进入角色记忆及活动日志。
- 用户通过 DL-11、DL-59 的开关控制是否启用相应资源与能力，自主活动另遵守 DL-52 的预算；具体默认值及范围组织仍待确定，不新增额外授权。

### DL-08 活动动机：角色形成意图，用户可以引导

- 角色依据角色设定、已有记忆和持续关注的事情，自行形成活动意图。
- 用户可以提供长期方向，无需逐项安排全部任务。
- 角色需要持续保留正在关注的事情、想做的事情和未完成意图，让活动能够跨轮次延续。
- 看网页、看视频、记笔记等活动可以由角色自己的动机推动，不仅来自用户的直接命令。

### DL-09 统一主体：协调多个对话与可并行任务

- 同一角色拥有一个统一的决策主体，协调不同对话窗口和自主活动。
- 角色应掌握自己正在进行的活动，并据此协调回复、暂停、继续或稍后处理。
- 具体任务可以并行执行，各对话窗口仍保留独立上下文。
- 不将每个窗口设计成彼此不知道对方活动的独立角色副本。
- 统一主体是产品与调度上的一致性要求；同一角色决策串行、独立任务可并行的原则已在 DL-49 确认，不将其等同于全部工作使用单线程或所有任务串行执行。

### DL-10 唤醒方式：事件唤醒与自主安排相结合

- 消息到达、网页加载完成、视频处理结束等事件可以唤醒角色，推进下一轮思考和行动。
- 角色可以根据自己的意图安排后续唤醒，例如稍后继续阅读、次日关注事情进展。
- 系统负责持久保存并调度这些安排。
- 没有待处理事件时，角色保留状态并等待；不以持续进行无意义模型调用维持存在。
- 关闭窗口与明确退出时的运行行为已在 DL-29 确认；重启重评估见 DL-30，任务与图恢复见 DL-65～DL-73，P3 实施范围见 DL-112；具体唤醒调度接口仍待设计验证。

### DL-11 能力开关：用户按角色启用或停用，角色自主使用

- 本条原有额外授权表述已按用户在 DL-59 的决定修订为开关控制。
- 用户为角色启用或停用相应资源与能力，开启后角色可自主使用，不另设授权、审批或逐次调用确认。
- 网页浏览、笔记、QQ 接入、电脑控制等能力可以分别通过开关控制。
- 安装和配置资源后，用启用状态决定角色是否使用，不再增加一套授权操作。
- 开关关闭时既有任务链的延续按 DL-71 处理；具体默认状态与组织方式仍待确定，不将这些细节扩展成额外授权流程。

### DL-12 主动交流：角色可以主动发起对话

- 主动发起交流属于角色的核心能力，角色无需等待用户先发消息。
- 角色可以依据自己的动机，在 Nowadays 中与用户的主对话窗口主动表达，例如分享发现、延续话题或谈起共同经历。
- 主动发出的消息作为该窗口的正式对话记录保存；具体活动经历仍归入角色的记忆与活动日志。
- 主动交流的频率，以及是否通过 QQ 等外部渠道主动联系，尚未确定。免打扰当前不纳入功能范围，见 DL-13。

### DL-13 当前范围：暂不加入免打扰功能

- 用户明确决定当前不需要免打扰，暂不增加该功能。
- 本轮不规划免打扰时段、因免打扰暂存主动消息或结束后补发等行为。
- 本条不改变 DL-12 已确认的角色主动交流能力。
- 免打扰不继续作为当前待确认功能推进；将来用户提出需要时，再讨论是否加入。

### DL-14 角色工作空间：独立持久保存，默认位于 Nowadays 所在目录

- 每个角色实例拥有独立、持久的工作空间，保存笔记、收集的资料及任务成果。
- 角色可以在后续活动中打开、修改和引用此前保存的内容。
- 工作空间与记忆互相补充：记忆用于回想经历，工作空间用于保存和持续维护实际内容。
- 用户明确要求默认放在 Nowadays 所在文件目录下的专用文件夹中，不使用系统默认用户数据路径作为工作空间默认位置。
- 具体文件夹名称、角色子目录结构及路径配置方式尚未确定；本条仅确认存放原则，未创建运行数据目录或改变现有存储实现。
- 此决定针对角色工作空间，不自动扩展为所有现有数据和凭据的迁移决定。

### DL-15 模型配置：全局管理服务，角色按能力独立绑定

- 全局统一管理可用的模型服务。
- 模型选择与能力绑定归属于角色实例，目标设计从以 QQ 账号为配置主体转向以角色为主体。
- 每个角色可以独立选择模型，并按能力分别绑定，例如对话、图片理解和视频理解可以使用不同模型。
- 后台记忆整理模型默认继承角色对话模型，允许单独绑定，见 DL-124。
- 同一角色在 Nowadays、QQ 及其他对话入口中沿用该角色的模型配置。
- 角色、对话及记忆处理的统一模型调用边界与服务适配职责见 DL-117。
- 具体配置结构、能力绑定字段和界面方案尚未确定；重写版按 DL-38 从全新数据开始，不安排旧账号策略迁移，本条不代表已修改旧分支配置实现。

### DL-16 记忆基础：以经历事件组织记忆，关联原始证据

- 采用用户专门设计并在参考底稿中提出的事件记忆组织与检索基础：经历事件关联原始证据。
- 保留实际发生的原始记录，包括对话、网页阅读记录和工具执行结果等。
- 从原始记录中整理可检索的事件记忆，描述发生了什么，并关联对应证据，以便回忆时追溯具体内容。
- 事件来源覆盖角色参与的对话与自主活动，适配 DL-04 的多窗口和 DL-07 的自主活动。
- 角色的计划、猜测与实际完成的事情在记录中应有所区分。
- 本条确认记忆的基础组织方式；后台整理与触发原则见 DL-20～DL-22，召回原则和检索基线见 DL-17、DL-23、DL-51，完整接入范围见 DL-87。具体字段、阈值和接口继续细化，不等于采纳参考底稿全部细节。
- 后续可以提出优化建议，但需与用户讨论确认后再修改已确认设计。

### DL-17 召回原则：多维事件索引与按需深入检索

- 用户确认“自动召回相关事件＋角色按需深入检索”的方向，P2 接入完整 Agent 链路见 DL-87；具体检索查询构造、图节点与接口仍待细化。
- 事件形成后，为其建立时间、事件名称、情绪、内容等多个可检索维度，支持记忆召回。
- 常规对话自动获得相关事件概况；需要具体原话、前因后果或更多证据时，角色可进一步查阅事件及对应原始记录。
- 用户提出的普通对话如何形成事件问题，已通过 DL-18～DL-22 确认粒度、后台整理、触发与保存职责；跨批次归并边界见 DL-96，触发数值见 DL-94，具体接口及精炼阈值继续细化。
- 触发与检索基础分别按 DL-21、DL-51 执行，具体切分、查询构造、排序与预算参数继续讨论；“事件确认”不预设为必须由用户人工审核。

### DL-18 事件粒度与生命周期：筛选零碎日常，精炼低召回事件

- 用户基本认可对话逐步整理、补充事件再形成记忆的方向，同时明确要求控制事件粒度，避免产生过多细小事件。
- “今天吃了什么”等零碎日常不应全部整理为独立事件；需要在事件形成环节进行筛选或聚合。
- 可以考虑事件级别筛选、事件触发统计等方式；具体采用哪种机制尚未确定。
- 对经过一定对话轮次、较少被召回的事件进行精炼，使其不再作为独立事件保留。
- 原始记录的保留与追溯仍遵循 DL-16；精炼事件不等于删除原始对话。
- 精炼去向已在 DL-19 确认为简短日常摘要，召回统计口径见 DL-97，初始观察轮次及候选阈值见 DL-98；具体整理判断与保存接口仍待细化，尚未实现验证。
- 后续提出的“日常片段／一般事件／重要事件”三档优先级方案不采用，见 DL-23。事件形成阶段的粒度筛选继续保留。

### DL-19 事件精炼去向：合并为简短日常摘要

- 对符合精炼条件的零碎事件，合并为简短的日常摘要，撤去各自的独立事件索引。
- 摘要正文只概括话语段，不复制原句或建立逐句证据清单；按 DL-92 在后台保留窗口和时间／消息范围，必要时再在该范围检索原始记录。
- 原始记录继续保留，不因事件精炼而删除。
- 摘要聚合范围及补充方式见 DL-99，统一检索入口见 DL-93；具体长度、更新及检索接口仍待细化。
- 上一轮提出的“同时考虑重要性和未完成状态”等优化建议尚未逐项确认，不作为本条已确定的精炼条件。

### DL-20 记忆整理：独立于实时对话的后台流程

- 角色正常聊天和开展活动，记忆整理由独立后台流程读取已经保存的对话及活动记录后进行。
- 整理流程承担批量整理事件、补充索引及精炼日常摘要等职责。
- 可以积累上下文再判断事件边界，不要求每次回复都额外调用一次记忆整理模型。
- 尚未整理的新消息保留在近期上下文中，供角色使用。
- 本条确认职责与执行流程分离，不增加另一角色主体或强制单独模型服务；首轮按 DL-123 在同一后端进程内独立调度，模型选择见 DL-124。
- 整理触发见 DL-21、DL-94、DL-95，记忆维护预算归属见 DL-109，批次调度见 DL-126，容量与超长记录原则见 DL-127；具体预算值与接口仍待细化。

### DL-21 整理触发：记录积累、交流停歇与活动结束相结合

- 对话窗口内新增待整理消息累计达到 50 条时，安排整理，具体数值见 DL-94。
- 新增待整理消息至少 30 条，且交流停歇 60 秒时，安排补充整理，具体数值见 DL-94。
- 阅读、观看视频或执行具体任务结束后，若有新记录，将相关经历交给整理流程，不要求凑够聊天消息数量；具体边界见 DL-95。
- 触发条件由程序判断，有新记录才需要整理。
- 触发整理仅表示检查相关内容，不直接决定事件边界；已有事件可以继续补充，也可以没有值得新增的事件。
- 对话数量与停歇阈值已在 DL-94 确认，活动结束边界见 DL-95，触发合并与批次见 DL-126，容量分批原则见 DL-127；具体预算值及去重接口仍待细化。

### DL-22 整理职责：模型判断语义，程序校验并保存

- 整理触发后，整理模型读取新增记录与相关事件草稿，依据后续确定的筛选标准判断事件的语义归属和价值。
- 整理模型可以提出新建事件、补充已有事件、归入日常概况、暂留待续四类处理结果。
- 程序检查引用的来源记录是否存在、结果格式是否正确、修改目标是否合法，再保存结果并更新索引。
- 本条确认模型与程序的职责划分；具体筛选标准、结果协议与校验细则尚未确定。

### DL-23 检索简化：不额外设置固定事件优先级

- 当前不加入“日常片段／一般事件／重要事件”等固定优先级划分，沿用多维索引查找与按需深入回忆。
- 普通召回的事件摘要交给对话模型结合上下文使用，不额外要求另一个模型逐项审阅或打分。
- 当匹配结果过多时，可按当前查询的匹配程度控制放入上下文的内容；具体选择算法、数量与长度预算尚未确定。
- 事件形成阶段仍按 DL-18 控制粒度、筛选或聚合零碎内容；取消固定优先级不意味着所有片段均形成事件。

### DL-24 角色成长：保留主观体验，允许心理与理解随经历变化

- 事件记忆同时保留发生经过和角色的主观体验，包括感受与对经历的理解。
- 发生经过关联原始证据；感受与理解明确属于角色的主观体验。
- 用户明确目标是角色可以拥有自己的成长和变化；角色卡提供性格底色和基础，角色的心理活动、想法与理解可以在后续经历中变化。
- 角色可以重新理解旧事，原始经历与记录仍然保留。
- 角色经历带来的成长与用户主动更新角色卡分别理解，不把成长等同于重建角色实例。
- 此决定不新增角色设定冲突检测或处理，仍遵循 DL-03；独立当前状态及其自主局部更新见 DL-25、DL-48，日记联动见 DL-26～DL-28。具体体验字段、触发细则与接口仍待确定。

### DL-25 角色当前状态：独立保存并持续更新

- 单独保留一份持续更新的角色当前状态，以简短描述表达目前的心境、关注事项、关系感受和正在追求的目标。
- 角色运行时，将角色卡底色、当前状态与相关经历记忆共同作为上下文，使成长形成的变化能够延续到后续交流和自主活动。
- 当前状态由角色自主提出局部变化、核心校验保存的方式已在 DL-48 确认；具体接口、触发细则与保存结构尚未确定，不预设每条消息都调用模型重写状态。
- 角色日记与当前状态摘要联动见 DL-26，书写时机由角色自主决定见 DL-27，状态局部更新原则见 DL-48；具体执行接口和更新顺序仍待设计。

### DL-26 角色日记：与当前状态摘要联动

- 加入角色日记，与 DL-25 的角色当前状态摘要联动。
- 日记按时间积累，以角色自己的口吻记录经历、当时的想法和后续体会，表达成长过程。
- 当前状态保持简短，描述角色目前的近况；日记与状态关联同一段经历和反思，分别保留过程与当前变化。
- 状态随有意义的变化更新，日记可以在角色想记录时书写，不要求每次状态变化都生成一篇日记。
- 本条确认两者联动及职责；书写方式已在 DL-27 确认，具体触发机制、更新顺序和界面呈现尚未确定。

### DL-27 日记书写：由角色自主决定，作为自主活动执行

- 将写日记作为角色的一项自主活动，由角色决定何时书写。
- 角色可以在一段经历后想要记录，也可以自行安排稍后整理感受；用户也可以邀请角色写日记。
- 后台记忆整理负责保存和组织经历，角色日记表达角色对经历的理解，不把每批后台整理自动变为固定日记产出。
- 当前状态可以独立更新，不以角色写日记为前提。
- 本条确认书写自主权，不预设固定的每日书写次数或时间；日记参与记忆召回的原则已在 DL-28 确认。

### DL-28 日记召回：作为可检索的主观记忆，与事件关联

- 日记作为可检索的主观记忆，与对应经历事件关联保存。
- 回忆事件时，可以一并提供发生经过与角色后来写下的感受和理解。
- 经历记录与主观理解保留各自的来源和性质，共同影响角色后续表现。
- 同一经历的事件和日记关联组织，避免因日记再次描述而把同一次经历重复整理成多份事实事件。
- 本条确认关联召回原则，具体检索、去重与上下文组装方式尚未确定。

### DL-29 运行生命周期：关闭窗口继续运行，明确退出才停止

- 关闭 Nowadays 主窗口后，应用保留在托盘，角色继续处理消息和开展自主活动。
- 用户明确选择退出应用时，停止角色运行并保存状态。
- 下次启动延续原有角色身份与经历；重评估原则见 DL-30，任务与图恢复及资源延续见 DL-65～DL-73，P3 范围见 DL-112；具体唤醒调度接口仍待设计验证。
- 本条确认窗口关闭与应用退出的行为区别，不预设开机自启或应用退出后仍有独立常驻服务。

### DL-30 重启恢复：结合当前情况重新评估安排

- 再次启动后恢复角色状态，由角色结合当前时间、未完成事项和新消息，重新安排后续行动。
- 已经过期的安排不机械逐条补执行，角色可以决定继续、调整或重新安排相关活动。
- 应用退出期间没有实际开展的活动，不记录成已经发生的经历。
- 本条确认恢复原则，结果不明先核查见 DL-53，检查点、任务进度及资源延续见 DL-65～DL-73；具体进度字段、核查工具和调度接口仍待实现方案细化。

### DL-31 网页浏览：每个角色拥有独立浏览器环境

- 每个角色拥有独立的浏览器环境，保存自己的标签页、浏览进度和登录状态，与角色工作空间关联。
- 角色可以在自己的浏览环境中持续开展阅读等活动。
- 用户可以进入角色的浏览环境查看或共同浏览。
- 操作用户正在使用的浏览器，属于由电脑控制开关决定可用性的能力，与角色独立浏览环境的使用分别理解，不再另加授权操作。
- 本条确认浏览环境的独立性与使用方向；浏览器引擎、界面布局、具体数据目录及共同浏览的控制方式尚未确定。

### DL-32 视频观看：跟随播放进度理解，支持自主观看与共同观看

- 将观看视频作为有播放进度、可以持续进行的角色活动。
- 角色既可以自主观看，也可以与用户共同观看。
- 角色根据已经观看的内容交流，并支持暂停、回看或稍后继续的体验方向。
- 观看经历可以进入角色记忆，沿用已有经历与证据的组织原则。
- 本条确认体验目标，不代表已经验证实时感知能力；画面、声音、字幕如何提供给模型，以及播放实现和具体支持范围，后续验证确定。

### DL-33 电脑控制：提供可单独启用的完整桌面操作能力

- Nowadays 提供完整桌面操作能力，可由用户为角色单独开启或关闭，使用控制遵循 DL-59，不增加额外授权操作。
- 能力方向包含查看屏幕、操作鼠标键盘、打开和使用软件，开启后可用于本地阅读、文件整理或跨软件任务等活动。
- 网页和视频等日常活动沿用各自的专用能力；桌面控制用于进一步参与电脑上的其他工作。
- 本条确认具备该能力的产品方向，尚未实现或启动实际桌面操作。
- 共享真实桌面的协调原则见 DL-34，资源关闭后既有任务链的延续见 DL-71～DL-73；具体桌面工具、接管方式及在途操作处理仍待讨论，用户接管后暂停角色输入的决定继续保留。

### DL-34 桌面协调：统一调度，同一桌面单任务控制，用户可随时接管

- 共享真实桌面的操作由 Nowadays 统一协调，同一桌面同一时间只交给一个操作任务，其他任务等待。
- 多个角色可以各自开展活动，需要操作共享桌面时再取得控制权。
- 用户可以随时接管；接管后角色暂停桌面输入并保留任务进度。
- 本条确认桌面控制权的协调原则；接管方式、排队策略、暂停后的恢复及具体实现尚未确定。

### DL-48 状态更新：角色自主提出局部变化，核心校验保存

- 角色 Agent 在对话、活动或反思过程中，可以主动提出当前状态的局部变化，由核心校验后保存。
- 更新只作用于发生变化的部分，未修改的状态继续保留；没有变化时无需更新。
- 当前状态更新不以书写日记为前提，与 DL-27 的职责区分一致。
- 变化保存在角色当前状态中，原始角色卡继续作为基础设定保留，不因该状态更新流程而自动重写。
- 本条确认自主更新和局部修改原则，具体更新接口、校验细则及并发处理机制尚未确定；不增加 DL-03 已排除的角色设定冲突处理。

### DL-49 角色并发：决策串行，独立任务可并行

- 同一角色的决策按顺序进行，角色意图和当前状态按统一顺序更新。
- 已发出的独立任务可以并行执行；等待独立任务结果期间，角色仍可处理新消息。
- 任务完成后，其结果再交回角色的决策流程，由角色决定后续行动。
- 顺序约束针对同一角色，不同角色可以独立运行；共享真实桌面的操作仍遵循 DL-34 的统一调度。
- 本条确认并发边界；用户新消息优先、任务切换及当前回复中断分别见 DL-50、DL-69、DL-82，具体队列、图中断接口与任务结果归并仍待实现方案细化。

### DL-50 消息调度：用户新消息优先进入下一轮决策

- 用户的新消息优先进入角色的下一轮决策，已经发出的独立任务可以继续运行。
- 角色看到消息后，结合正在进行的活动决定如何回应，以及是否调整活动安排。
- 调度负责让角色及时注意到用户，具体回应与行动仍由角色决定，不因新消息自动取消全部独立任务。
- 同窗口多条消息的共同处理已在 DL-79 确认，输入状态与固定退出时间见 DL-80、DL-81，当前回复中断见 DL-82；具体队列与执行接口仍待设计，不能因合并消息而让发送方长时间等待。

### DL-51 第一版召回基线：多维条件过滤与全文检索

- 第一版以多维条件过滤与全文检索作为记忆召回的技术起点，沿用参考底稿的先程序检索思路。
- 用时间、情绪、来源等条件缩小范围，检索事件名称、摘要和内容。
- 全文检索优先验证 SQLite FTS5，中文分词及实际匹配效果需要单独验证，不预先宣称能够满足召回要求。
- 以实际查询样例建立测试基线，后续根据漏召回情况判断是否增加语义向量检索；向量检索当前保留为候选，不作为第一版必选依赖。
- 本条不确定具体查询构造、分词、排序、返回数量或上下文长度参数，也不增加 DL-23 已取消的固定事件重要等级。

### DL-52 自主活动预算：按角色配置，与主动对话分开统计

- 为每个角色的后台自主活动设置可配置执行预算，管理模型调用量和工具执行量。
- 使用有限额度且达到预算上限时保存活动进度，等待后续预算或安排再继续；无限制模式见 DL-107。
- 用户主动对话与后台自主活动分开统计，避免后台活动挤占正常聊天的预算。
- 用户交办任务及为回复用户进行的按需检索归属见 DL-110，不按前台或后台的位置计量。
- 自主活动统一使用一项额度，见 DL-104；每次实际模型或工具调用扣 1 点，见 DL-105；本地自然日恢复规则见 DL-106；默认每天 200 点并支持无限制，见 DL-107。具体执行限制接口仍待确定。

### DL-53 工具异常：明确失败自主处理，结果未知先核查

- 明确失败的工具调用，由角色在预算内决定重试、换方法或结束任务。
- 执行结果未知时，先核对实际状态，再决定后续操作；无法核实时保留未知状态。
- 不把连接中断或未收到响应直接等同于操作未发生，例如保存笔记后响应中断，应先检查实际文件状态。
- 本条确认异常处理原则，五种工具调用基础状态见 DL-70；具体状态转移、核查工具、重试上限与执行接口仍待确定，不代表所有工具都具有可核查的执行结果。

### DL-54 经历连续性：第一版不做剧情分支与回档

- 第一版每个角色采用一条持续的经历时间线，围绕独立数字生命持续成长的主线建设。
- 不同对话窗口仍各自保存，共同构成该角色的生活经历，不因统一经历时间线而合并聊天窗口。
- 第一版暂不实现平行剧情分支、剧情回档或重生，不直接采用参考底稿中的分支运行方案。
- 本条不取消角色数据备份、迁移和故障恢复的设计方向；数据恢复与主动回退剧情分别理解。
- 普通消息重试和历史记录编辑的具体规则不由本条自动确定；记忆人工修改的页面管理定位见 DL-55，具体修改规则仍待确定。

### DL-55 人工记忆修改：定位为页面上的数据管理操作

- 页面入口、交互及具体字段修改规则遵循 DL-45，在前端阶段再细化；人工管理对应后端的基础数据读写职责，角色自主核验与纠错另按 DL-56 设计。
- 本条不改变 DL-22 的后台记忆整理职责，也不增加 DL-03 已排除的设定冲突自动处理。

### DL-56 角色纠错：自主核验记录与陈述，判断后更正或回应

- 用户明确修订上一步决定，要求角色具备自主核验与纠错能力，不仅依靠用户在页面中修改数据。
- 角色可以检索记忆和来源，自行判断是记录错误，还是用户的回忆或表达有误，不预设任意一方总是正确。
- 若判断记录错误，角色可以更正对应记忆；若判断是回忆或表达有误，由角色结合自身性格与情境决定如何回应和处理，不强制采用固定纠错话术。
- DL-55 的用户页面数据管理入口继续保留；上一轮提出的“用户管理接口与角色行动工具分离”尚未获确认，不因本条自动写成新决定。
- 本条针对经历记忆和陈述核验，不引入 DL-03 已排除的用户角色设定冲突自动处理。
- 可修改的数据范围与原始来源保护已在 DL-57 确认；核验工具、证据不足时的处理及修订记录方式仍需逐项确定，不预设每轮额外调用独立审核模型。

### DL-57 纠错范围：更正整理后的记忆，保留原始来源

- 角色自主纠错可以更正整理后的事件、摘要与关联索引。
- 原始对话和实际活动记录保留原貌，作为角色核验与记忆追溯的依据，不由该纠错流程改写。
- 本条限定角色自主纠错的修改边界；用户页面上数据管理的具体可编辑范围与交互规则仍待前端阶段确认。
- 具体更正接口、修订记录、索引同步和并发校验方式尚未确定。

### DL-58 Skill 脚本：第一版支持执行，内容与环境由用户负责

- 第一版支持角色按需通过已启用的执行工具运行 Skill 随包脚本，执行结果进入统一任务记录。

- 系统进行实际加载、解析和调用所必需的处理，运行中自然产生的错误如实记录或返回，后续按 DL-53 交给角色处理。

### DL-63 执行分工：角色管理层持续调度，LangGraph 推进思考与行动

- 用户确认方案核对 R1 的职责边界；“角色运行时”在此更明确称为角色管理与调度层，避免与 LangGraph 自身的 Agent 运行时概念混淆。
- 角色管理层主要是普通应用代码，在应用运行期间接收消息、管理待处理任务、保存唤醒安排和维持角色决策顺序。
- LangGraph 组织角色的上下文读取、模型调用、记忆检索和工具使用，推进一轮思考与行动，产生回复、局部状态变化及后续安排；一轮可以包含多次模型与工具调用。
- 独立长任务交出执行后，让出角色的决策位置，角色可以处理其他消息；任务结果返回后进入角色队列，推进后续决策。短工具调用可以在本轮图执行中完成。
- 外围管理层保持轻薄，复用 LangGraph 已有的工具循环、检查点及恢复能力，不另造一套 Agent 执行引擎。两层可以在同一个程序进程中组织，具体部署不在本条确定。
- 应用运行时的待命不需要持续调用模型；退出、持久化和重启行为仍遵循已有生命周期决定。
- 具体图执行何时结束、何时检查点暂停后恢复，以及长短任务分类仍需细化，本条不把所有长流程强制定为同一种恢复方式；检查点分文件保存见 DL-65，执行编号映射见 DL-66。

### DL-64 提交顺序：先登记，再执行，保存结果后报告完成

- 用户确认方案核对 R2：输入先保存，再进入角色决策。
- 外部工具调用前先登记任务，再实际执行；结果返回后先保存，再反馈到角色后续处理。
- 本轮正式回复、局部状态变化与该轮完成标记，在同一角色业务数据库事务中提交，保存成功后再对外报告本轮完成。
- 任务登记不等于执行成功，本轮完成也不等于所有后台任务完成；结果未知继续遵循 DL-53 先核查的原则。
- 以上由后端自动完成，不增加资源开关之外的用户授权或审批操作。
- 工具调用基础状态见 DL-70，流式输出与未完成内容保留见 DL-77、DL-78；具体表结构、标识字段、回执去重及检查点提交接口仍待确定，不将外部工具调用或工作空间文件写入等同于数据库原子事务。

### DL-65 角色存储：业务库与检查点库分文件保存

- 业务库保存正式对话、记忆、角色当前状态和任务记录等长期业务数据；检查点库保存图执行阶段与恢复所需的必要中间状态。
- 两份文件都放在该角色的数据目录内，继续遵循角色数据隔离原则。
- 检查点用于继续执行，不能覆盖已经提交的业务记录；恢复时结合任务实际结果处理，结果未知仍按 DL-53 先核查。
- `role.sqlite` 与 `execution.sqlite` 仅为示意名称；检查点身份映射已在 DL-66 确认，实际文件名、驱动、保留与备份策略及跨进程恢复接口仍待验证确定。

### DL-66 检查点身份：每次决策独立编号，同次恢复沿用编号

- 用户确认方案核对 R4：每次决策拥有独立执行编号，对应 LangGraph 保存与恢复检查点所用的 `thread_id`。
- 新消息或自主唤醒引发新的决策时，创建新的执行编号；同一次决策暂停后继续或重启后恢复时，沿用原执行编号。
- 因同窗口新消息而被替代的旧回复不自动从检查点续写，按 DL-101 进入新的回复决策；这与未被替代任务的正常暂停恢复区分。
- 执行编号关联所属角色及相应对话窗口或自主活动，以区分不同执行的进度。
- 不同执行仍属于同一角色，角色身份、对话历史、当前状态和长期记忆继续由角色业务数据保持连续；同一角色决策串行的规则不变。
- 恢复时使用最新状态的原则已在 DL-67 确认；编号格式、关联字段、任务结果与执行的具体对应、上下文刷新接口及检查点保留周期仍待细化。

### DL-67 恢复信息：沿用执行进度，新的判断读取最新资料

- 用户确认方案核对 R5：恢复时沿用原检查点保存的执行进度，新的判断读取当前业务资料。

- 已提交的最新角色状态继续保留，不能用旧执行快照把角色状态退回过去；最新设定的使用不增加 DL-03 已排除的设定冲突自动处理。
- 以上由核心自动完成，不增加额外授权、审批或用户逐次确认。
- 具体上下文刷新接口、状态更新版本协调、旧的未提交输出处理与在途调用取消方式尚未确定。

### DL-68 工具调度：短暂等待，未返回则原任务自动转后台

- 用户确认方案核对 R6：工具调用先登记任务，允许短暂前台等待；及时返回就在本轮使用结果，尚未返回则原任务继续在后台执行，角色让出决策位置。
- 转后台沿用原任务编号与实际调用，不取消或重新发起工具调用，也不把前台等待窗口结束直接记为失败。
- 任务完成后先保存实际结果，再按原任务编号交回角色的顺序决策流程。
- 系统自动处理该衔接，用户无需逐工具手动分类；不改变资源仅由开关决定可用性的原则。
- 具体等待时长、执行总超时、结果归并和图暂停／结束接口仍待原型验证；转后台不代表外部服务必然支持进程退出后的继续执行或恢复。

### DL-69 任务切换：在可保存进度的位置让出注意力

- 收到用户新消息后，原任务在可保存进度的位置让出角色的注意力；已经发出的独立操作可以继续，返回的实际结果先保存。
- 原任务需要角色再次思考、选择或发起下一步时，优先让新消息进入角色决策；不因任务切换重复发起已在执行的操作。
- 角色结合消息和当前任务决定继续、暂停或结束原任务；暂停时复用已有任务档案保存进度，不另建一套活动存档与恢复机制。
- 区分实际操作进度、后台待处理结果与角色已接收处理的内容进度。后台返回字幕等内容，不直接代表角色已经理解相应内容；实际接收处理后才更新相应进度。
- 本条补充 DL-49、DL-50、DL-68 的切换行为；当前窗口新消息对未完成思考或回复的中断按 DL-82 处理，已发出的实际工具操作继续按原规则保存结果，不因切换而取消后重发。具体可保存节点、进度字段、图暂停／中断接口和结束任务时的在途操作处理仍待设计与验证。

### DL-70 工具调用记录：五种基础状态，前后台另记

- 工具调用记录区分待执行、执行中、成功、明确失败与结果未知五种基础状态。
- 待执行表示已登记但尚未调用；执行中表示已进入调用流程并等待结果，不单独证明远端已经开始处理；成功与明确失败需有已保存的明确结果。
- 无法确认实际结果时记为结果未知，按 DL-53 先核查，不能自动按失败重做。
- 前台／后台作为独立运行模式记录，转后台不改变实际调用标识，也不将执行中的调用直接记为失败。
- 角色暂停思考或任务切换不代表实际工具调用已经停止。以上是内部运行记录，不增加用户操作，不将工具调用状态直接当作角色持续任务的完整生命周期。
- 具体字段、枚举拼写、状态转移及取消、超时、重试尝试的细节仍待设计与验证。

### DL-71 资源关闭：前台立即关闭，既有任务链继续至结束

- 用户修订资源关闭方式：前台开关立即显示关闭，对新任务立即按关闭处理；关闭时已在执行的原任务链可以继续使用相关资源，直至该任务链执行结束。
- 保留范围是原任务链的后续执行，不只限于已经发出的单次调用；为完成该链所需的后续模型、MCP 或 Skill 使用仍可继续，不因资源开关关闭而截断任务链。
- 延续使用只属于原任务链，不使其他新任务或无关活动获得已关闭资源的使用能力；任务链结束后不再保留该链的延续使用。
- 以上由系统按任务归属自动处理，不增加额外授权、审批或用户逐次确认；实际调用仍按既有规则登记、保存结果和遵守预算及调度约定。
- 本条修订 DL-11、DL-59、DL-67 及方案 R5 中有关关闭后新调用的笼统表述，取代 R9 中仅允许单次在途调用结束的未确认建议。
- 任务链目标边界与结束判定已在 DL-72 确认，暂停与重启后的资源延续见 DL-73，链结束时的在途调用见 DL-103；具体持久化字段与资源释放接口仍待细化，不以单次工具返回或一轮图执行完成自动认定整个任务链结束。

### DL-72 任务链边界：按具体目标组织，由角色判断结束

- 任务链围绕创建时记录的一项具体目标组织，角色根据实际执行结果判断目标完成，或者决定放弃、无法继续而终止，并保存结束记录。
- 暂停、等待工具结果、临时回复消息仍保留原任务链；一轮图执行完成或单次工具返回不直接代表整条链结束。
- 新出现的独立目标另建任务，采用当时的资源开关状态；长期兴趣持续存在，通过一次次具体任务推进，不作为无限延续的单条任务链。
- 例如“看完视频 A 并写笔记”可作为同一任务链，笔记完成后结束；随后观看视频 B 属于新任务，不能沿用原链对已关闭资源的延续使用。
- 任务链结束后，按 DL-71 结束该链对已关闭资源的延续使用；暂停与重启后的延续按 DL-73 处理，在途调用按 DL-103 处理。具体字段与接口仍待细化。

### DL-73 任务恢复：持久保留原任务链的资源延续关系

- 原任务链对相关资源的延续关系与任务进度一起持久保存，临时暂停或应用退出不直接结束该链。
- 恢复后角色重新评估并决定继续原目标时，仍作为原任务链，可以继续使用该链原先保留的相关资源，直至任务链结束。
- 前台资源开关保持关闭，新任务不能使用这些资源；恢复原任务不将资源重新开放给其他任务。
- 继续复用已有任务档案，不另建活动存储或额外授权流程；恢复仍遵守最新角色资料、预算和结果未知先核查的规则，不据此假定外部调用会在进程退出期间继续执行。
- 同一资源的配置或内容修改按 DL-102 处理；具体持久化字段、资源连接重建与释放接口仍待设计验证，本条确认恢复语义，不代表已经实现。

### DL-74 Skill 加载：先提供简介，使用时按需读取

- 平时向角色提供当前任务可用 Skill 的名称、用途简介及读取入口，供角色选择。
- 角色判断需要使用某个 Skill 时，再读取完整的 `SKILL.md`；引用文档、素材和脚本根据任务需要读取或使用。
- 读取 Skill 不自动运行脚本，实际执行由角色按任务需要通过可用工具发起，继续遵守 DL-58。
- 使用通用目录规范，减少不必要的上下文占用；资源可用性继续遵守开关及原任务链延续规则，不增加额外审查、依赖预检或授权步骤。
- 具体发现目录、读取工具、上下文保留与缓存方式仍待实现方案细化，本条不代表已实现 Skill 加载器。

### DL-75 本地基础工具：随程序提供 MCP 文件与执行能力

- Nowadays 随程序提供一套本地 MCP 基础工具，负责文件读写、目录检索以及命令／脚本执行，供角色和通用 Skill 使用。
- Skill 保留通用目录与指令，角色按说明调用基础工具或已接入的外部 MCP，无需将每个 Skill 单独改写成 MCP 服务。
- 基础工具沿用已有资源开关、任务链资源延续和统一调用记录，依赖与运行环境仍由用户处理，不增加额外审查、依赖预检或授权步骤。
- 具体工具接口、进程组织、路径与运行方式、角色隔离仍需设计和 P0 验证；本条不选择实现包或承诺所有第三方 Skill 直接可运行，尚未开始实现。

### DL-76 外部 MCP：支持本地 stdio 与远程 Streamable HTTP

- 第一版支持本地命令启动的 stdio MCP 服务，以及通过服务地址连接的远程 Streamable HTTP MCP 服务。
- 本地方式由用户填写启动命令和参数，Nowadays 启动服务并连接；远程方式由用户提供服务地址等必要连接配置。
- 两种方式沿用相同的资源开关、任务登记、实际结果保存及原任务链资源延续规则，不增加额外授权或审批操作。
- 首轮后端原型已用本地 MCP 样例跑通主链路，远程连接按 DL-115 在桌面前端完成后实施，具体服务兼容性仍需实际验证。
- 具体协议版本、SDK、连接配置字段、远程凭据和重连方式仍待设计验证；本条不等同于支持所有 MCP 可选能力或所有历史传输方式，尚未完成实现。

### DL-77 对话输出：支持流式回复，区分生成、完成与中断

- 后端从首轮原型开始支持面向用户回复文本的流式输出，通过 CLI／API 在生成过程中逐步提供增量文字，桌面页面以后再设计。
- 生成中的回复标记为生成中，尚未报告完整完成；正式回复、局部状态变化和本轮完成标记按 DL-64 保存成功后，才报告已完成。
- 中途出错或中断时标记已中断、明确尚未完成，并保留当前进度说明，不将已经显示的部分文字视为完整成功回复。
- 中断部分文字的保留原则已在 DL-78 确认；具体传输方式、事件字段、保存结构和重连补发仍待细化。工具调用及结果保存继续遵守已有规则，文本输出不单独证明实际操作成功。
- 本条确认后端输出行为，尚无实现或验证结果，不改变先后端、后前端的推进顺序。

### DL-78 中断回复：保留部分文字及其未完成状态

- 中断时已经输出的部分回复保留在对话历史中，明确标注已中断、未完成。
- 角色后续读取相关对话时，可以看到部分文字及其状态，知道此前已经输出过哪些内容；不将其当作完整成功的回复。
- 本轮不会因部分文字被保留而标记为完成，也不将尚未成功提交的局部角色状态当作已经正式更新。
- 例如输出至“我刚才看到的视频里……”时中断，保留这部分原文及中断状态；同窗口新消息中断后的回复方式见 DL-101，不要求机械续写原句。
- 具体持久化结构、增量保存与发送顺序、客户端接收状态及重连补发仍待实现方案细化，尚未开始实现或验证。

### DL-79 连续消息：同窗口共同处理，启动时机需兼顾响应体验

- 用户认可下一轮决策开始时，将同一窗口中尚未处理的消息一起交给角色，由角色决定共同回应或分别回应。
- 每条消息仍独立保存，保留原文、顺序与来源，不将不同对话窗口的消息合并为同一窗口上下文，也不要求每条消息各自启动完整一轮思考。
- 用户补充必须确定下一轮决策的启动时间，避免因等待过久损害发消息方的对话体验；本条不将“共同处理”解释为可以无限等待消息积累。
- 下一轮回复调用结合 DL-80 的正在输入状态触发，停止输入 1 秒后退出的固定默认规则见 DL-81，当前回复中断见 DL-82；具体执行接口仍待验证，不将输入状态时长等同于完整响应时间承诺。

### DL-80 对话启动：用户正在输入时等待，退出状态后再调用

- 用户要求在 Nowadays 内加入“正在输入”状态，与连续消息共同处理方案配合；当前仅在系统内生效，不扩展到 QQ 等外部平台。
- 已经发送的消息先按既有规则保存；用户仍处于正在输入状态时，暂缓该对话窗口的下一轮回复模型调用，等离开正在输入状态后再进入调用调度。
- 调用时结合该窗口已经发送但尚未处理的消息，由角色共同判断和回应；正在输入状态本身不是一条已发送消息。
- 本条确认对话调用的启动条件；已经开始的思考或回复按 DL-82 处理，用户实际发送新消息才触发中断，单纯进入输入状态不打断当前回复。
- 输入状态进入与停止输入 1 秒后退出的固定默认规则见 DL-81，窗口关闭、断线与重启后的失效见 DL-84；具体接口及发送与继续编辑的状态交接仍待细化。当前仍为设计阶段，不提前实现正式页面。

### DL-81 输入状态退出：固定默认 1 秒，不提供用户配置

- 用户实际输入或编辑时进入正在输入状态，继续编辑则刷新计时；停止输入 1 秒后退出。
- 输入法仍在组词、选字期间保持正在输入，仅输入框保持焦点不持续维持该状态。
- 退出后，仅在存在已发送而尚未处理的消息时进入回复调度；未发送的草稿不触发回答，也不作为已发送消息交给模型。
- 用户明确要求目前使用固定默认 1 秒，不提供用户配置项；后续确有变更需要时再讨论修改，不采用此前建议中的用户可调整初始值。
- 本条决定输入状态的退出规则，新消息中断当前回复见 DL-82，客户端离开后的状态清理见 DL-84；具体状态交接、断线检测与接口仍待设计，尚未开始实现。

### DL-82 回复中断：实际发送新消息才打断，输入结束后再决策

- 当前对话中，角色已经开始思考或回复时，用户实际发送新消息才触发当前未完成思考或回复的中断；单纯继续打字或进入正在输入状态不打断已经开始的回复。
- 中断后保存已经输出的部分内容及进度，部分回复继续按 DL-78 标记未完成。
- 等用户退出正在输入状态后，再结合已发送的新消息进入下一轮决策；同一角色仍按顺序推进有效决策，不同时执行两轮有效思考。
- 已经发出的实际工具操作按既有规则保留结果，不因回复切换而取消后重发；原任务链的继续、暂停或结束仍交给角色判断。
- 本条补充 DL-49、DL-50、DL-69、DL-79～DL-81 的调度与切换行为。具体图中断、模型调用取消、旧输出处理与保存顺序仍需 P0 验证，不假定取消本地等待能够停止远端模型计算，尚未开始实现。

### DL-83 客户端断线：后端原执行继续，重连读取已有结果

- CLI／桌面客户端连接断开时，只要后端仍在运行，正在进行的原决策与工具任务继续执行并保存结果，不因客户端断线直接停止。
- 客户端重新连接后读取原执行的进度和已有结果，不因重连自动创建新决策、重新调用模型或重复执行工具。
- 应用进程完全退出时，仍按已确认的保存、停止与重启重评估规则处理，不据此增加退出后继续运行的常驻服务。
- 具体重连补发、事件关联、客户端显示去重及连接状态接口仍待设计验证；输入状态在断线后的清理按 DL-84 处理，尚未开始实现。

### DL-84 输入状态清理：窗口关闭、断线或重启后清除

- 正在输入作为临时运行状态；关闭对应聊天窗口、确认对应客户端断线或后端重启时，清除相应状态，不从旧状态恢复为仍在打字。
- 已发送并保存的待处理消息继续按既有规则处理，避免角色持续等待已经离开的客户端输入。
- 未发送草稿不会因状态清理而交给模型，已完成消息也不因清理状态而重新触发处理。
- 具体窗口与连接归属、断线检测和状态交接接口仍需设计验证，不新增用户配置项或提前实施正式页面，尚未开始实现。

### DL-85 P0 首要验证：最小工具链的中断、保存与恢复

- 用户确认 P0 技术小样优先验证“LangGraph 思考 → 调用本地 MCP → 保存结果 → 中断或暂停 → 恢复执行”的最小链路。
- 重点验证已完成的工具操作不重复执行、中断后旧输出不覆盖新回复，以及恢复时读取最新角色资料并保留已完成结果。
- 先使用可控离线模型、本地 MCP 样例、实际 LangGraph 和角色业务／检查点 SQLite 存储验证，记录实际依赖版本、接口与运行证据，再据此展开角色业务模块。
- 离线小样不替代真实模型或远程服务验收；P0 不建设正式页面、完整记忆整理或全部角色管理接口。
- 本条确认实施方案中的验证目标，不代表已完成验证，也不自动启动编码、安装依赖或推送远程。其他工作包与具体技术组合继续核对。

### DL-86 P1 完成范围：角色创建、数据持久化与资源配置

- 用户确认 P1 建立单角色的数据基础：创建角色，建立独立数据库和工作空间。
- 保存和读取角色设定、当前状态、消息，以及模型、MCP、Skill 的必要配置、绑定和开关。
- 通过 CLI／API 验证“创建 → 保存 → 读取 → 停止并重新启动后读取”的数据连续性；角色设定更新保持身份与经历，不增加设定冲突处理。
- P1 以数据与配置可保存、可读取为完成边界，模型回复和实际工具调用在 P2 接入；第一轮仍只验收单角色，正式前端、旧数据迁移与完整记忆整理不进入 P1。
- 具体字段、资源配置存储位置与接口仍待设计，不预先决定共享 MCP 实例或所有资源统一分库；当前确认范围，尚未开始实现。

### DL-87 P2 完整范围：记忆形成、检索与 Agent 对话回复闭环

- 用户要求 P2 完整加入此前讨论的 Agent 式记忆调用与消息回复功能，修订此前仅基础上下文或只读取预置事件的候选，不将完整记忆整理继续后置。
- P2 纳入既有事件记忆设计：保存对话和实际工具结果等原始记录，后台按已确认触发原则整理事件、补充多维索引、控制零碎事件粒度，并将符合条件的低召回事件精炼为简短日常摘要，保留原始来源。
- 回复链路自动召回相关事件概况，结合角色设定、当前状态和近期对话构建上下文；Agent 可以根据需要继续检索记忆、读取事件详情及关联原始记录，结合实际查询结果与按需 Skill／MCP 调用推进思考，再生成回复，不限于一次固定检索后直接回答。
- 此前已确认的角色主观体验、当前状态、日记关联召回及角色自主记忆纠错，按 DL-24～DL-28、DL-48、DL-56、DL-57 接入相关数据和对话调用；纠错只改整理后的记忆与索引，原始对话和实际活动证据保留。
- 正式回复、角色局部状态变化与本轮完成标记按 DL-64 保存；流式输出、输入等待、新消息中断、未完成部分保留及客户端重连继续遵守已有决定。
- 记忆整理仍按 DL-20 独立于实时回复运行，不要求每条消息先完成事件整理；尚未整理的新内容仍由近期上下文提供。检索沿用 DL-51 的多维条件与全文检索基线，不新增固定事件重要等级或默认向量依赖。
- 完成验收必须覆盖“实际对话／活动记录 → 自动整理事件和索引 → 后续问题召回 → Agent 按需追溯证据 → 回复 → 保存”的真实业务闭环，不能仅以手工预置事件或固定回复作为完整功能已实现的证据；离线模型与测试事件仍可用于自动化验证，不要求用户手工维护记忆。
- P2 可以拆分内部实施工作包，但完整记忆与 Agent 回复能力作为整体完成边界。整理触发与精炼初始阈值见 DL-94、DL-95、DL-98；具体字段、查询、排序、上下文预算、图节点及接口仍待细化验证。自主定时唤醒归 P3，范围见 DL-112；正式前端、QQ、自主浏览和视频／桌面控制不因本次调整自动纳入 P2。
- 本条修订 DL-60 的首轮记忆范围，并确认方案 R24 的完整方向；不代表已开始编码、通过验证或整体方案已经定稿，不提前推送远程。

### DL-88 P2 实施顺序：记忆形成、检索维护、Agent 对话联动

- 用户确认 P2 在完整范围内按三个内部步骤推进：先完成记忆形成与保存，再完成检索与维护，最后接入 Agent 对话联动。
- 第一步从实际记录接通后台事件整理、原始来源关联及索引保存；第二步完成查询、原文追溯、日常精炼、主观记忆关联与限定范围的纠错；第三步将自动召回及按需记忆工具接入思考／工具循环，与回复和状态保存协同运行。
- 三步分别保留可核对的结果，全部联动验收后才算 P2 完成，不以局部步骤完成代替完整记忆与 Agent 回复能力。
- 这是开发依赖顺序，运行时后台整理仍独立于实时回复；具体内部编号、字段、接口及参数继续逐项细化，当前未启动实现。

### DL-89 记忆来源语义：按实际表达、完成状态和工具结果整理

- 用户确认后台整理模型结合已保存的原文、完成状态与关联工具实际结果，判断可以形成的记忆内容。
- 中断回复可以进入整理范围，其中已明确表达的信息可以按实际含义参与整理；截断部分保持未完成，不补成完整承诺或已完成动作。
- 工具是否执行完成依据实际结果；回复中断不抹除明确成功的工具结果，结果未知仍保留未知，不仅凭角色措辞认定成功。
- 未输出的草稿不当作已发生的对话，计划与意图不当作已完成动作；既有任务与意图仍可按原规则保存。
- 仍遵守已有事件粒度、聚合和触发规则，不要求每个中断生成独立事件，不增加额外审核、独立语义审查或用户确认。
- 具体记录关联、状态字段、增量保存与验收样例仍待实现方案细化，当前尚未开始实现。

### DL-90 基础自动召回：程序构造首批查询，Agent 按需深入

- 第一批自动召回由程序结合本轮已发送消息、当前窗口近期话题和角色当前关注事项，提取明确的人物、主题、时间等索引线索，执行多维条件与全文检索。
- 基础召回不固定额外增加一次独立模型调用；随后由 Agent 根据完整对话语义与召回结果，自行决定是否改写查询、进一步搜索事件或读取原始记录。
- 检索限制在所属角色范围，同一角色其他窗口的记忆仍可召回，不默认只查当前窗口。
- 时间、来源、情绪等仅在查询意图明确时作为约束，其他情况下作为匹配线索；不因角色当前心情或偶然词语排除其他相关经历。
- 无命中与证据不足时的处理见 DL-91；具体查询结构、中文分词、相对时间解析、去重排序、返回长度及错误接口继续细化，不据此采用参考底稿中的固定条数、轮数或预算，当前未启动实现。

### DL-91 召回不足：按需深查并保留不确定，区分无结果与查询失败

- 未命中仅表示本次查询没有找到相关结果，不自动判定事情从未发生或用户记错。
- Agent 根据当前话题决定是否需要历史依据：普通闲聊可直接回应，涉及过去约定、具体原话或事实核对时，可以改写查询，继续查找事件、日常摘要与原始对话。
- 继续检索仍无足够证据时保留不确定，由角色结合自身性格和情境决定如何表达或询问，不编造回忆，也不强制固定话术。
- 实际查询失败与成功但无结果需分别反馈给 Agent；搜索始终保持角色数据范围，不因扩大搜索而跨角色访问。
- 不强制每次未命中都增加模型／工具回合；具体深查参数、错误接口与返回长度仍待细化，当前未启动实现。

### DL-92 日常摘要来源：正文概括，后台保留话语段范围

- 用户采用比较中的第三种方式：日常摘要正文只做话语段总结，不复制原句，不对摘要中的每句话建立一对一原文映射。
- 后台保留所属对话窗口及时间／消息范围，作为需要时缩小原始记录查找范围的线索；原始聊天记录继续独立保留。
- 普通召回提供概括后的摘要，不自动附带原文或逐条来源引用清单；Agent 需要具体细节时，再在对应范围检索原始记录。
- 精炼前的零碎事件仍按 DL-19 退出独立索引，不因保留来源范围而恢复为独立检索结果；普通事件与原始证据的既有组织原则不因此改变。
- 本条细化 DL-19 的来源关联方式；统一检索入口后续已在 DL-93 确认，具体范围字段、去重与返回预算仍待细化，当前尚未实现。

### DL-93 统一记忆检索：事件与日常摘要共用入口

- 用户确认事件与日常摘要使用同一个记忆检索入口，同一次主题搜索可以返回相关的两类记录，结果标明事件或日常摘要。
- Agent 无需预先判断一段经历保存为何种形式，再决定使用哪个检索入口；需要细节时按结果类型进一步读取。
- 日常摘要继续按 DL-92 只提供概括内容，后台保留话语段范围，按需追溯原始记录，不自动附带原文或逐条引用。
- 已精炼的零碎事件不重新作为独立结果返回，记录类型不构成新的重要等级；具体接口、去重、排序与返回预算仍待细化，当前尚未实现。

### DL-94 对话整理阈值：累计 50 条，或至少 30 条且停歇 60 秒

- 用户修订 R30 的初始数值：对话窗口内新增待整理消息累计达到 50 条时安排整理。
- 当待整理消息累计至少 30 条，且交流停歇 60 秒时，也安排整理；少于 30 条不单凭停歇触发该条件。
- 计数针对尚未整理的消息记录，用户消息和角色回复按已有条数口径计，流式分片不重复计数；触发后仍由整理模型判断事件，不按 50 条硬切事件或强制新增事件。
- 该后台停歇阈值不改变 DL-81 的 1 秒输入状态退出值，也不阻塞实时回复。具体单批容量、记录状态变更及触发去重接口仍待细化。
- 用户当时询问第三项“活动”指什么，未在该次询问中确认新边界；解释后的任务边界与独立于消息数量触发方式已在 DL-95 确认。

### DL-95 活动结束整理：具体任务结束且有新记录时独立触发

- 用户确认这里的活动是角色围绕具体目标开展的一项任务，例如读完网页并整理笔记、整理完一批文件，沿用既有任务档案，不另建一套活动系统。
- 任务结束且产生新的实际活动记录时，安排后台整理该段经历，不要求先凑够 30 条或 50 条聊天消息。
- 一次普通回复、单次模型思考或单个工具返回，不直接等同于整项活动结束；任务途中暂停去回复消息，也不代表原任务结束。
- 仍由整理模型判断是否新建事件、补充已有事件、归入日常概况或暂留待续，不因活动结束强制生成独立事件；任务完成与终止的既有规则遵循 DL-72。
- 本条确认触发语义，不提前实现浏览器、视频等后续工作包；任务记录归集、触发去重及单批容量仍待细化。

### DL-96 事件归并：同一具体经历跨批次持续补充

- 用户确认按同一件具体事情的连续发展归并事件，不按整理批次、固定消息数或临时换话题直接切分。
- 后续记录继续同一经历时，补充原事件；独立的新经历可形成另一个事件，零碎日常仍遵循 DL-18 的筛选或聚合规则，不强制每件小事单独成事件。
- 整理模型结合新增记录与相关已有事件判断是否属于同一经历；例如今天讨论一次出行、明天补充其安排，可以持续补充同一个事件，避免每批整理重复新建。
- 本条不新增固定事件优先级；已有事件的查找、更新及索引一致性接口仍待细化，当前尚未实现或验证。

### DL-97 召回统计：实际提供给角色，同一决策同一事件只计一次

- 用户确认事件经自动召回实际放入角色上下文，或角色主动检索读取时，计为一次召回。
- 同一轮角色决策内，同一事件反复返回或读取只计一次，避免同轮多次读取抬高频次。
- 仅在数据库中匹配、未提供给角色的候选，以及后台整理、索引维护的内部检索，不计入角色召回次数。
- 不要求角色在最终回复中提及、引用或复述事件，也不增加模型判断是否真正使用记忆的额外调用；该统计记录可观察的召回行为，不等同于测量模型内在使用程度。
- 本口径用于后续低召回事件精炼；初始观察轮次及次数阈值已在 DL-98 确认，具体统计保存接口仍待细化，当前尚未实现或验证。

### DL-98 精炼候选阈值：至少 100 轮未补充，最近 100 轮召回不超过 1 次

- 用户确认第一版初始值：事件创建或最近一次补充新内容后，至少经过 100 轮对话，且最近 100 轮内按 DL-97 统计的召回次数不超过 1 次，进入后台精炼候选。
- 一轮指角色完成一次针对已发送消息的回复决策；同次决策处理多条消息、调用多次工具仍计一轮，同一角色各对话窗口合计，纯工具调用和后台整理不额外计为对话轮次。
- 事件有新内容补充后，重新计算观察期；此轮次不同于 DL-94 的消息条数。
- 满足候选阈值后，由后台整理模型结合内容判断是否合并为日常摘要，不直接强制精炼或撤去独立索引；实际精炼时沿用 DL-19、DL-92，原始记录保留。
- 本组值作为初始方案，后续根据实际效果讨论调整，不构成已验证的最佳参数；不新增固定事件重要等级，具体统计及提交接口仍待细化。

### DL-99 日常摘要归集：同角色按经历日期聚合，可分话题并持续补充

- 用户确认按同一角色、经历发生的日期归集需要精炼的日常内容，日期依据原始记录，不以执行精炼当天代替经历发生当天。
- 同一天内容较多或话题差别明显时，可以分成数条简短摘要，不强行形成一篇长摘要。
- 后续还有当天内容进入精炼时，可以补充相关摘要，日期仍归属原经历发生当天。
- 同一角色不同对话窗口的经历可以归集，后台保留各自窗口及时间／消息范围，不混并原始对话窗口；不同角色不合并，正文及按需追溯仍遵循 DL-92。
- 有待精炼内容时才整理，不要求每天固定生成；角色自主书写的日记继续独立保留，不被日常摘要替代。
- 日期时区、摘要长度及具体更新接口仍待细化，当前尚未实现或验证。

### DL-100 记忆并发修改：旧结果不覆盖新版本，受影响内容重新处理

- 用户确认后台整理与角色纠错同时处理相关记忆时，保存前若目标记录或作为依据的相关记忆已更新，旧结果不直接写入覆盖最新内容。
- 后台保留受影响内容的待处理状态，重新读取最新记忆及原始依据后再整理，不阻塞实时聊天；尚未保存的结果不标记为已完成。
- 记忆正文、来源关联及检索索引作为同一组修改一起更新，避免内容与搜索结果对应不同版本。
- 以上由系统自动处理，无需用户介入；不增加用户审批、内容审核或角色卡设定冲突处理，不让后台整理模型直接改写角色当前状态。
- 具体版本字段、提交单元、重新处理机制及其他记录的更新接口仍待设计验证；当前尚未实现或运行验证。

### DL-101 新消息替代旧回复：新决策重新组织回答，原任务与工具独立延续

- 用户确认同窗口新消息打断未完成回复后，旧回复保留已输出部分及中断标记，不自动从其检查点续写旧答案。
- 等用户退出正在输入状态后，由新决策结合待处理消息、已输出内容、最新角色资料及实际结果重新判断回应方式；角色可以继续原话题，也可以调整回答，不要求机械续写原句。
- 旧执行晚到的文本及未提交状态不写入新回复或当前状态；原回复的执行记录、业务任务链与工具调用分别关联保存。
- 中断旧回复不等于结束原任务链。已发工具按原调用保存真实结果，不因切换重复执行；新决策可读取这些结果，由角色决定原任务继续、暂停或结束。
- 本条不改变 DL-83 的普通断线继续原执行规则，也不取消未被新消息替代的任务按 DL-66、DL-67 暂停和重启恢复的能力。
- 具体标识、结果交接、旧输出隔离与上下文刷新接口待 P0 验证，当前尚未实现。

### DL-102 配置变更生效：已发调用沿用原配置，后续使用最新配置

- 用户确认任务执行期间修改同一资源的模型服务配置、MCP 连接配置或 Skill 内容时，已发出的调用沿用发起时的配置完成，不为切换配置而取消重发。
- 下一次尚未发起的调用或按需读取使用最新配置、最新 Skill 内容，不将整条任务链锁定在创建时的旧配置。
- 已完成步骤保留实际结果，不因配置变更重新执行；已关闭资源但原任务链按 DL-71、DL-73 延续使用的情况，也遵循此规则。
- 实际连接或执行错误仍按 DL-53 如实处理，不保证外部环境修改后旧服务仍可用，不自动替用户恢复旧配置。
- 本条针对同一资源条目的修改，删除及改绑另行核对，任务结束时在途调用见 DL-103；进程与连接交接、Skill 读取时机等接口仍待验证，不增加额外授权、审批或内容预检。

### DL-103 任务链结束后的在途调用：保存真实结果，不自动重启任务

- 用户确认角色按 DL-72 决定任务完成或终止后，不再发起该任务的后续调用，结束该链对已关闭资源的延续使用。
- 已发出的工具调用不因任务结束而强制取消或重复执行，继续接收并按原任务、原调用保存实际结果，不将未返回结果擅自标为成功。
- 晚到结果不自动重启已结束任务，也不允许原链继续派生新调用；角色在之后的决策中仍可读取实际结果。
- 相关调用结束且没有其他任务使用后，再释放连接等资源，不直接终止其他任务共用的连接或进程。
- 结果未知仍按 DL-53 处理，应用退出仍遵循 DL-29、DL-30，不保证外部调用一定返回或在退出后继续存活。超时、失联、晚到结果关联与释放接口仍待设计验证。

### DL-104 自主活动统一额度：模型与工具共用一项预算

- 用户要求自主活动采用统一的一项额度，不分别设置模型调用额度与工具调用额度，便于管理与使用。
- 模型与工具的自主活动消耗共用该角色的同一额度；沿用 DL-52 的按角色配置及用户主动聊天单独统计规则，不将用户主动聊天并入自主活动额度。
- R39 原先提出的两项独立额度方案不采用；统一额度的扣减方式后续已在 DL-105 确认为每次实际模型或工具调用扣 1 点。
- 额度周期及恢复规则见 DL-106，默认额度与无限制模式见 DL-107，耗尽处理见 DL-108，后台记忆维护归属见 DL-109；混合任务及具体接口仍待细化，当前尚未实现或验证。

### DL-105 统一额度扣减：一次实际模型或工具调用扣 1 点

- 用户确认自主活动采用统一点数，每实际发起一次模型调用扣 1 点，每实际发起一次工具调用也扣 1 点，共用同一余额。
- 用户只需配置总额度，不分别管理模型与工具的额度或扣减权重；例如两次模型调用、两次工具调用共扣 4 点。
- 同一次调用转后台、接收流式分片或重连读取已有结果不重复扣点，实际发起的新重试另计 1 点。
- 点数代表活动调用量，不代表精确费用；用户主动聊天继续按 DL-52 单独统计。
- 额度周期及恢复方式已在 DL-106 确认，默认值及无限制模式见 DL-107，有限额度耗尽处理见 DL-108，后台记忆维护归属见 DL-109；混合任务归属仍待讨论，具体计次保存与去重接口尚未实现或验证。

### DL-106 额度恢复周期：本地自然日零点恢复，不累积余额或离线额度

- 用户确认自主活动额度按本地自然日计算，每天零点恢复到用户设置的总额度，昨日剩余额度不累积。
- 余额及所属日期持久保存，同一天重启应用保留剩余额度，不重新发放。
- 关闭应用数天后，只恢复当前日的一份额度，不累计离线天数的额度。
- 额度恢复后，角色结合当前情况重新评估等待预算的活动，再决定是否继续，不虚构离线经历或直接重放全部旧操作。

### DL-107 默认额度与无限制：每天 200 点，可修改为无限制

### DL-108 有限额度耗尽：保存进度暂停新调用，接收在途结果

- 用户确认有限自主活动额度用尽后，只保存进度，不再为自主活动发起新的模型或工具调用。

- 若最后 1 点用于模型思考，模型返回尚未执行的工具请求，则先保存请求及进度等待，不继续透支额度；未发请求不记为已执行，也不额外调用模型生成收尾说明。
- 原任务保持暂停，不直接结束任务链；额度恢复后由角色结合最新情况和实际结果重新评估是否继续，已完成操作不重做。

### DL-109 记忆维护预算：不扣自主额度，不另设用户管理额度

- 角色自主决定写日记仍属于自主活动，按实际模型或工具调用扣点，不因涉及记忆而自动归入后台维护。

### DL-110 消耗按任务来源归属：用户任务不扣自主额度，自主任务继续扣点

- 角色自行发起的刷网页、写日记等活动按自主活动扣点；自主活动途中回复用户，只将回复所需调用归入用户对话，原自主任务后续调用仍扣自主额度。
- 用户仅询问进展不改变原任务归属，例如询问视频看到哪里，不将整项自主看视频任务改为用户任务。

### DL-111 混合模型调用：按发起目的计一次，后续工具分别归属

- 调用发起登记时记录归属，不根据最终文字事后猜测，也不额外调用模型判断；已发调用不因中途插入消息而重新归类或重复计数。
- 后续工具调用仍按各自实际服务的任务遵循 DL-110，计划在回复中被调整或提及，不使后续自主工具调用免扣点。

- 用户确认首轮后端提供仅监听本机回环地址的 HTTP API，处理消息发送、输入状态、配置修改及历史、记忆、任务等数据查询。

- CLI 作为薄客户端通过同一 API 验证，未来桌面界面复用该入口，业务核心仍可独立启动。
- 第一版继续为单用户本机桌面，不因此增加网页访问、远程部署或确定桌面框架；桌面模式的托盘与退出规则保持。
- 客户端断线后后端继续原执行，重连读取原进度和结果，遵循 DL-83；事件流断开不等于取消业务任务，不因重连创建重复调用。
- 端口、路由、消息及事件结构、补发去重与具体服务实现仍待细化验证，传输协议不替代业务持久化，当前尚未实现。

### DL-122 消息提交去重：同次重试沿用编号，主动再发视为新消息

- 用户确认客户端每次主动发送生成唯一提交编号；因断线或未收到回执重试同次发送时，沿用原编号。
- 后端将提交编号与角色、窗口和已保存消息持久关联，重复提交返回原消息及关联处理进度，不重复保存历史、登记处理或再次打断当前回复。
- 用户主动再次发送时，即使文字相同也生成新编号，视为独立消息，不按文本内容去重。
- 同一编号对应不同内容时返回明确冲突错误，不覆盖原消息；编号关联需跨重启保留。
- 以上由客户端和后端自动处理。本条仅针对消息提交，其他操作的去重、具体字段、保存顺序及唯一约束仍待设计验证，不保证外部工具的跨系统恰好一次执行，当前尚未实现。

### DL-123 首轮进程组织：一个 TypeScript 后端，职责分模块独立调度

- 用户确认首轮采用一个 TypeScript 后端进程，承载本地 API／SSE、角色管理与调度、LangGraph、后台记忆整理及数据库访问，各部分保持清晰模块边界与显式依赖。
- 首轮仍只验证单角色，不因进程组织扩充原型范围，不按角色或记忆职责分别部署独立服务。
- CLI 独立连接后端，未来桌面界面复用同一 API；MCP 按既有本地 stdio 或远程 HTTP 服务方式接入，工具侧职责独立。
- 同进程内记忆整理与实时回复仍独立调度，聊天不逐轮等待整理；角色决策串行、独立工具任务可并行的规则保持。
- 断线不直接停止后端，桌面模式明确退出仍按 DL-29 保存并停止，不增加退出后的常驻服务。
- 启动、关闭、连接管理与实际响应性仍需验证，内部工作线程等实现细节由实际证据决定，当前尚未实现。

### DL-124 记忆整理模型：默认继承对话模型，支持角色单独绑定

- 用户确认后台记忆整理默认沿用该角色的对话模型，无需额外配置才能使用。
- 需要时可以为该角色单独选择记忆整理模型，仍从全局已配置模型服务中选择，沿用 DL-15 的角色能力绑定方式。
- 复用的是模型服务配置与调用实现，不复用角色当前聊天上下文；记忆整理根据自身待整理记录、相关事件和整理职责构造输入，按既有条件独立运行。
- 后台记忆整理仍不直接替角色更新当前状态或写日记，预算归属遵循 DL-109，不新增额外审核模型或固定三模型槽位。
- 本条确认默认继承及按需覆盖，失败进度和重试原则见 DL-125；具体字段、开关与任务链关联、重试调度接口仍待验证，当前尚未实现。

### DL-125 记忆整理失败：保留待处理进度，后台延后重试且不自动换模型

- 用户确认模型请求、整理结果保存等步骤失败时，保留原始记录及未完成内容的待整理状态，记录实际错误，不提前推进完成标记。
- 对应记忆结果、来源及索引成功保存后，才标记该处理范围完成；已成功提交部分保留，重试不重复生成事件。
- 失败内容由后台稍后重试，不阻塞聊天，不要求重新等到新消息凑够 30 条或 50 条；配置恢复或重启后可继续调度待处理内容。
- 连续失败时逐渐延长重试间隔，不在实时回复链中紧密反复调用，也不自动切换其他模型服务；具体间隔和次数在实施时再定。
- 重试前读取已保存进度及最新相关记忆，沿用 DL-100 的旧结果不覆盖新版本规则。保存顺序、处理标记、去重约束及调度接口仍待验证，当前尚未实现。

### DL-126 后台整理批次：同角色单批串行，合并触发并固定输入范围

- 用户确认同一角色同一时间只运行一个后台记忆整理批次，消息积累、交流停歇及活动结束等多个触发合并登记，不同时启动多份整理处理相同记录。
- 批次开始时固定本次处理记录范围；执行期间新增记录保留待处理，按既定触发条件交由后续批次处理。
- 批次完成后检查排队请求及待处理范围，已成功整理的内容不重复处理；失败范围继续按 DL-125 后台延后重试。
- 合并的是调度请求，不混并各窗口原始聊天，保留各自来源与范围；不同角色独立调度。
- 该串行仅约束后台整理，不占用角色实时决策的位置，不要求聊天等待；角色纠错与后台记忆修改继续按 DL-100 协调。
- 容量分批及超长记录处理原则见 DL-127；具体预算值、触发登记、范围及去重接口仍待设计验证，不将触发阈值自动等同于硬切分容量，当前尚未实现。

### DL-127 整理容量：按可用上下文分批，超长记录分段且原文完整保留

- 用户确认后台整理按模型可用上下文容量分批，结合整理说明、相关事件和待处理内容，为结果输出预留容量，不另外按固定消息条数硬切。
- 待处理范围超出容量时按原始顺序分批；单条消息或活动记录过长时可分段输入，保留原记录归属和分段顺序，原始记录完整保存，不截断丢弃剩余内容。
- 未实际处理的部分继续保持待整理状态，对应范围处理并成功保存后才推进完成标记，不因输入截断提前标记完成。
- 同一事件跨批继续补充，沿用 DL-96，不因分批新建多个重复事件；单批串行与失败重试遵循 DL-126、DL-125。
- DL-94 的 50 条、至少 30 条且停歇 60 秒仍是触发条件，不要求一次将全部记录送入模型；具体容量预算、分段及位置记录接口由实施验证确定，不新增逐次管理批次的设置，当前尚未实现。

### DL-136 角色自主选择服饰，主页与对话共用导入素材

- 角色 Agent 从自己的可用服饰中决定当前穿着。主页和对话读取同一角色的当前服饰，对话在该服饰内选择表情和姿势差分。

- 图片只校验格式是否受支持、文件是否可解码。差分按文件名自动登记，名称含义不明确也可导入并供 Agent 调用。图片内容由用户管理。
