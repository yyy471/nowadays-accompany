# 首轮后端原型实施方案

日期：2026-11-02。

状态：**实施方案草案**。首轮目标已由用户在 [DL-60](161-digital-life-direction-decisions.md#dl-60-首轮后端原型验证单角色对话扩展持久化与自主唤醒) 确认；本文的模块拆分、接口与实施步骤是供后续逐部分细化的建议，不等于这些细节已经全部确认。尚未开始编码或完成集成验证。

## 1. 已确认目标

首轮原型打通一个角色的实际链路：

```text
创建角色
  → 加载模型、MCP、Skill 配置与开关
  → 通过 CLI／API 接收消息
  → 使用 Skill 调用一个 MCP 工具
  → 生成回复并保存到角色 SQLite 数据库
```

同时验证角色能按自己的安排再次唤醒、继续一次自主活动，并在应用重启后恢复已有状态。

首轮重点是 LangGraph、存储、扩展与调度协同运行。之后逐步补齐后台记忆整理和“自主阅读 → 笔记 → 经历记忆 → 主动分享”的完整闭环。

## 2. 范围边界

- 单角色原型，用 CLI／API 脚本操作和验收；第一版长期目标仍可管理多个角色。
- 先后端、后前端；本轮不建设正式界面，不决定复用旧前端。
- QQ／SnowLuma 接入后置，不以连接 QQ 作为角色运行前提。
- 第一版不做剧情分支和回档；数据恢复与任务恢复按已确认原则处理。
- 不迁移旧运行数据，不保留旧私有插件协议，不为旧接口增加默认兼容层。
- 模型、MCP、Skill 只用开关控制，不设计额外授权、审批或逐次调用确认。
- Skill 内容、依赖和环境由用户处理，不增加内容审查、预检或试运行步骤。
- 视频与完整桌面控制的具体排期尚未确定，不将它们自动列为本轮原型的完成前提。

## 3. 模块边界建议

以下是实施建议，后续逐部分评审，不在本文提前确定全部文件布局。

| 模块 | 首轮职责 |
| --- | --- |
| 契约 | 定义角色、对话输入输出、任务结果、状态变化和唤醒安排的传输结构 |
| 应用用例 | 创建角色、配置资源、提交消息、查询历史、启动与停止角色等操作 |
| 角色运行时 | 统一接收消息与任务结果，串行推进角色决策，管理独立任务和唤醒安排 |
| Agent 编排 | LangGraph 状态、模型与工具循环、角色状态局部更新和轮次结束处理 |
| 模型接入 | 根据角色的能力绑定选择模型，处理服务配置与启用状态 |
| 扩展接入 | MCP 工具发现与调用，标准 Skill 的读取与按需使用，连接统一任务记录 |
| 存储 | 角色独立 SQLite、原始记录、当前状态、任务与唤醒安排，工作空间文件 |
| 控制入口 | 提供 CLI／API 脚本使用的核心用例入口和运行结果查询 |

角色身份与数据归属由 Nowadays 掌握。LangGraph 检查点保存执行所需状态，与正式消息和经历记录分工明确，不存入无限增长的完整人生历史。

## 4. 角色执行链建议

```text
入口接收消息或运行触发
  → 定位角色、当前窗口与待处理事项
  → 进入该角色的顺序决策流程
  → 装载角色设定、当前状态、近期上下文
  → 根据开关提供可用模型、Skill 和 MCP 工具
  → LangGraph 推进模型／工具调用
  → 保存实际工具结果、正式回复和局部状态变化
  → 保留未完成任务与后续唤醒安排
```

- 同一角色决策串行，已发出的独立任务可以并行；结果返回后重新进入角色决策。
- 用户新消息优先进入下一轮决策，已有独立任务不因新消息被全部取消。
- 自主活动与用户主动对话分开统计预算，具体计量与默认值待定。
- 角色可以提出局部状态变化，不自动重写原始角色卡。
- 明确失败由角色在预算内处理；结果未知先核查，无法核实时保持未知。

消息正式保存、工具执行和状态更新之间的具体提交顺序，需要在接口与事务设计中验证，不能只凭图示假定已经具备一致性。

## 5. 持久化与恢复建议

### 5.1 业务数据

每个角色拥有自己的 SQLite 数据库，与工作空间位于角色数据目录。首轮需要覆盖的概念数据包括：

| 数据 | 用途 |
| --- | --- |
| 角色资料与当前状态 | 保留持续身份、基础设定引用与当前变化 |
| 对话与原始消息 | 保存窗口归属、输入、正式回复和来源 |
| 任务与实际结果 | 保存角色发起的操作及其完成、失败或未知状态 |
| 唤醒安排 | 保存角色安排的后续活动与处理状态 |

具体表结构、状态枚举、版本字段和唯一约束后续设计。应用级配置另外管理，其保存结构尚未决定。

### 5.2 执行恢复

- 再次启动后加载已有角色状态、未完成事项和唤醒安排。
- 角色结合当前时间和新消息重新评估，不机械逐条重放过期计划。
- 已经执行的操作需要根据实际结果核对，结果未知时不直接当作未发生。
- 停止期间没有实际开展的活动不写成已发生经历。
- LangGraph 的检查点驱动及其与角色数据库的物理组织方式，需要以 TypeScript 生态实际支持情况验证；本文不提前指定包或版本。

## 6. 扩展样例建议

首轮使用一个可重复运行的本地 MCP 样例工具，以及一个符合标准目录格式、指导角色调用该工具的最小 Skill。

- 工具返回易于核对的固定或确定性结果，以便验证实际调用，而非只根据模型回复认定调用成功。
- Skill 导入只读取和保存，不自动执行随包脚本。
- 随包脚本执行属于第一版已确认能力，首轮样例的具体脚本与运行语言需后续选择，不承诺所有外部 Skill 都能直接运行。
- 示例配置不包含真实密钥。真实模型服务验证由用户配置可用服务，结果单独记录。

| 阶段 | 目标 | 可检查结果 |

## 8. 验收场景草案

| 场景 | 需要看到的结果 |
| --- | --- |
| 单角色对话 | CLI／API 输入能得到回复，原始输入和正式回复保存到角色数据库 |
| Skill 与 MCP | Skill 被实际读取，指定 MCP 工具发生真实调用，返回结果与回复关联 |
| 资源开关 | 关闭的资源不被使用；启用资源直接可用，没有额外授权或审批流程 |
| 局部状态更新 | 角色提出的变化保存，未修改部分与基础角色卡保留 |
| 自主唤醒 | 唤醒安排持久保存，到时经角色决策推进一次活动 |
| 重启恢复 | 恢复角色状态，结合当前情况处理未完成事项和过期安排 |
| 预算与调度 | 自主活动预算独立统计，用户新消息能够进入下一轮决策 |
| 明确失败与未知结果 | 能区分明确失败和结果未知，按已确认规则继续处理 |

自动化回归使用离线模型与本地 MCP 样例，不自动调用付费模型或真实 QQ。真实服务验证与离线测试分别记录，不能互相代替。

验收脚本、命令和具体断言待实现工作包形成后补齐；当前没有可执行代码，不提供虚构的“已通过”测试结果。
