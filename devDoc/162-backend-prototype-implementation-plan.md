# 首轮后端原型实施方案

创建日期：2026-11-02。最后更新：2026-11-03。

状态：**首轮实施基线已确认（DL-129）**。首轮目标见 [DL-60](161-digital-life-direction-decisions.md#dl-60-首轮后端原型验证单角色对话扩展持久化与自主唤醒)，P2 按 DL-87 纳入完整记忆与 Agent 回复；R1～R64 已确认。具体工程契约在对应阶段实现前落实，尚未确认的用户行为仍逐项讨论，尚未开始编码或完成集成验证。

推进状态：[首轮执行清单](164-backend-prototype-execution-checklist.md)已按 R64／DL-129 确认为阶段推进依据；按 DL-62 同步文档及新旧分支，编码启动另行安排。确认的是范围与推进方式，具体依赖和接口仍需实际验证。

## 1. 已确认目标

首轮原型打通一个角色的实际链路：

```text
创建角色
  → 加载模型、MCP、Skill 配置与开关
  → 通过 CLI／API 接收消息
  → 自动召回相关事件概况，结合角色资料与近期对话构建上下文
  → Agent 按需继续检索记忆、读取原始证据、使用 Skill／MCP
  → 生成回复并保存到角色 SQLite 数据库
```

同时验证角色能按自己的安排再次唤醒、继续一次自主活动，并在应用重启后恢复已有状态。

首轮重点是 LangGraph、存储、记忆、扩展与调度协同运行。按 DL-87，后台记忆整理、事件索引、自动召回与 Agent 按需深入检索纳入 P2，必须从实际保存的记录形成记忆并用于后续回复。“自主阅读 → 笔记 → 经历记忆 → 主动分享”的完整自主活动体验及浏览器等其他能力继续按后续工作包安排。

## 2. 范围边界

- 单角色原型，用 CLI／API 脚本操作和验收；第一版长期目标仍可管理多个角色。
- 先后端、后前端；本轮不建设正式界面，不决定复用旧前端。
- QQ／SnowLuma 接入后置，不以连接 QQ 作为角色运行前提。
- 第一版不做剧情分支和回档；数据恢复与任务恢复按已确认原则处理。
- 不迁移旧运行数据，不保留旧私有插件协议，不为旧接口增加默认兼容层。
- 模型、MCP、Skill 只用开关控制，不设计额外授权、审批或逐次调用确认。
- Skill 内容、依赖和环境由用户处理，不增加内容审查、预检或试运行步骤。
- 视频与完整桌面控制的具体排期尚未确定，不将它们自动列为本轮原型的完成前提。

## 3. 模块职责与待细化布局

以下模块中，角色管理层与 LangGraph 的执行职责已按 R1／DL-63 确认；其他拆分及具体文件布局仍逐部分评审。

| 模块 | 首轮职责 |
| --- | --- |
| 契约 | 定义角色、对话输入输出、任务结果、状态变化和唤醒安排的传输结构 |
| 应用用例 | 创建角色、配置资源、提交消息、查询独立窗口历史与消息／活动记录、启动与停止角色等操作 |
| 角色管理与调度层 | 持续接收消息、任务结果和唤醒触发，维护角色的决策顺序、待处理事项与独立任务 |
| Agent 编排（LangGraph） | 推进一轮有界的思考与行动，组织上下文、模型与工具调用，提出状态变化及后续安排；复用图的检查点和恢复能力 |
| 模型接入 | 根据角色的能力绑定选择模型，处理服务配置与启用状态 |
| 扩展接入 | MCP 工具发现与调用，标准 Skill 的读取与按需使用，连接统一任务记录 |
| 记忆 | 原始证据关联、后台事件整理、索引与日常摘要精炼、自动召回、Agent 按需检索与来源追溯，按既有范围支持主观记忆及纠错 |
| 存储 | 角色独立业务 SQLite、单独文件保存的图检查点、原始记录、事件与索引、主观记忆、当前状态、任务与唤醒安排，以及工作空间文件 |
| 控制入口 | 按 DL-121 提供本地 HTTP API 与 SSE，CLI 及未来桌面共用入口，执行核心用例与运行结果查询 |

角色身份与数据归属由 Nowadays 掌握。LangGraph 检查点保存执行所需状态，与正式消息和经历记录分工明确，不存入无限增长的完整人生历史。

角色管理层保持轻薄，主要是应用代码，与 LangGraph 属于同一套角色 Agent 的不同职责。首轮按 DL-123 在一个 TypeScript 后端进程中组织 API、角色调度、LangGraph、后台记忆及数据库访问，各模块依赖显式、调度独立；不以新增模型或另一套 Agent 引擎实现调度。

## 4. 角色执行链

```text
入口接收消息或运行触发
  → 定位角色、当前窗口与待处理事项
  → 保存输入或需要持久保留的触发记录
  → 新决策登记独立执行编号；同次恢复取回原编号
  → 满足当前窗口输入状态条件后，进入该角色的顺序决策流程
  → 装载角色设定、当前状态、近期上下文
  → 自动召回相关事件概况及有关联的主观记忆，保留来源引用
  → 根据开关提供可用模型、Skill 和 MCP 工具
  → LangGraph 推进思考，按需继续查询记忆、读取事件详情与原始证据
  → 按需使用 Skill／MCP，每次外部工具调用先登记再执行
  → 工具结果先保存再反馈；独立长任务登记后交出执行并让出决策位置
  → 基于实际检索与工具结果继续判断，按需要再次检索或调用，再生成回复
  → 本轮正式回复、局部状态变化及完成标记在角色业务库中一起提交
  → 提交成功后报告本轮完成，管理层保留未完成任务和后续安排
  → 管理层继续接收任务结果、新消息及后续唤醒
```

独立的后台记忆链读取已保存记录：

```text
新增记录积累／交流停歇／活动结束触发
  → 按 DL-21 检查是否存在需要整理的新记录
  → 整理事件、关联原始证据、维护索引和精炼日常摘要
```

后台链按 DL-20 独立调度；主对话流程不逐轮等待它完成。不同窗口的近期上下文各自加载，同一角色长期记忆共享，检索结果保留来源窗口与平台标记，沿用 DL-04、DL-05。

- 同一角色决策串行，已发出的独立任务可以并行；结果返回后重新进入角色决策。
- 用户新消息优先进入下一轮决策，已有独立任务不因新消息被全部取消。
- 自主活动与用户主动对话分开统计预算；按 DL-104～DL-107 使用一项统一额度，每次实际模型或工具调用扣 1 点，有限额度按本地自然日恢复；默认每天 200 点，用户可修改或设为无限制。
- 角色可以提出局部状态变化，不自动重写原始角色卡。
- 明确失败由角色在预算内处理；结果未知先核查，无法核实时保持未知。
- 独立长任务等待期间不持续占用角色的决策位置，结果返回后进入角色队列，推进后续图执行。
- 图执行可以结束后启动后续决策，也可以利用检查点暂停和恢复；执行编号映射已按 R4／DL-66 确认，具体场景、编号字段和图恢复接口仍待细化。
- 暂停恢复时保留执行进度和已完成结果，后续思考及新调用使用最新角色设定、当前状态、资源开关与预算，遵循 R5／DL-67。
- 短工具调用与独立长任务按 R6／DL-68 自动衔接：短暂等待后未返回，原任务继续在后台执行并让出角色决策位置；不因转后台取消、重发或直接判定失败。

上述保存与执行顺序已按 R2／DL-64 确认。长任务可以仍在后台执行；本轮完成与任务完成分别记录，不能把任务登记当作成功。具体实现与一致性仍需通过验收场景验证。

### 4.1 已确认的工具等待与转后台（R6／DL-68）

1. 先登记任务及关联，再发起实际工具调用。
2. 在短暂前台等待窗口内取得结果，则按 R2 保存结果，在本轮继续处理。
3. 仍未返回时，保留同一任务与调用在后台进行，当前图执行结束或暂停以让出角色决策位置；具体图接口仍待验证。
4. 实际结果返回后先保存，再按原任务编号交回角色队列，推进后续决策。

等待窗口只决定调度方式，不等同于执行总超时。结果恰在转后台边界返回时需要只归并一次；进程中断后仍按实际状态与 DL-53 处理，不假定后台任务自动跨进程存活。

### 4.2 已确认的任务切换方式（R7／DL-69）

- 收到新消息后，在可保存进度的位置让出角色注意力；已经发出的独立操作可以继续，其结果先保存。
- 原任务需要角色再次思考、选择或发起下一步时，优先让新消息进入决策，由角色结合消息与当前任务决定继续、暂停或结束。
- 暂停进度复用已有任务档案，不另建独立活动存档与恢复机制；任务业务进度与图检查点各自保留其职责。
- 后台获取或分析的结果先作为待处理内容；只有角色实际接收处理后，才更新其已处理内容进度，不能用播放器位置或结果已返回推定已经理解。

当前回复中断按 R18／DL-82 处理；实际工具操作仍按原规则保存结果，不因回复切换而取消后重发。具体保存节点、进度结构、在途操作暂停／结束方式及图接口仍需设计验证，不承诺远端操作能即时停止。

### 4.3 已确认的流式回复与完成状态（R15／DL-77）

- 首轮后端通过 CLI／API 支持面向用户回复文本的增量输出，生成时标为生成中。
- 正式回复、角色局部状态变化与本轮完成标记按 R2 一起保存成功后，才报告已完成。
- 出错或中断时明确标为已中断、尚未完成，并保留当前进度说明；已显示的部分文字不代表完整回复成功。

本项不提前设计桌面页面；中断部分文本保留见 R16／DL-78，具体传输、事件字段、保存结构及重连补发仍待细化。实际工具结果仍单独保存，不能仅根据流式文本认定操作成功。

### 4.4 已确认的中断部分回复保留（R16／DL-78）

- 已经输出的部分回复保留在对话历史中，明确标注已中断、未完成。
- 角色后续读取相关对话时同时读取部分原文及其状态，能够知道此前已经输出的内容。
- 保存部分文字不把本轮标记为完成，也不将尚未成功提交的角色状态当作正式更新。

如何继续生成、具体增量保存与发送顺序、客户端接收状态及重连补发仍待细化，不预先决定自动重试、续写或覆盖原内容。

### 4.5 已确认的连续消息共同处理（R17／DL-79）

- 下一轮决策开始时，同一窗口中尚未处理的消息共同交给角色，由角色决定共同或分别回应。
- 每条消息独立保存原文、顺序及来源，不跨窗口合并上下文，不要求每条消息各自执行完整一轮模型决策。
- 用户要求明确下一轮的启动时机，避免长时间等待；启动条件按 R18／DL-80 结合正在输入状态，固定停止输入 1 秒后退出见 R19／DL-81，当前回复中断见 R18／DL-82。不将此时长当作固定响应时限。

### 4.6 已确认的正在输入状态与启动条件（R18／DL-80）

- 当前仅支持 Nowadays 内部对话窗口的正在输入状态，不接入 QQ 等外部平台。
- 已发送消息先保存；用户处于正在输入状态时，暂缓该窗口的下一轮回复模型调用，退出状态后再进入调用调度，并共同处理此前积累的已发送消息。
- 状态本身不是已发送消息；按 DL-82，用户实际发送新消息才触发当前回复中断，单纯进入输入状态不打断已经开始的回复。

状态进入与固定 1 秒退出规则见 R19／DL-81，客户端离开后的清理见 R21／DL-84；具体状态交接、断线检测及接口仍待设计。首轮可通过 CLI／API 模拟输入状态验证启动条件，不提前建设正式页面。

### 4.7 已确认的输入状态退出默认值（R19／DL-81）

- 实际输入或编辑时进入正在输入状态，继续编辑刷新计时；停止输入 1 秒后退出。
- 输入法仍在组词、选字时保持状态，仅输入框保留焦点不持续维持状态。
- 退出后，有已发送但尚未处理的消息才进入回复调度；未发送草稿不触发回答，也不作为已发送消息提交模型。
- 1 秒是当前固定默认值，不提供用户配置项，后续需要时再讨论变更。

当前回复中断方式见 R18／DL-82，客户端离开后的状态清理见 R21／DL-84；具体状态交接、断线检测及执行接口仍待设计。

### 4.8 已确认的新消息中断当前回复（R18／DL-82）

- 当前对话中，实际发送新消息触发当前未完成思考或回复中断；单纯打字不打断。
- 中断后保存进度与已输出部分，标注未完成；下一轮等待输入状态退出，再结合已发送的新消息开始，同一角色有效决策仍串行。
- 已发出的实际工具操作按原规则保存结果，不因回复切换而取消后重发。

具体图中断、模型取消、旧输出隔离和保存顺序需 P0 验证；不把本地取消等同于远端模型计算已经停止。

## 5. 持久化与恢复

### 5.1 业务数据

每个角色拥有自己的 SQLite 业务数据库，与独立的检查点库及工作空间位于角色数据目录。首轮业务库需要覆盖的概念数据包括：

| 数据 | 用途 |
| --- | --- |
| 角色资料与当前状态 | 保留持续身份、基础设定引用与当前变化 |
| 对话与原始消息 | 保存窗口归属、输入、正式回复和来源 |
| 事件、来源与多维索引 | 从实际记录整理经历，关联原始证据，支持自动召回和 Agent 深入检索 |
| 日常摘要与整理进度 | 保存零碎事件精炼结果及来源关系，追踪已整理记录和召回统计 |
| 主观记忆与日记关联 | 保留角色体验、日记及其事件关联，配合当前状态参与对话与回忆 |
| 任务与实际结果 | 保存角色发起的操作及其完成、失败或未知状态 |
| 唤醒安排 | 保存角色安排的后续活动与处理状态 |

具体表结构、状态枚举、版本字段和唯一约束后续设计。应用级配置另外管理，其保存结构尚未决定。

### 5.2 执行恢复

- 再次启动后加载已有角色状态、未完成事项和唤醒安排。
- 角色结合当前时间和新消息重新评估，不机械逐条重放过期计划。
- 已经执行的操作需要根据实际结果核对，结果未知时不直接当作未发生。
- 停止期间没有实际开展的活动不写成已发生经历。
- LangGraph 检查点与业务数据分文件保存的布局已按 R3／DL-65 确认；具体 TypeScript 检查点驱动和恢复接口仍需 P0 验证，不提前指定包或版本。

### 5.3 已确认的业务提交顺序（R2／DL-64）

- 输入或需持久保留的触发记录先保存，再交给角色决策。
- 每次外部工具执行前保存任务及其关联，实际调用完成后的结果先落盘，再交回角色。
- 正式回复、角色局部状态变化与本轮完成标记在同一角色业务库事务中一起提交，成功后再报告本轮完成。
- 任务结果未知时先核查，不能凭任务登记或检查点直接重做。
- 外部 MCP 调用、工作空间文件写入、图检查点与业务库之间的具体协调需要单独实现，不把它们预设为一笔跨系统原子事务。

### 5.4 已确认的数据库文件分工（R3／DL-65）

每个角色的业务库与 LangGraph 检查点库分文件保存，均放在该角色目录内。以下名称仅作示意：

```text
<角色目录>/
  role.sqlite        # 正式对话、记忆、当前状态及任务等业务记录
  execution.sqlite   # 图执行检查点与必要中间状态
  workspace/         # 笔记等工作文件
```

检查点用于继续图执行，业务库保留已提交的正式记录；恢复时结合业务任务状态判断后续动作，缺少已知结果的操作仍按未知处理。检查点身份映射见5.5节，具体文件名、驱动、保留及备份策略仍待确定，不因分文件布局假定两份数据库具有跨文件原子提交。

### 5.5 已确认的执行编号映射（R4／DL-66）

- 每次有界决策拥有独立执行编号，对应 LangGraph 检查点的 `thread_id`。
- 新消息或自主唤醒引发新决策时创建新编号；同一次决策暂停后继续或重启后恢复时沿用原编号。
- 执行关联所属角色、对话窗口或自主活动。角色历史与当前状态从角色业务数据装载，不以一个长期检查点线程替代角色人生存储。
- 多个执行编号不创建多个角色人格，也不改变同一角色决策串行的要求。
- 具体编号和关联字段仍需设计；恢复时读取最新资料的原则已在 R5／DL-67 确认，具体刷新接口仍待实现方案细化。

### 5.6 已确认的恢复资料原则（R5／DL-67）

- 恢复原执行编号、检查点进度和已经完成的实际结果。
- 后续模型判断与新工具调用使用最新角色设定、当前状态、相关上下文、资源开关和剩余预算。
- 保留已提交的最新业务状态，不用旧快照整份覆盖；更新仍按角色局部状态提交原则处理。
- 已关闭的资源不再供新任务使用；按 R9／DL-71，关闭时已在执行的原任务链可继续使用相关资源直至该链结束，实际结果照实记录。最新开关不被旧检查点覆盖，也不因恢复而重新开放资源给新任务。
- 本条不增加角色设定冲突检测或资源授权流程。具体版本字段、未提交输出处理及上下文刷新接口仍待细化。

### 5.7 已确认的工具调用基础状态（R8／DL-70）

| 状态 | 保存语义 |
| --- | --- |
| 待执行 | 已登记，尚未进入实际调用流程 |
| 执行中 | 已进入调用流程，执行或等待结果；不单独证明远端已开始处理 |
| 成功 | 已取得并保存明确成功结果 |
| 明确失败 | 已取得并保存明确失败结果 |
| 结果未知 | 无法确认实际结果，先核查，不自动按失败重做 |

前台／后台独立记录，转后台保持同一调用，角色暂停不代表实际调用已经停止。这些状态描述工具调用，不直接充当角色持续任务的完整生命周期。具体字段、状态转移、重试、取消与超时细节仍待设计，不增加额外用户操作。

### 5.8 已确认的资源关闭与任务链延续（R9／DL-71）

- 前台开关立即显示关闭，新任务立即按关闭处理。
- 关闭时已在执行的原任务链可以继续使用相关资源，包括为完成该链所需的后续调用，直到任务链结束。
- 延续使用限定于原任务链，不适用于其他新任务或无关活动；整条链结束后不再保留延续使用。
- 调用登记、实际结果保存、预算与同一角色决策串行规则继续适用，不增加额外用户操作。

任务链目标边界与结束判定见 R10／DL-72，暂停和重启后的资源延续见 R11／DL-73；具体归属字段与资源连接释放方式仍待设计，不将单次工具返回或一轮图结束等同于整条任务链结束。

### 5.9 已确认的任务链目标与结束（R10／DL-72）

- 创建任务链时记录具体目标，由角色根据实际执行结果判断完成，或者决定放弃／无法继续并终止，随后保存结束记录。
- 暂停、等待工具结果、临时回复消息保持原任务链，不以单次调用返回或一轮图执行完成代替整条链的结束。
- 新出现的独立目标另建任务，采用当时的资源开关状态；长期兴趣通过一次次具体任务推进。
- 整条链结束后，按 R9 结束该链对已关闭资源的延续使用。

具体字段、接口以及任务链结束时仍有在途操作的处理仍待设计。

### 5.10 已确认的任务恢复与资源延续（R11／DL-73）

- 将原任务链的资源延续关系与任务进度一起持久保存；暂停或退出应用不直接结束原链。
- 恢复时由角色重新评估，决定继续原目标后沿用原任务链及其保留的相关资源，直到整条链结束。
- 前台资源开关保持关闭，新任务仍不可使用；原任务恢复不重新开放资源。
- 仍使用最新角色资料与预算，未知结果先核查，不假定进程退出期间外部调用持续运行。

具体持久化字段、资源连接重建与释放、资源配置变化的处理仍待设计与验证，不另建活动存储或额外授权流程。

### 5.11 已确认的客户端断线与重连（R20／DL-83）

- 客户端断线时，只要后端仍在运行，原决策与工具任务继续执行并保存结果。
- 重连按原执行关联读取进度与已有结果，不因连接恢复而新建决策、重调模型或重发工具。
- 应用完全退出仍执行既有保存、停止和重启重评估规则，不新增退出后继续运行的常驻服务。

具体重连补发、事件关联和客户端显示去重接口仍待设计，输入状态失效方式见 R21／DL-84。

### 5.12 已确认的临时输入状态清理（R21／DL-84）

- 正在输入是临时状态，关闭对应聊天窗口、确认对应客户端断线或后端重启时清除，不恢复为仍在打字。
- 已保存的待处理消息继续按调度规则处理，未发送草稿不因此提交模型，已完成消息不重新触发。

窗口与连接归属、断线检测及具体状态交接接口仍待设计验证，不新增用户配置项或正式页面实施。

### 5.13 已确认的中断内容与记忆来源（R26／DL-89）

后台整理模型结合实际原文、完成状态与关联工具结果判断记忆。中断回复中已明确表达的内容可参与整理，截断处保持未完成，不补成完整承诺；工具成功、失败或结果未知按实际结果理解，不能只凭回复措辞判断操作已完成。

未输出草稿不作为已发生的对话，计划不作为已完成动作；任务意图可按原规则保存。仍遵守事件粒度、聚合与触发规则，不要求每个中断生成事件，不新增额外审核。具体记录关联、状态字段及保存接口仍待细化。

### 5.14 已确认的基础自动召回查询（R27／DL-90）

程序结合当前窗口已发送新消息、近期话题与角色关注事项生成明确的人物、主题、时间等检索线索，先取得相关事件概况，不固定额外调用独立模型。Agent 根据对话语义和基础结果决定是否改写查询、继续检索或读取原文。

角色归属是检索范围，同角色其他窗口记忆仍可召回；仅在意图明确时使用时间、来源或情绪等约束，其余作为匹配线索，不能由当前心情推定应排除其他情绪的经历。具体查询结构、中文匹配、相对时间、去重排序、返回预算与无命中处理仍待细化。

### 5.15 已确认的召回不足与查询异常（R28／DL-91）

未命中只表示当前查询未找到相关结果，不证明事情从未发生。Agent 根据问题是否需要历史依据，选择直接回应或按需改写查询、继续检索事件／摘要与原始对话；证据仍不足时保留不确定，自行决定表达或询问，不编造回忆或直接判定用户记错。

查询失败与查询成功但无结果分别反馈，检索始终在所属角色范围内。不强制每次未命中都增加模型或工具回合，错误接口与具体检索参数继续细化。

### 5.16 已确认的日常摘要来源粒度（R29 来源部分／DL-92）

日常摘要正文只概括话语段，不复制原句或逐句关联证据。后台保留原对话窗口与时间／消息范围，原始记录继续独立保存；普通召回不自动携带原文或逐条引用清单，需要具体内容时再由 Agent 在对应范围检索。

零碎事件精炼后仍退出独立索引，不因摘要范围关联而重新作为独立结果返回。此决定只细化日常摘要，不改变普通事件的证据关联；统一检索入口已按 DL-93 确认，具体范围字段、去重与返回预算仍待细化。

### 5.17 已确认的统一记忆检索入口（R29 入口部分／DL-93）

事件与日常摘要通过同一入口检索，同一次主题查询可以返回两类相关记录，并标明记录类型。Agent 根据结果按需进一步读取，无需先猜测保存形式；日常摘要仍按 DL-92 返回概括内容，需要时才查询后台话语段范围及原始记录。

具体接口、去重、排序与返回预算继续细化，已精炼零碎事件不重复作为独立结果返回，记录类型不表示重要等级。

### 5.18 已确认的对话整理触发数值（R30 数值部分／DL-94）

同一对话窗口中，新增待整理消息累计达到 50 条时安排整理；或者累计至少 30 条且交流停歇 60 秒时安排整理。未达到 30 条时，不单凭停歇触发本条件，无新增待整理记录也不重复触发。

用户消息与角色回复分别计条，流式分片不重复计数。该条件仅安排后台整理检查，不按 50 条硬切事件或强制产生新事件，不影响 1 秒输入状态规则或让实时回复等待整理。单批容量、状态变化及去重接口另行细化。

### 5.19 已确认的活动结束整理边界（R30 活动部分／DL-95）

角色围绕具体目标开展的任务结束且有新活动记录时，安排后台整理这段经历，不受 30 条或 50 条聊天消息阈值限制。沿用既有任务档案及 DL-72 的结束规则，不新建活动系统。普通回复、单个模型思考或工具返回不直接等同于活动结束；任务途中暂停去回复消息也不代表任务结束。

该条件不强制生成独立事件，也不提前启动浏览器、视频等后续工作包；记录归集、触发去重及单批容量继续细化。

### 5.20 已确认的跨批次事件归并（R31／DL-96）

整理模型结合新增记录与相关已有事件，按同一具体经历的连续发展判断归属：后续发展补充原事件，独立新经历另行处理，零碎日常沿用粒度筛选或聚合。不按整理批次、固定消息数或临时换话题直接切分，避免每批整理重复新建同一事件。查找、更新及索引一致性接口仍待细化。

### 5.21 已确认的事件召回统计口径（R32／DL-97）

事件通过自动召回实际进入角色上下文，或由角色主动检索读取时，记录召回；同一角色决策内同一事件只计一次。未提供给角色的搜索候选，以及后台整理和索引维护的内部检索不计。最终回复无需提及事件，也不增加模型使用判定调用。此统计供后续低召回精炼使用，观察轮次及次数阈值见 DL-98，具体保存接口仍待细化。

### 5.22 已确认的精炼候选阈值（R33／DL-98）

事件创建或最近补充新内容后至少经过 100 轮已完成对话，且最近 100 轮内召回不超过 1 次时，进入精炼候选。角色完成一次针对已发送消息的回复决策计一轮，同次多条消息、多次工具调用仍计一轮，同一角色各窗口合计；纯工具调用、后台整理不额外计轮次。事件补充新内容后重新计算观察期。

由后台整理模型结合候选内容判断是否精炼，不直接强制合并；实际精炼沿用既有日常摘要及原始记录保留规则。本组值为第一版初始方案，实际效果和统计、提交接口仍待验证，不新增固定事件重要等级。

### 5.23 已确认的日常摘要聚合范围（R34／DL-99）

待精炼内容按同一角色、原始经历发生的日期归集，同一天可以根据内容量及话题形成数条简短摘要；后续同日内容可以补充相关摘要。日期不使用执行精炼当天代替原始经历日期。跨窗口可在同角色范围归集，但后台保留各自窗口及时间／消息范围，不混并原始对话；不同角色不合并。

仅在有待精炼内容时处理，不要求每天固定生成；角色自主书写的日记继续独立保留。正文及来源范围遵循 DL-92，时区、长度及更新接口仍待细化。

### 5.24 已确认的记忆并发修改规则（R35／DL-100）

后台整理与角色纠错保存记忆时，若目标记录或作为依据的相关记忆已更新，旧结果不直接写入覆盖最新内容；后台保留受影响内容的待处理状态，重新读取最新记忆及原始依据后处理，不阻塞聊天或提前标记完成。记忆正文、来源关联及检索索引作为同一组修改一起更新。

系统自动处理，不增加用户介入、审批或内容审核，不涉及角色卡设定冲突判断，也不让后台整理直接更新角色当前状态。具体版本字段、提交单元和重新处理机制仍待设计验证。

### 5.25 已确认的新消息中断后回复处理（R36／DL-101）

被同窗口新消息替代的旧回复保留部分文字及中断状态，不自动从检查点续写；输入状态退出后，新决策结合待处理消息、已输出内容、最新资料与实际结果重新组织回答。旧执行晚到的文本和未提交状态不写入新回复或当前状态。

回复执行与业务任务链、工具调用分别关联；原任务由角色决定继续、暂停或结束，已发工具保存真实结果且不因回复切换重发。普通断线仍遵循 DL-83，未被新消息替代的任务暂停及重启恢复仍遵循 DL-66、DL-67。具体交接及隔离接口需 P0 验证。

### 5.26 已确认的资源配置变更规则（R37／DL-102）

修改同一资源的模型服务配置、MCP 连接配置或 Skill 内容时，已发调用沿用原配置完成，不为切换配置取消重发；后续尚未发起的调用或读取使用最新配置和内容。已完成步骤不重做，关闭资源后仍按原任务链延续使用的情况也遵循此规则。

实际错误按 DL-53 处理，不保证外部环境修改后旧服务仍可用，不自动恢复旧配置。任务结束时在途调用见 DL-103；删除、改绑及具体进程、连接与读取接口继续核对验证。

### 5.27 已确认的任务结束与在途调用处理（R38／DL-103）

任务链完成或终止后，不再发起该链的后续调用或延续使用已关闭资源；已发出的工具调用继续接收并保存真实结果，不因任务结束而强制取消或重发。晚到结果不自动重启原任务或派生新调用，仍可供角色后续决策读取。相关调用结束且没有其他任务使用后，再释放连接等资源。

结果未知与应用退出继续遵循既有规则，不保证外部调用必然返回或退出后存活；具体关联、失联处理和释放接口仍待验证。

### 5.28 已确认的自主活动统一额度（R39／DL-104）

每个角色的自主活动使用一项统一额度，模型与工具消耗共用该额度，不分别配置两套上限；用户主动聊天仍按 DL-52 单独统计。原先两项额度候选不采用。扣减方式按 DL-105，周期及恢复按 DL-106，默认值与无限制模式按 DL-107；具体消耗归属继续逐项讨论，当前尚未实现。

### 5.29 已确认的统一点数扣减（R40／DL-105）

每实际发起一次自主模型或工具调用，统一扣 1 点；用户只设置总额度，不分别管理模型和工具权重。同一次调用转后台、接收流式分片或重连读取已有结果不重复扣点，实际发起的新重试另计。点数代表活动调用量，不代表精确费用。周期及恢复按 DL-106，默认值及无限制模式按 DL-107；消耗归属仍待讨论，实际计次与去重接口待实现验证。

### 5.30 已确认的每日额度恢复（R41／DL-106）

自主活动额度按本地自然日每天零点恢复到用户设定总额，昨日余额不累积。余额及日期持久保存，同日重启不重新发放；跨数日退出后只恢复当前日额度，不累积离线天数。额度恢复后，角色根据当前情况重新评估等待活动，再决定是否继续。

每日默认点数及无限制模式见 DL-107；具体日期时区及周期切换、余额持久化和消耗归属接口仍待设计验证，当前尚未实现。

### 5.31 已确认的默认点数及无限制模式（R42／DL-107）

每个角色默认每天 200 点，用户可以修改总额度或设置为“无限制”。有限额度按 DL-105 扣点、按 DL-106 每日恢复；无限制时不因点数用尽而暂停，仍记录实际调用量，同一调用不重复计数。用户主动聊天仍单独统计，资源开关、任务归属及既有调度规则保持。

200 点为初始默认值，具体配置表示、运行期间修改方式和消耗归属等接口仍待细化，当前尚未实现或验证。

### 5.32 已确认的有限额度耗尽处理（R43／DL-108）

有限自主活动额度用尽后保存进度，不再发起新的自主模型或工具调用；已发调用继续接收保存真实结果，不强制取消或重复扣点。最后一点用于模型后返回的未执行工具请求保存等待，不透支额度，也不额外调用模型生成收尾说明。

原任务保持暂停，额度恢复后重新评估，不重做已完成操作或把未发请求记作已执行；无限制模式不触发暂停。请求记录、扣点及调用登记的保存顺序和恢复接口仍待实现验证。

### 5.33 已确认的后台记忆维护预算归属（R44／DL-109）

后台事件整理、日常摘要精炼及索引维护不扣角色自主活动额度，也不新增一项用户需管理的额度，只记录实际调用量。自主额度耗尽时，已保存经历仍按既有触发规则形成记忆。角色自主决定写日记仍属于自主活动，按实际调用扣点。

本条保持资源开关、实际错误处理和既有触发规则，不要求空闲时额外调用模型；任务来源归属见 DL-110，单次混合模型调用见 DL-111，具体记录接口仍待细化验证。

### 5.34 已确认的用户任务与自主活动消耗归属（R45／DL-110）

按调用所服务的任务来源计量，不按前台或后台位置计量。为回复用户所需的模型调用和记忆检索，以及用户明确交办任务的必要调用不扣自主额度，记录实际调用量，不新增用户管理额度；角色自行发起的活动仍扣自主额度。

自主活动中回复用户只改变回复所需调用的归属，不将原活动整体改为用户任务；询问进展也不改变原任务归属。后台维护遵循 DL-109，单次混合模型调用见 DL-111；具体来源与交接接口仍待细化，当前尚未实现。

### 5.35 已确认的单次混合模型调用计量（R46／DL-111）

一次模型调用同时处理用户回复与自主计划时，按发起目的记一次，不拆点或重复计数。为处理用户消息或用户交办任务发起的模型调用不扣自主额度；为推进自主活动发起的调用扣 1 点，顺带主动分享不改变归属。发起登记时记录归属，不额外调用模型分类，也不因中途插入消息重新归类。后续工具调用仍按 DL-110 分别归属，后台维护遵循 DL-109。具体关联与保存接口仍待实现验证。

### 5.36 已确认的模型接入职责边界（R52／DL-117）

角色决策、对话与记忆处理通过统一业务接口调用模型，适配层集中处理服务协议、流式输出和工具调用格式差异。离线与真实模型使用同一业务入口，真实兼容性按 DL-116 另验；全局服务与角色能力绑定遵循 DL-15，不另建编排引擎。首批协议及列表功能见 DL-118，依赖、字段及具体封装方式仍待后续方案与 P0 证据确定，当前尚未实现。

### 5.37 已确认的首批模型协议及列表选择（R53／DL-118）

首批接入 OpenAI Chat Completions 兼容接口、Responses 及 Anthropic Messages，分别适配协议。模型服务配置提供“获取模型列表”后选择模型的能力；后端先实现列表获取和 CLI／API 验证，按钮与选择控件在桌面前端阶段接入，不提前开发页面。

按用户配置的服务请求相应列表，不写死模型名单。列表获取与实际流式、工具调用等能力分别验证；手动填写、列表失败处理及测试连接按钮见 DL-119／R54，具体协议版本、SDK、分页与接口待验证，当前尚未实现。

### 5.38 已确认的手动模型填写与测试连接入口（R54／DL-119）

获取列表作为辅助选择，保留手动填写模型 ID，不以列表获取成功作为保存或使用配置的前提。失败时显示实际原因，保留当前配置及模型选择，不自动清空或切换。提供用户主动点击的“测试连接”按钮，不设为保存或使用配置的强制前置步骤。

后端先提供相应接口，按钮与控件后置到桌面前端；具体测试请求、返回及记录范围已按 DL-120／R55 确认，当前尚未实现或验证。

### 5.39 已确认的测试连接请求与结果（R55／DL-120）

使用当前填写的服务配置、协议及模型 ID，发一次简短实际模型请求，返回成功或失败、耗时与实际错误原因，保留原配置。测试不带角色资料、记忆或聊天，不调用 MCP／Skill，不进入角色聊天、记忆或自主计划，不扣自主额度，独立记录为配置测试调用。

该功能由用户主动触发，不作为保存配置的前提；基本请求往返与完整 Agent、工具及流式能力分别验证，具体协议字段和接口仍待实现验证。

### 5.40 已确认的本地 API 与客户端通信（R56／DL-121）

后端 HTTP API 仅监听本机回环地址，接收消息、输入状态和配置操作并查询历史、记忆及任务；SSE 推送回复增量、执行进度和完成／中断状态。CLI 作为薄客户端通过同一 API 验证，未来桌面界面复用，核心仍可独立运行，不增加网页或远程部署方案。

断线及重连遵循 DL-83，连接断开不取消业务任务，重连读取原执行与结果。端口、路由、事件结构及补发、去重接口仍待设计验证，当前尚未实现。

### 5.41 已确认的消息提交重试去重（R57／DL-122）

每次主动发送生成唯一提交编号，同次发送因未收到回执等原因重试时沿用原编号；后端持久关联角色、窗口及原消息，重复提交返回原消息和进度，不重复保存、登记处理或打断回复。主动再次发送即使文字相同仍使用新编号；同编号不同内容返回冲突错误，不覆盖原消息。

去重关联跨重启保留，具体字段、保存顺序和唯一约束仍待设计验证。该规则仅针对消息提交，不代表其他操作或外部工具已获得跨系统恰好一次执行保证，当前尚未实现。

### 5.42 已确认的首轮后端进程组织（R58／DL-123）

首轮采用一个 TypeScript 后端进程承载 API／SSE、角色管理及调度、LangGraph、后台记忆整理与数据库访问；模块职责清晰，不按角色或记忆职责拆成独立服务。CLI 独立连接，未来桌面复用同一 API，MCP 按既有服务方式接入；原型仍只验证单角色。

后台整理与实时回复在同进程中独立调度，聊天不等待整理，角色决策串行及独立工具任务可并行规则保持。桌面生命周期遵循 DL-29，具体启动、关闭、连接、工作线程与响应性待验证，当前尚未实现。

### 5.43 已确认的后台记忆整理模型选择（R59／DL-124）

后台记忆整理默认继承角色对话模型，需要时按角色单独从全局模型服务选择。复用服务配置及调用实现，不复用当前聊天上下文；整理根据待处理记录、相关事件及自身职责独立构造输入并按既有条件触发，预算继续遵循 DL-109，不替角色更新当前状态或写日记。

不新增额外审核模型或固定三模型槽位，失败进度和重试原则见 DL-125／R60；具体字段、开关与任务链关联接口仍待验证，当前尚未实现。

### 5.44 已确认的记忆整理失败进度与重试（R60／DL-125）

失败时保留原始记录及待处理状态并记录实际错误，记忆结果、来源及索引成功保存后才标记对应范围完成，已提交部分不重复生成。后台稍后重试，不阻塞聊天或重新等待消息数量条件；配置恢复、重启后可继续调度未完成内容。

连续失败逐渐延长重试间隔，不自动换模型；具体间隔及次数实施时再定。重试读取已保存进度和最新相关记忆，遵循 DL-100，实际标记、去重及调度接口仍待验证，当前尚未实现。

### 5.45 已确认的后台整理批次调度（R61／DL-126）

同一角色同一时间只运行一个整理批次，多个触发合并登记，保留来源及范围。批次开始固定本次输入，期间新增内容按既定条件交后续批次；结束后检查排队请求及待处理范围，成功范围不重复处理，失败按 DL-125 重试。

原始窗口历史不混并，不同角色独立调度。该串行仅约束后台整理，聊天独立运行，纠错并发遵循 DL-100。容量分批原则见 DL-127，具体预算值、范围与去重接口仍待验证，当前尚未实现。

### 5.46 已确认的整理容量与超长记录处理（R62／DL-127）

按模型可用上下文容量分批，结合说明、相关事件和原始记录预留结果输出容量；超长记录分段并保留归属和顺序，原文完整保存，未实际处理部分不提前标完成。同一事件跨批补充，沿用 DL-96；触发数量及停歇时间不改变，不要求一次输入全部待处理记录。

批次与失败处理遵循 DL-126、DL-125，具体预算值、分段和处理位置由实施验证确定，不新增逐次管理批次的设置，当前尚未实现。

## 6. 扩展样例建议

首轮使用一个可重复运行的本地 MCP 样例工具，以及一个符合标准目录格式、指导角色调用该工具的最小 Skill。

- 工具返回易于核对的固定或确定性结果，以便验证实际调用，而非只根据模型回复认定调用成功。
- Skill 导入只读取和保存，不自动执行随包脚本。
- 随包脚本执行属于第一版已确认能力，首轮样例的具体脚本与运行语言需后续选择，不承诺所有外部 Skill 都能直接运行。
- 示例配置不包含真实密钥。真实模型服务验证由用户配置可用服务，结果单独记录。

### 6.1 已确认的 Skill 加载方式（R12／DL-74）

- 根据当前任务可用资源提供 Skill 名称、用途简介与读取入口，供角色选择。
- 角色需要时读取完整 `SKILL.md`，引用文档、素材和脚本随实际任务需要读取或使用。
- 读取 Skill 不自动运行脚本，实际执行由角色通过可用工具发起，沿用统一任务记录与 DL-58 的处理规则。

发现目录、读取工具、上下文保留与缓存方式仍待细化，不增加额外内容审查、依赖预检、授权或审批。

### 6.2 已确认的本地 MCP 基础工具（R13／DL-75）

- 随程序提供本地 MCP 基础工具，负责文件读写、目录检索与命令／脚本执行，供角色和通用 Skill 使用。
- Skill 保留通用目录与指令，可调用基础工具或已接入的外部 MCP，不逐个改写成独立 MCP 服务。
- 沿用既有资源开关、任务链资源延续和统一调用记录；内容、依赖及环境仍由用户负责，不增加额外审查、预检或授权。

具体工具接口、进程组织、路径处理、脚本运行方式及角色隔离待设计和 P0 验证，不提前锁定实现包，也不承诺所有第三方 Skill 直接可运行。

### 6.3 已确认的外部 MCP 连接方式（R14／DL-76）

- 本地服务：用户配置命令及参数，由 Nowadays 启动并通过 stdio 连接。
- 远程服务：用户提供服务地址等必要配置，通过 Streamable HTTP 连接。
- 两种方式共用资源开关、任务记录、结果保存和原任务链资源延续规则，不增加额外授权或审批。

第一版支持以上两种方式；首轮原型先用本地样例验证主链路，远程按 DL-115 在 P5 后首个后端补充工作包、正式桌面前端接入前完成。具体 SDK、协议版本、连接配置、凭据、重连及服务兼容性仍待设计验证。

## 8. 验收场景

| 场景 | 需要看到的结果 |
| --- | --- |
| 单角色对话 | CLI／API 输入能得到回复，原始输入和正式回复保存到角色数据库 |
| 多窗口与来源 | 在同一角色的两个测试窗口保存独立历史及来源标记；跨窗口经历可通过角色长期记忆召回，但不会混入另一个窗口的原始聊天历史；CLI／API 可分别查询历史与活动记录，无需真实 QQ 或正式页面 |
| 记忆形成与索引 | 从实际保存的对话及工具活动记录触发后台整理，生成或补充事件并建立多维索引与原始来源关联；不要求每条回复同步完成整理 |
| 中断内容的记忆语义 | 中断回复的明确表达可参与整理，截断部分不补成完整承诺；明确工具成功不因回复中断而丢失，未知仍为未知；未输出草稿和未完成计划不被记为已发生对话或已完成动作 |
| Agent 记忆回复 | 后续消息自动召回相关事件概况，Agent 按需继续查询、读取事件详情和原始证据，再依据实际结果回答；可核对检索记录和来源，不能只用固定预置事件替代 |
| 基础查询构造 | 程序结合新消息、近期话题与角色关注事项检索首批事件，不固定增加独立模型调用；同角色跨窗口可召回，仅明确查询意图才施加时间、来源或情绪约束 |
| 无命中与查询失败 | 无结果不被判为事情从未发生；需要历史依据时 Agent 可继续检索，仍无证据则保留不确定；成功无结果与查询失败分别反馈，普通闲聊不被强制追加工具回合 |
| 事件精炼与主观记忆 | 零碎事件按既有规则聚合，符合条件的低召回事件精炼为日常摘要且保留证据；事件与角色主观体验、日记关联参与召回，不重复生成同一事实事件 |
| 日常摘要来源范围 | 摘要正文仅概括，后台可定位窗口及时间／消息范围，普通召回不带原文或逐条引用；需要细节时可在范围内检索，精炼前零碎事件不重新独立返回 |
| 统一记忆检索 | 同一主题查询可返回相关事件与日常摘要并标明类型；Agent 可按类型深入读取，摘要不自动展开原文，精炼前零碎事件不重复独立返回 |
| 日记自主书写与状态 | 角色可根据对话邀请或经历决定是否写日记，保存并关联事件后可召回；不要求每次事件整理自动生成日记，也不要求每次当前状态变化必须写日记 |
| 角色记忆纠错 | 角色读取记忆和来源判断记录或陈述是否错误，按既有范围更正事件、摘要与索引，原始对话和实际活动证据保持原貌；不增加角色卡冲突处理 |
| 流式回复与完成 | 生成时收到增量文字并显示生成中，正式回复与状态保存成功后才报告完成；生成或保存中断时明确为未完成，不能只凭部分文字报告成功 |
| 中断部分回复保留 | 已输出的部分原文持久保留并标注已中断、未完成，查询历史及角色读取相关上下文可看到原文和状态；本轮及尚未提交的角色状态不被误记为成功 |
| 正在输入与调用启动 | 有待处理消息时，持续输入期间暂缓下一轮回复调用；停止输入 1 秒后退出并进入调度，输入法组词选字保持状态，仅聚焦不阻塞，未发送草稿不触发回答；不提供用户配置项 |
| 新消息中断回复 | 单纯打字不打断已有回复；实际发送新消息后中断、保存未完成部分和进度，等待输入状态退出后再处理新消息；旧执行不覆盖新结果，已发工具不被重复调用 |
| 客户端断线与重连 | 后端运行期间断开客户端，原决策及工具继续执行、保存结果；重连可查询原进度与结果，不产生重复模型调用或工具操作 |
| 输入状态失效 | 关闭对应聊天窗口、确认客户端断线或重启后清除旧输入状态，已发送待处理消息可继续调度，纯草稿及已完成消息不重新触发 |
| Skill 与 MCP | Skill 被实际读取，指定 MCP 工具发生真实调用，返回结果与回复关联 |
| Skill 按需加载 | 先向角色提供可用 Skill 简介，使用时读取完整 SKILL.md，所需引用按需读取；加载内容不会自动执行随包脚本 |
| 本地 MCP 基础工具 | 通用 Skill 通过随程序提供的本地 MCP 实际读写样例文件、检索目录并执行样例命令／脚本；结果与任务关联，无额外预检或授权步骤 |
| 资源开关 | 关闭立即阻止新任务使用，既有任务链仍能继续调用相关资源至该链结束；启用资源直接可用，没有额外授权或审批流程 |
| 任务链目标边界 | 暂停、等待及临时处理消息保留原链；完成或角色决定终止后保存结束记录，独立新目标使用新任务及当前资源开关，不继承旧链的资源延续 |
| 资源延续恢复 | 关闭资源后暂停原任务或重启应用，恢复继续原目标时沿用该链保留的资源；前台仍为关闭，新任务不可使用；原链结束后结束其延续使用 |
| 局部状态更新 | 角色提出的变化保存，未修改部分与基础角色卡保留 |
| 自主唤醒 | 唤醒安排持久保存，到时经角色决策推进一次活动 |
| 重启恢复 | 恢复角色状态，结合当前情况处理未完成事项和过期安排 |
| 预算与调度 | 自主活动预算独立统计，用户新消息能够进入下一轮决策 |
| 长任务与新消息 | 可控任务未返回期间角色仍处理新消息；任务释放后结果回到决策流程，任务不被重复执行 |
| 任务切换与进度 | 在可保存进度的位置切换，角色决定原任务去向；暂停沿用既有任务档案，后台结果返回不提前更新角色已处理内容进度；使用可控分段任务验证，不要求本轮实现视频功能 |
| 自动转后台 | 快速、延迟及等待边界返回时仍是同一任务、同一次实际调用，结果只归并一次；前台等待结束不直接变成执行失败 |
| 中断与提交顺序 | 输入保存、任务调用、结果落盘和完成通知之间发生中断时记录可追溯；回复与状态一起提交，不把任务登记或未知结果记成成功 |
| 存储文件分工 | 角色业务记录与执行检查点分文件保存且归属同一角色目录；检查点恢复不覆盖已提交业务记录 |
| 执行编号与恢复 | 新决策使用新编号，同次暂停恢复保持原编号；一个暂停活动与后来消息的进度分别保存，角色决策仍串行推进 |
| 恢复时资料更新 | 暂停期间更新角色状态、设定或关闭 MCP 后恢复，新的判断使用最新资料；既有任务链的资源延续按 R9 处理，新任务仍不可使用关闭资源，已完成操作不重复，最新业务状态不被旧快照回退 |
| 明确失败与未知结果 | 能区分明确失败和结果未知，按已确认规则继续处理 |

自动化回归使用离线模型与本地 MCP 样例，不自动调用付费模型或真实 QQ。真实服务验证与离线测试分别记录，不能互相代替。

验收脚本、命令和具体断言待实现工作包形成后补齐；当前没有可执行代码，不提供虚构的“已通过”测试结果。

### R1 角色管理层与 LangGraph 的执行边界（已确认，DL-63）

**核对时发现的空白**：原第3节将独立任务和唤醒安排归给角色运行时，第4节将模型／工具调用归给 LangGraph，但未明确长任务等待期间如何让出当前决策。若一直占用角色决策位置，会与 DL-49、DL-50 的要求不一致。

**已确认并写入正文的职责**：

- 角色管理与调度层承载角色的持续运行，维护待处理事项、任务、唤醒安排与决策顺序。
- LangGraph 在每次触发时推进一次有界的角色决策，读取上下文、调用模型、提出行动与状态变化；角色身份和长期经历继续由业务存储持有。
- 独立长任务交给任务执行部分处理，保存任务关联与后续安排后让出决策位置；结果再进入角色队列，推进后续图执行。短工具调用可在本轮完成，具体结束或暂停恢复方式按场景继续细化。
- 外围管理层保持轻薄，复用 LangGraph 现有能力，角色身份与业务经历仍在自己的数据库中持续保存。

**已补入的验收场景**：使用一个可控的等待任务，证明其未返回期间用户新消息能被角色处理；随后释放任务，证明结果回到角色决策流程，且不会重复执行该任务。当前仅确定场景，尚未执行验证。

**核对依据**：DL-09、DL-49、DL-50、DL-60，以及 [LangGraph 官方概览](https://docs.langchain.com/oss/javascript/langgraph/overview)与[持久化说明](https://docs.langchain.com/oss/javascript/langgraph/persistence)。上述职责划分已由用户确认为本项目选择，不是框架强制的唯一架构。

R1 本身未确定长短任务衔接、检查点身份映射、物理存储和运行中决策中断方式；后续 R3／DL-65、R4／DL-66 与 R6／DL-68 已确认分文件存储、执行编号和自动转后台原则，等待参数及具体图中断接口仍待确定。

### R2 记录保存、外部动作与完成通知的顺序（已确认，DL-64）

**核对时发现的空白**：原第4节未规定输入、任务登记、实际调用、结果保存和完成通知的顺序。只在流程末尾保存全部内容，无法明确处理执行中断时已收到的消息、已发出的操作和只保存一部分的本轮结果。

**已确认原则：先登记，再执行，结果保存后再报告完成。**

- 用户输入或需要持久保留的触发先写入角色数据库，再进入决策流程。
- 外部工具调用前先保存任务及稳定标识，记录准备执行的操作；实际执行与数据库提交分别处理，不能将任务登记视为已经执行成功。
- 实际工具结果先保存，再交回角色决策；回执重复到达时根据任务标识处理。
- 一轮正式回复、角色局部状态变化及该轮完成标记，在同一角色业务数据库事务中提交，提交后再对外报告本轮完成。
- 中断后核对实际任务状态，继续遵循 DL-53：结果未知先核查，不能仅凭已有任务登记或检查点就自动重做。

**纳入验收的中断场景**：输入保存后中断；任务已发出而回执未保存；结果保存后通知未发出；回复与状态提交中断；同一回执重复送达。各场景需要证明记录可追溯，且不会把未执行或未知操作记成成功。当前尚未执行验证。

**依据与边界**：[SQLite 原子提交说明](https://www.sqlite.org/atomiccommit.html)支持同一数据库事务内的原子提交；[LangGraph 容错说明](https://docs.langchain.com/oss/javascript/langgraph/fault-tolerance)说明节点重试机制。上述提交原则已确认，实际实现尚未验证；不将外部 MCP 调用、工作空间文件写入和数据库提交视为同一原子事务，也不承诺任意外部工具都能保证只执行一次。

本项尚未确定表结构、状态枚举、回执接口及检查点提交细节；消息提交去重原则见 DL-122／R57，流式完成关系见 R15／DL-77，传输方式见 DL-121／R56，具体字段、事件和保存接口仍待细化。

### R3 业务库与检查点库的物理组织（已确认，DL-65）

**核对时发现的空白**：业务数据与执行检查点的职责已区分，但原第5节尚未确定是否放在同一数据库文件中。用户已确认分文件布局，检查点驱动与实际持久化接口仍待 P0 技术小样验证。

**已确认布局**：每个角色保留一份正式业务数据库，再将 LangGraph 检查点保存到该角色目录内另一份独立 SQLite 文件。示意名称如下，实际文件名尚未确定：

```text
<角色目录>/
  role.sqlite        # 正式业务记录
  execution.sqlite   # LangGraph 执行检查点
  workspace/         # 笔记等工作文件
```

- 业务库保存正式对话、角色状态、任务实际结果与唤醒安排，是已提交业务记录的依据。
- 检查点库保存图的执行阶段、所需引用及必要中间状态，用于继续图执行；不覆盖已经提交的业务记录。
- 恢复时结合业务任务状态核对，已经完成的步骤不因旧检查点而重复执行；没有已知结果的操作仍按 DL-53 处理，不能仅凭数据库缺少成功记录认定其未发生。
- 两份库都归属于同一角色数据目录，不跨角色共享执行状态；不预设跨文件事务，具体保留、备份及恢复策略后续细化。

**依据与边界**：[LangGraph 持久化说明](https://docs.langchain.com/oss/javascript/langgraph/persistence)将检查点定位为线程图状态快照。上述独立文件布局已由用户确认，是本项目选择而非框架要求；具体 TypeScript 驱动、文件接口和跨进程恢复能力必须由 P0 实际验证。

### R4 检查点身份：按一次决策执行组织（已确认，DL-66）

**核对时发现的空白**：原方案未决定 LangGraph 的 `thread_id` 对应角色、对话窗口还是单次决策执行。直接混用这些身份，无法清楚区分暂停中的活动、正在处理的新消息和各自恢复位置。

**已确认映射**：每次有界决策拥有独立执行编号，以该执行编号对应 LangGraph 检查点线程；同时记录所属角色及相关对话窗口／自主活动。

- 新消息或自主唤醒引发新的决策时创建新的执行编号。
- 同一次决策暂停后继续或重启后恢复，沿用原执行编号；具体是否允许继续仍按业务记录和恢复规则判断。
- 对话历史、角色状态和长期记忆从角色业务数据加载，不依赖把整个角色人生累积在一个检查点线程内。
- 长任务具有自己的任务记录和发起执行关联，完成结果可以触发后续决策；新决策与原任务之间的关系保留。
- 多个执行编号不创建新的角色人格，也不取消同一角色决策串行的规则。

**依据与边界**：[LangGraph 检查点文档](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)说明检查点按 `thread_id` 保存和恢复。将其映射到本项目的决策执行已由用户确认，是本项目选择，框架不强制这一映射。恢复时读取最新资料的原则见 R5／DL-67，具体编号格式、关联字段、刷新接口及保留周期仍待细化。

### R5 暂停恢复与最新角色状态、资源开关的协调（已确认，DL-67）

**核对时发现的空白**：一项决策暂停期间，角色可以继续处理新消息，用户也可以更新角色设定或资源开关。原方案未规定恢复后的新判断与调用如何结合晚于检查点的业务变化。

**已确认原则**：执行进度沿用原检查点，新的判断与动作读取当前业务数据。

- 恢复原执行编号及已完成步骤、工具实际结果，不因刷新上下文而重做已经确认完成的操作。
- 在继续新的模型判断或发起新的工具调用前，读取最新角色设定、当前状态、相关对话／记忆以及资源开关和剩余预算。
- 已关闭的资源不再供新任务使用；本条原有“不再发起新调用”的表述按 R9／DL-71 修订，关闭时已在执行的原任务链可以继续使用相关资源至整条链结束，实际结果照实记录。
- 已提交的角色状态保持为当前状态，不能将旧检查点中的整份状态直接覆盖回业务库；具体局部更新与版本协调机制另行设计。
- 读取新设定不包含 DL-03 已排除的角色设定冲突检测、清理或自动重写历史，也不增加资源开关之外的授权或审批操作。

**已补入的验收场景**：暂停一项活动，处理新消息并更新状态，再恢复原活动；暂停期间关闭一项 MCP 或更新角色设定后恢复。需证明新的判断采用最新信息，已完成动作不重复，原始记录和已提交状态不被旧快照回退。当前尚未执行验证。

本项恢复原则已确认，具体上下文刷新接口、版本字段、旧的未提交输出处理和在途任务取消方式仍待细化。

### R6 短调用与独立长任务的自动衔接（已确认，DL-68）

**核对时发现的空白**：原方案已确定长任务应让出角色决策位置，但未确定普通工具调用转为后台任务的方式，不能仅依赖预先猜测它会耗时多久。

**已确认方式**：工具调用统一登记任务，允许短暂前台等待；在等待窗口内返回则在本轮使用结果，仍未返回则转后台执行，角色让出决策位置。已明确需要持续进行的活动可直接按独立长任务安排。

- 转后台沿用原任务编号和原来的实际调用，不取消后重新发起，也不因前台等待窗口结束而将任务记为失败。
- 结果完成后，先按 R2 保存，再交回角色的顺序决策流程。
- 同一任务在返回与等待窗口结束的交界处只归并一次完成结果，具体竞争处理需要验证。
- 这属于自动运行调度，用户不需要给每个工具额外手工分级或确认；资源可用性仍仅由开关控制。
- 本机制针对可独立执行的工具任务，不据此并发推进同一角色的多个模型决策。
- 转后台不承诺外部服务在进程退出后能继续或恢复执行；重启后的结果未知处理仍遵循 DL-53。

**已补入的验收场景**：同一工具分别快速返回、延迟返回、恰在等待窗口边界返回，以及转后台后重启。需证明实际调用未被重新发起、结果不重复归并，角色可在等待期间处理新消息。当前尚未执行验证。

自动转后台原则已确认，前台等待窗口、执行总超时、结果归并与图暂停／结束接口仍待 P0 和调度设计细化。

### R7 任务切换与既有进度存档（已确认，DL-69）

**核对时发现的空白**：持续活动在新消息到来时如何切换，以及其业务进度与工具操作、图检查点之间的分工尚未明确。

**讨论背景**：用户以观看到第3分钟的视频为例核对后台是否继续，并指出已有任务存档与恢复，不应重复增加机制。协作者撤回新增独立活动存档的建议。

**已确认原则**：在可保存进度的位置让出角色注意力，由角色决定原任务去向，复用既有任务存档与恢复。规划、活动和操作的概念区分不意味着各自新建一套存储或运行系统。

- **角色任务**承载角色规划中的持续事项，例如观看视频 A，使用既有任务档案保存目标、业务进度及暂停／继续所需信息。
- **工具调用明细**保存完成角色任务时的实际操作与结果，例如获取字幕或分析片段，关联到角色任务；R2、R6 已确认的稳定标识、先登记后执行与转后台行为继续保留。
- **图执行进度**仍由 LangGraph 的执行编号和检查点保存，按 R3、R4 与角色业务数据分工；图执行到哪个节点与视频实际处理到几分几秒分别记录。

已发出的独立操作可以继续，返回结果先保存。原任务需要角色再次思考、选择或发起下一步时，优先让新消息进入决策；角色结合消息与当前任务决定继续、暂停或结束。暂停使用已有任务档案保存进度。

播放器位置、后台获取／分析的结果和角色实际接收处理的内容进度需要区分。后台结果先保存为待处理内容，角色实际接收处理后才更新相应进度。具体可保存节点、进度结构、感知接口与在途操作结束方式仍待设计，不将“后台始终继续看完视频”写成默认行为，也不提前确定新的数据表或关联接口。

**验收场景**：使用可控分段任务，在保存进度后处理新消息；在途操作结果继续保存，原任务可由角色决定继续或暂停，恢复不重复操作，未处理的后台内容不标为已理解。本轮不以实现真实视频感知为前提，当前尚未执行验证。

### R8 工具调用状态与前后台模式（已确认，DL-70）

**核对时发现的空白**：工具调用记录的基础状态尚未定义，已确认的“明确失败”“结果未知”和自动转后台需要在存储中清楚区分。

**已确认的工具调用基础状态**：以下五种状态主要描述实际调用，不直接当作角色任务的完整生命周期；具体字段与枚举拼写后续确定：

| 状态 | 含义 |
| --- | --- |
| 待执行 | 已登记，尚未进入本地调用流程 |
| 执行中 | 已进入调用流程，正在执行或等待实际结果；不单独证明远端已开始处理 |
| 成功 | 已取得并保存明确的成功结果 |
| 明确失败 | 已取得明确的失败结果，由角色在预算内决定后续处理 |
| 结果未知 | 不能确认实际结果，先核查，不自动当作未执行或失败后重做 |

- 前台／后台单独作为运行模式记录，转后台时任务可以继续处于执行中，不为切换模式重发调用。
- 图决策暂停与工具任务执行状态分别理解；图暂停期间工具仍可能执行并返回结果。
- 结果未知后可根据实际核查补充状态；具体状态转移、重试记录与回执竞争处理仍待设计。
- 本表为 Nowadays 内部任务记录语义，不要求第三方 MCP 服务采用项目私有状态协议。

**验收场景**：转后台保持同一任务执行状态与标识；连接中断不自动记为明确失败；核实未知结果后保存实际结论；图暂停不造成正在执行的工具任务被误记为已取消。当前尚未执行验证。

本项不决定取消、超时与重试尝试的完整状态机，后续按必要场景补充，不提前增加额外用户操作。

### R9 资源关闭时的既有任务链延续（已确认，DL-71）

**核对时发现的空白**：DL-59 已确认资源仅通过开关控制，但关闭开关时既有任务如何完成尚未确定。用户修订 R5 的笼统关闭语义，要求支持整条任务链继续使用资源至结束。

**已确认方式**：前台立即显示关闭，对新任务立即按关闭处理；关闭时已经在执行的原任务链仍可使用相关资源，包括完成该链所需的后续调用，直至整条链结束。延续使用只属于原任务链，不适用于新任务或无关活动。

**验收场景**：一条可控任务链使用某资源，运行期间关闭该资源；开关立即为关闭，新任务不能使用该资源，原任务链仍能发起完成该链所需的后续调用，结果照实保存，整条链结束后不再保留延续使用。当前尚未执行验证。

原先“只等待已发出的单次调用结束、阻止其后续调用”的候选建议未采纳。任务链目标边界与结束判定见 R10／DL-72，暂停与重启后的资源延续见 R11／DL-73；具体字段及资源连接释放方式仍待细化。本项不决定显式取消或用户接管桌面时的处理，不增加额外授权或确认步骤。

### R10 任务链的目标边界与结束判定（已确认，DL-72）

2026-11-03，用户确认任务链按具体目标组织及结束的规则。

**已确认规则**：任务链围绕创建时记录的一项具体目标组织，角色根据实际执行结果判断目标完成，或者决定放弃／无法继续并结束，随后保存结束记录。暂停、等待结果及临时处理消息保留原任务归属，不直接算结束；一轮图执行完成或单次工具返回也不直接代表任务链完成。

例如原目标为“看完视频 A 并写一份笔记”，观看、整理和写笔记属于同一任务链；完成后再看另一条视频属于新任务。长期兴趣通过一次次具体任务推进，新出现的独立目标另建任务，不将其追加到旧链以延续已关闭资源的使用。

任务链结束后，按 R9 结束该链对已关闭资源的延续使用；暂停和重启后的资源延续见 R11／DL-73。具体持久化字段与结束时仍有在途操作的处理仍待设计；本项不新增目标语义审核、用户审批或一套活动存储。

**验收场景**：一条具有具体目标的任务链暂停、等待工具并临时处理消息后仍保持原链；完成或角色决定终止时保存结束记录。随后出现独立目标时创建新任务，按当前资源开关执行，不沿用旧链对已关闭资源的延续使用。当前尚未执行验证。

### R11 暂停与重启后的任务链资源延续（已确认，DL-73）

**已确认规则**：将原任务链对相关资源的延续关系与任务进度一起持久保存。临时暂停或应用退出不直接结束该链；恢复后重新评估并决定继续原目标时，仍作为原链，可以继续使用该链原先保留的相关资源。前台开关保持关闭，新任务仍不可使用这些资源；链结束时结束其延续使用。

本项延续既有任务档案，不新增授权操作或独立活动系统，也不表示进程退出期间外部调用必然继续执行。恢复时仍遵守最新角色资料、预算和结果未知先核查的已确认规则；资源连接与持久化字段另行设计。

**验收场景**：原任务运行期间关闭资源，分别在临时暂停与应用重启后恢复；确认原链的资源延续关系仍在，角色决定继续原目标后可以使用相关资源，前台开关保持关闭，新任务不可使用，链结束后不再延续。当前尚未执行验证。

### R12 Skill 的按需加载方式（已确认，DL-74）

**已确认规则**：根据任务可用的 Skill 先提供名称、用途简介及读取入口；角色判断需要某个 Skill 时再读取其完整 `SKILL.md`，其引用文档、素材和脚本按实际任务需要读取或使用。加载 Skill 内容不自动运行脚本，实际脚本执行继续按 DL-58 处理。

**验收场景**：使用包含引用文档及脚本的本地 Skill，验证角色先看到简介，在选用后读取完整指令，再读取所需引用；单纯加载内容不执行脚本，角色实际发起执行时另有可核对的工具调用及结果。当前尚未执行验证。

### R13 随程序提供本地 MCP 基础工具（已确认，DL-75）

**已确认规则**：由 Nowadays 随程序提供一套本地 MCP 基础工具，支持文件读写、目录检索与命令／脚本执行，供通用 Skill 使用。Skill 保留通用目录和指令，通过这些工具或已接入的外部 MCP 完成操作，无需逐个改写成 MCP 服务。

基础工具按既有资源开关、角色任务归属和统一调用记录接入。内容、依赖与环境仍由用户负责，不增加审查、预检或额外授权。默认工作目录使用角色工作空间、Skill 引用路径按其所在目录解析作为后续实现建议，具体接口与路径处理尚待细化。

### R14 外部 MCP 的连接方式（已确认，DL-76）

**已确认规则**：第一版支持本地命令启动的 stdio 服务和通过地址连接的远程 Streamable HTTP 服务。用户提供启动命令、参数或服务地址等必要连接配置，使用仍由已有开关控制，不增加额外授权或审批操作。

**参考依据**：[MCP 架构说明的传输层](https://modelcontextprotocol.io/docs/learn/architecture#transport-layer)介绍 stdio 与 Streamable HTTP。具体协议版本、SDK、连接配置字段、远程凭据及重连方式待后续设计与验证，本段不决定支持所有可选 MCP 能力或旧式传输。

**验收范围**：首轮通过本地样例验证命令启动、发现工具、调用和结果保存；远程连接在对应后续工作包中使用可控 HTTP 服务验证配置连接、工具调用及相同的任务与开关语义。当前尚未执行验证。

### R15 对话的流式输出与正式提交（已确认，DL-77）

**已确认规则**：后端从首轮原型开始支持面向用户回复文本的流式输出，CLI／API 可以在生成过程中收到增量内容。生成中的内容标为生成中、尚未完成；按 R2 保存正式回复、状态变化与本轮完成标记后，才报告已完成。中途出错或中断时明确标为已中断、尚未完成，并保留当前进度说明，不将已显示的部分内容视为完整成功回复。

本项只决定输出与完成状态的关系，不提前设计桌面页面；中断部分文字保留见 R16／DL-78，具体传输方式、事件字段、持久化结构与重连补发另行细化。工具调用与实际结果仍按既有规则记录，不将模型文本已输出等同于工具操作已成功。

**验收场景**：通过可控模型增量输出文字，验证正式提交前仅报告生成中，提交成功后报告已完成；分别在生成中和正式保存时注入中断，确认没有虚假的完成通知。当前尚未执行验证。

### R16 中断后的部分回复保留（已确认，DL-78）

**已确认规则**：已经向客户端输出的部分回复持久保留在对话记录中，并明确标注中断、未完成。后续查询历史或角色加载相关上下文时，仍能看到这部分文字及其未完成状态，知道此前已经输出过哪些内容。

保存部分文字不把本轮标记为完成，也不将尚未成功提交的角色状态当作正式更新。具体记录结构、增量保存与发送顺序、客户端接收状态及继续生成的方式仍待细化；本项不预先决定自动重试、续写或覆盖原内容。

**验收场景**：模型输出可核对的半段文字后中断；查询历史及角色读取相关上下文时仍能取得部分原文和未完成状态，本轮不会标记为完成，未提交的角色状态不被误认为已经更新。当前尚未执行验证。

### R17 连续用户消息的下一轮处理（已确认，DL-79；启动规则见 DL-80～DL-82）

**已确认部分**：下一轮决策开始时，同一对话窗口已经收到但尚未处理的用户消息一起交给角色判断；每条消息仍独立保存，保留原文、顺序及来源，由角色决定共同回应还是分别回应，不要求每条消息各自触发一整轮模型执行。

不同窗口仍保持独立上下文，不将其消息合成同一窗口对话；同一角色决策串行与新消息优先的规则不变。用户补充：必须明确下一轮何时开始，过久会让发送方等待并损害对话体验。

批次边界、数量与上下文容量仍需设计。启动条件按 R18／DL-80 结合正在输入状态，停止输入 1 秒后退出的固定默认规则见 R19／DL-81，当前回复中断见 R18／DL-82；具体执行接口仍需验证，不承诺固定响应时限。

### R18 新消息触发与当前决策切换（已确认，DL-80、DL-82）

**用户确认的启动条件**：在 Nowadays 内加入正在输入状态；已发送消息先保存，用户仍继续打字时等待，离开正在输入状态后再发起该窗口的下一轮回复调用，结合已积累的同窗口未处理消息。当前只在系统内生效，不扩展到 QQ 等外部平台。

此前“新消息保存后直接请求启动，不考虑输入状态”的候选按本次要求修订，不能绕过正在输入条件立即开始回复调用。状态进入与固定 1 秒退出见 R19／DL-81，客户端离开后的状态清理见 R21／DL-84；具体状态交接、断线检测及接口仍待设计。

**已确认的中断规则**：当前对话中，用户实际发送新消息才触发当前未完成思考或回复中断；单纯进入正在输入状态或继续打字不打断已有回复。中断后保存进度和已输出部分，部分回复标为未完成；下一次回复调用仍需等待输入状态退出，再结合已发送的新消息开始，同一角色两轮有效决策不同时推进。

具体图中断、模型调用取消、保存顺序、旧输出隔离与切换接口需 P0 验证，不能让旧执行晚到的输出覆盖新回复或业务状态；不声称取消本地等待必然停止远端模型计算。

已发出的实际工具操作与本次模型决策分开处理，继续按既有规则保存结果，不因切换而取消后重发。已同步修订 DL-69 的切换边界，原任务链后续仍由角色判断。输入状态退出时间不等于固定首字时间，模型响应耗时与切换时延需实际测量。

**验收场景**：已有回复期间，仅输入草稿不触发中断；实际发送新消息后保存中断内容和进度，持续输入期间不发起下一轮回复，停止输入 1 秒后再进入调度。注入旧执行晚到输出及工具晚到结果，验证前者不覆盖新结果、后者照实保存且工具不重发。当前尚未执行验证。

### R19 正在输入状态的退出判定（已确认，DL-81）

**已确认规则**：实际输入或编辑时进入正在输入状态，持续编辑就刷新状态；停止输入 1 秒后退出，输入法仍在组词或选字时保持正在输入。仅输入框保持焦点不持续占用该状态。

用户明确要求 1 秒作为当前固定默认值，不提供用户配置项；后续需要变更时再讨论修改。此前“可调整初始值”的候选未被采用。

退出状态后，只有存在已发送而尚未处理的消息才请求下一轮回复调用；单纯编辑未发送草稿不触发角色回答，也不把草稿作为已发送消息交给模型。客户端离开后的状态清理见 R21／DL-84；发送与继续编辑之间的状态交接、断线检测及具体接口需后续设计验证，尚未开始实现。

**验收场景**：通过可控时间源验证持续输入刷新计时，停止输入 1 秒后退出；输入法组词选字期间不退出，仅聚焦不阻塞；有已发送待处理消息才进入回复调度，纯草稿不触发模型。检查用户配置与接口不新增输入退出时长配置项。当前尚未执行验证。

### R20 客户端断线后的原执行延续（已确认，DL-83）

**已确认规则**：CLI／桌面客户端的连接断开时，只要后端仍在运行，已有决策与工具任务继续执行并保存结果。客户端重新连接后按原执行关联查询进度及结果，不因重连自动创建新决策、重新调用模型或重发工具。

本项只讨论客户端连接中断；应用进程退出仍遵守已确认的保存、停止与重启重评估规则。重连补发、事件编号与客户端显示去重的具体接口仍待细化，当前不表示已经实现连接恢复。

**验收场景**：在模型增量输出和工具等待期间分别断开客户端，保持后端运行；验证原执行继续且结果保存，重连查询原执行不会增加模型或工具调用次数。应用退出与重启另按既有恢复用例验证。当前尚未执行验证。

### R21 输入状态在客户端离开后的失效（已确认，DL-84）

**已确认规则**：正在输入作为临时运行状态；关闭对应聊天窗口、确认对应客户端连接断开或后端重启时，清除对应输入状态，不从旧状态恢复为仍在打字。已经保存的待处理消息继续按调度规则处理，未发送草稿不因此提交模型。

不将过期输入状态永久保留而阻塞回复，也不因清理状态重发已完成消息。具体窗口与连接归属、断线检测及状态交接接口需后续设计验证，不增加用户配置项或正式页面实施工作。

**验收场景**：保持正在输入状态时，分别模拟关闭窗口、确认连接断开与后端重启；验证旧状态被清除，已保存的待处理消息能够继续调度，未发送草稿和已完成消息不触发新调用。当前尚未执行验证。

### R22 P0 技术小样的首要验证目标（已确认，DL-85）

**已确认目标**：P0 使用可控离线模型、本地 MCP 样例、实际 LangGraph 与两份 SQLite 存储，验证一条最小的“思考 → 工具调用 → 保存结果 → 中断／暂停 → 恢复”链路；将图执行中断、检查点恢复及工具结果不重复执行作为首要可行性目标。

同时用可控流式输出验证新消息切换后旧输出不覆盖新结果，恢复原执行时使用最新角色资料，并保留已完成的实际工具结果。小样记录具体版本、接口、成功与失败证据，供后续 P1～P4 的业务实现使用。

本项仍为方案核对，不自动启动编码、安装依赖或调用真实服务。小样不建设正式页面、完整记忆整理或全部角色管理接口；离线结果不替代真实模型与服务验收。第7节其他工作包的精确拆分仍待后续核对。

### R23 P1 角色创建、存储与资源配置的范围（已确认，DL-86）

**已确认范围**：P1 在 P0 验证结果基础上，完成单角色的创建与持久化基础：建立角色目录、独立数据库及工作空间，保存和读取角色设定、当前状态、对话原始记录，以及模型、MCP、Skill 的必要资源配置、角色绑定与开关。

通过同一组应用用例供 CLI／API 使用，以“创建 → 写入 → 读取 → 停止后重新启动读取”验证数据连续；按既有规则更新角色设定，不增加设定冲突处理、内容审查或额外授权。具体资源配置存储位置与字段仍待细化，本项不预先决定共享 MCP 实例或所有资源统一分库。

P1 以数据基础与配置可保存、可查询为完成边界，模型对话及 Skill／MCP 调用链在 P2 接入。第一轮仍只验收单角色，不实施正式前端、旧数据迁移或完整记忆整理。当前仍为方案核对，未启动实现。

**验收场景**：通过 CLI／API 创建一个角色，写入并查询资料、消息和资源配置，停止后重新启动仍可读取；修改角色设定保持角色身份及已保存记录，不触发额外设定冲突处理。当前尚未执行验证。

### R24 P2 完整记忆、Agent 回复与 Skill／MCP 闭环（范围已确认，DL-87；内部实施细节待核对）

**已确认范围**：在 P1 的角色与配置基础上，通过 CLI／API 提交消息，结合角色设定、当前状态、近期对话和自动召回的事件记忆，进入 LangGraph Agent。Agent 可以按需继续查询记忆、读取事件详情与关联原始记录，使用标准 Skill 和可用 MCP 工具，结合实际检索及工具结果继续判断，再生成流式回复。

后台按已确认的触发与职责分工，从实际对话和活动记录整理事件、维护多维索引及原始来源关联，控制粒度并精炼低召回日常事件。角色主观体验、当前状态、日记关联及自主记忆纠错按既有决定接入相关数据和调用，保留原始证据。

正式回复、角色局部状态变化与本轮完成标记按已确认事务顺序保存；输入原文、检索及工具调用与结果可核对。完成边界为“实际记录 → 后台事件形成与索引 → 后续消息自动召回 → Agent 按需深入记忆及使用 Skill／MCP → 基于结果回复 → 保存”，不能只凭模型声称记得或已经调用工具判定完成。

输入状态启动条件、固定 1 秒退出、新消息中断、未完成部分保留与客户端重连延续作为本阶段的对话行为接入；具体异常覆盖在 P4 汇总验证。优先使用可控离线模型和本地样例，真实模型服务由用户配置后单独验收，协议和适配器仍待细化。

本阶段已纳入完整记忆与 Agent 回复，不自动扩展到自主浏览、视频或桌面控制；远程 MCP 工作包见 DL-115／R50，不因本地闭环通过而宣称远程服务已验证。内部工作包、字段、具体检索参数和图接口仍待细化，已确认整理阈值按相关 DL 执行，当前不启动实现。

**范围修订**：用户明确要求完整加入此前讨论的 Agent 式记忆调用及回复功能；此前仅基础上下文、仅读取预置事件或将完整记忆整理后置的候选未采用。已修订 DL-60、方案正文及 P2 工作包，P0、P1 的既有范围保持其阶段分工。

**验收场景**：用实际保存的对话与可核对工具结果形成事件和索引；在后续提问中验证自动召回及 Agent 进一步读取证据后回答，包含粒度筛选、日常精炼、相关主观记忆和限定范围的自主纠错用例。测试事件可作为离线回归数据，但不能替代实际记忆形成链路，也不要求用户手工整理记忆。当前尚未执行验证。

### R25 P2 内部实施顺序（已确认，DL-88）

**已确认顺序**：在 DL-87 完整范围内，按依赖拆成三个内部步骤，全部完成并通过联动验收后才算 P2 完成。

1. **记忆形成与保存**：从实际原始记录接通后台事件整理、来源关联和索引写入，落实零碎内容聚合与日常摘要的数据基础。
2. **记忆查询与维护**：完成多维条件与全文检索、事件详情及原始证据读取、召回统计与日常精炼，接入主观记忆／日记关联及限定范围的记忆更正。
3. **Agent 对话联动**：将自动基础召回和按需记忆工具接入 LangGraph 思考／工具循环，与角色状态、Skill／MCP、流式回复、输入等待、中断和结果保存共同验证完整业务链。

各步骤分别保留可核对的数据与调用证据，再完成从实际记录形成事件到后续 Agent 检索回复的整体验收。测试样例用于验证对应步骤，不代替完整业务链；具体内部编号、字段、接口与参数尚未确定。

这是开发依赖顺序，不把运行时改成“每条消息先同步整理事件再回复”；后台整理与实时对话仍遵守 DL-20 的独立运行原则。内部具体字段、接口与参数继续核对，当前未启动实现。

### R26 中断与不同完成状态的记忆来源（已确认，DL-89；对应核对 O01）

**已确认原则**：后台整理模型读取实际保存的原文、记录完成状态和有关联的工具实际结果，根据已经发生和已经明确表达的范围组织事件。中断记录可以进入整理范围，不因整条回复未完成就丢弃其中已明确表达的内容，也不补写截断部分的含义。

- 已经输出的完整表达可以按其实际含义参与整理；未说完整的部分保留中断、未完成的性质，不由整理模型补成完整承诺或已完成动作。
- 工具操作是否发生及完成到哪里，依据已保存的实际结果；即使回复被中断，明确成功的工具结果仍可以成为对应事件来源，结果未知则保持未知，不能仅凭角色措辞判定成功。
- 未输出的回复草稿不当作已经发生的对话，计划与意图不当作已完成动作；既有任务和意图的持续保存不受影响。

进入整理范围不等于每个中断都必须新建事件，仍沿用已有事件粒度、聚合与后台触发规则。语义由整理模型判断，程序继续按 DL-22 处理来源、格式及保存，不新增独立审核模型、额外语义审查或用户确认。

具体字段、记录关联及验收样例继续细化，当前不启动实现。验收需覆盖完整表达后截断、工具已成功但回复中断、工具结果未知及只有未输出草稿的情况；当前尚未执行验证。

### R27 基础自动召回的查询构造（已确认，DL-90；对应核对 O02）

**已确认方式**：第一批自动召回由程序根据当前窗口的已发送新消息、近期话题和角色当前关注事项，提取明确的人物、主题、时间等索引线索，执行多维条件与全文检索，得到相关事件概况。该基础步骤不固定增加一次独立模型调用。

角色归属作为检索范围；同一角色的其他窗口记忆仍可被召回，不默认按当前窗口限制长期记忆。时间、来源或情绪等仅在查询意图明确时作为约束，其余作为匹配线索，不能因为角色当前心情或消息中的偶然词语就排除相关经历。

Agent 结合基础结果和完整对话语义，自行决定是否进一步改写查询、查找更多事件或读取原始证据，继续沿用 DL-17 的两阶段召回。具体查询结构、中文分词、相对时间解析、去重排序、返回长度及无命中处理仍待逐项细化，本项不直接采纳参考底稿的固定条数或预算。

具体查询结构与实现接口继续细化。验收需包含明确时间和主题查询、对话指代线索、同角色跨窗口经历，以及当前情绪与历史事件情绪不同但仍应相关的情况；当前尚未执行验证。

### R28 基础检索无命中或证据不足时的处理（已确认，DL-91；对应核对 O02）

**已确认原则**：未命中仅表示当前查询没有找到相关结果，不自动判定事情从未发生。Agent 结合当前话题判断是否需要历史依据；普通闲聊可直接回应，涉及过去约定、具体原话或事实核对时，可按需改写查询、调整非明确限制条件、查阅日常摘要及原始对话，再决定回应。

继续检索仍无足够证据时，保留不确定性，由角色结合自身性格和情境决定如何表达或询问，不编造回忆、不因检索无结果直接判定用户记错，不强制固定话术。实际检索失败与成功但无结果应分别反馈给 Agent；查询始终遵守角色数据范围，不因扩大搜索而跨角色访问。

本项不强制每次无命中都增加模型／工具回合，也不预先设定固定检索轮数、返回条数或预算；这些参数和错误接口后续细化。验收覆盖普通闲聊、需要原话证据但首次未命中、继续查询仍缺证据、查询失败等情况；当前未启动实现或验证。

### R29 日常摘要参与检索（已确认，DL-92、DL-93；对应核对 O02）

用户比较摘要来源方式后明确采用第三种，已按 DL-92 修订 DL-19：正文只做话语段总结，后台保留窗口及时间／消息范围，普通召回不附带原文或逐条引用清单，需要时再按范围检索。随后按 DL-93 确认统一检索入口。

**已确认的入口方式**：日常摘要与事件通过同一记忆检索入口查询，依据时间、主题、关键词和内容匹配，返回时标明事件或日常摘要。日常摘要按 DL-92 返回概括内容，来源范围保留在后台；Agent 需要具体细节时再查询范围及原始记录，不要求先恢复已精炼的独立事件。

精炼前的零碎事件继续按 DL-19 退出独立索引，不作为独立结果重复返回。事件／日常摘要仅为记录类型，不新增固定记忆重要等级；具体摘要字段、索引、去重和返回预算仍待细化，当前不启动实现。

**来源粒度的比较（第三种已按 DL-92 确认）**：

| 方式 | 收益 | 代价 |
| --- | --- | --- |
| 仅保存摘要，不保存来源关联 | 结构简单，日常片段被概括为模糊印象 | 原始聊天仍可单独搜索，但需要重新定位；摘要失真时更正成本更高 |
| 摘要与每条来源细粒度关联 | 容易直接定位具体原话及修订依据 | 关联维护较细，若把每个琐碎内容都映射回来，可能削弱日常精炼的简化作用 |
| 摘要正文只概括，后台保留话语段范围 | 正文简短，可按窗口及时间／消息区间缩小追溯范围，不维持逐句映射 | 精确查证仍需在该范围内检索，不能直接认定摘要中的每句话都有一对一原句 |

已确认采用第三种：摘要不复制原句，不按琐碎事项建立逐句证据清单；后台保留原对话窗口和时间／消息范围，普通召回提供摘要，需要具体细节时再检索原始记录。统一入口已按 DL-93 确认，具体范围字段、检索去重与预算继续细化。验收需验证同一主题查询可命中两类相关记录，摘要结果不携带原文或逐条清单，后台范围可用于深入查询，精炼前零碎事件不独立返回；当前尚未实现或验证。

这项建议基于本项目的日常精炼、原始历史保留与自主纠错目标；保留后台关联不等于必须把原文或关联清单放入每次模型上下文。原始经历与高层概括分别保存的架构思路可参考 [Generative Agents](https://arxiv.org/abs/2304.03442)，但该论文不构成本项目这三种方式的对比实验结果，具体效果仍需后续样例验证。

### R30 后台记忆整理触发（已确认，DL-94、DL-95，对应核对 O03）

**已确认的对话数值**：用户将消息积累触发改为 50 条，将交流停歇触发改为“至少 30 条待整理消息且停歇 60 秒”。任一对话条件满足即可安排整理，无新增记录不重复触发。

消息按保存的消息记录计数，用户消息与角色回复分别计条，流式分片不重复计条；各窗口保持自身记录顺序和归属，后台整理不混并各窗口的近期对话。具体活动记录归集、记录状态变更和触发去重接口后续细化。

该后台停歇时间不改变 DL-81 的 1 秒输入状态退出值，也不让实时回复等待后台整理。触发仅表示检查待整理内容，不强制新建事件或按 50 条切分事件。单批容量、记录状态变化与触发去重的接口继续细化，当前不启动实现。

**已确认的活动边界**：这里的活动指角色围绕具体目标开展的一项任务，例如读完一份网页资料并整理笔记、整理完一批本地文件，沿用既有任务档案，不新建活动系统。在这项任务结束并有实际新记录时，安排整理该任务的经历，不要求先凑够聊天消息阈值。

这不指每次模型思考、一次普通回复或单个工具调用返回；临时暂停原任务去回复消息，也不直接代表原任务已经结束。任务结束遵循 DL-72，整理后的语义处理遵循 DL-22；触发不强制形成独立事件。具体接口仍待细化，当前尚未实现或运行验证。

### R31 跨批次事件归并边界（已确认，DL-96，对应核对 O03）

用户确认按同一件具体事情的连续发展归并事件，而不按整理批次、固定消息数或临时换话题切分。后续记录继续同一经历时，补充原事件；独立的新经历可形成另一个事件，零碎日常仍按既有粒度规则处理。是否属于同一经历由整理模型结合新增记录和相关事件判断，具体查找及保存接口后续细化。

例如今天讨论一次出行、明天补充其安排，可以继续补充同一事件；同一批记录中另一次无关经历可单独处理。验收需覆盖跨批补充、同批不同经历和零碎日常筛选，当前尚未实现或验证。

### R32 低召回精炼的召回统计口径（已确认，DL-97，对应核对 O03）

用户确认事件经自动召回实际提供给角色，或经角色主动检索读取时，计为召回；同一轮角色决策内，同一事件反复返回或读取只计一次。仅在数据库中匹配、未提供给角色的候选，以及后台整理或索引维护的内部检索，不计入角色召回次数。

不要求角色在最终回复中引用或复述事件，也不增加模型判断是否真正使用记忆的额外调用。这是可记录的召回口径，不宣称能测量模型内在使用程度。观察轮次及精炼候选阈值已按 DL-98／R33 确认；具体保存接口仍待细化，当前尚未实现或验证。

### R33 低召回事件的精炼候选阈值（已确认，DL-98，对应核对 O03）

已确认的初始值：事件创建或最近一次补充新内容之后，至少经过角色的 100 轮已完成对话，且最近 100 轮内按 DL-97 计的召回次数不超过 1 次时，进入后台精炼候选。事件新建或有新内容补充后重新满足观察期，避免刚形成或仍在补充的事件立即进入候选。

用户确认一轮指角色完成一次针对已发送消息的回复决策，同次决策处理多条消息或调用多次工具仍计一轮；同一角色各对话窗口合计，自主后台整理和纯工具调用不额外计为对话轮次。此口径与 DL-94 的消息条数不同。

达到候选阈值不直接撤去独立事件索引，由后台整理模型结合内容判断是否按既有规则精炼为日常摘要，原始记录仍保留。100 轮和不超过 1 次为已确认的初始参数，后续根据实际效果讨论调整，当前尚无运行验证；本项不引入固定重要等级。

### R34 日常摘要的聚合范围（已确认，DL-99，对应核对 O03）

用户确认按同一角色、原始经历发生的自然日归集需要精炼的日常内容；同一天内容多或话题差别明显时，可分为数条简短摘要，不强行塞入一篇长摘要。日期归属按原始记录时间判断，不使用执行精炼当天的日期代替经历日期，具体时区和字段实现后续细化。

后续还有同一天的日常内容被精炼时，可补充相关摘要；跨窗口经历可以在同角色范围内归集，但后台仍分别保留各窗口及时间／消息范围，来源归属不丢失，不混并原始对话窗口。不同角色不合并。摘要正文及按需追溯遵循 DL-92。

仅在有待精炼内容时处理，不要求每天固定生成，也不替代角色自主书写的日记。摘要长度和具体更新接口仍待细化，当前尚未实现或验证。

### R35 后台整理与角色纠错的并发修改（已确认，DL-100，对应核对 O04）

用户确认后台整理和角色纠错都以读到的记忆版本为修改依据；保存时若目标记录或作为依据的相关记忆已经更新，旧结果不直接提交覆盖最新内容。受影响的整理内容保留待处理，稍后重新读取最新记忆及原始依据再处理，不阻塞实时回复，不把尚未保存的处理结果标成已完成。

例如后台正在依据旧事件整理摘要，角色先依据原始记录更正了该事件，随后返回的后台旧摘要不能把错误内容重新写回。相关记忆正文、来源关联与检索索引作为同一组修改一起保存，避免正文与索引分别对应不同版本；具体版本字段、提交单元和重新处理机制后续设计验证。

本规则处理存储更新冲突，不判断角色卡设定冲突，不增加用户审批或内容审核，也不让后台记忆模型改写角色当前状态。当前状态和日记等其他记录的具体更新接口仍待细化，当前尚未实现或验证。

### R36 新消息中断后的旧回复与任务恢复（已确认，DL-101，对应核对 O05）

用户确认因同窗口新消息而中断的旧回复执行，不自动恢复其检查点继续输出旧答案；保留已输出部分及中断标记，待输入状态退出后，由新的决策结合未处理消息、已输出内容、最新角色资料及实际结果重新判断怎样回应。角色可以继续原话题，也可以调整回答，不要求机械续写原句。旧执行晚到的文本和未提交状态不写入新回复或当前状态。

旧回复执行与其关联的业务任务链、工具调用分别记录：中断旧回复不等于结束原任务链。已发出的工具仍按原调用编号保存真实结果，不重发；新决策可读取这些结果，由角色决定原任务继续、暂停或结束，原任务链按既有规则延续。具体标识、结果交接和上下文刷新接口待 P0 验证。

本规则仅明确被新消息替代的旧回复，不改变客户端断线时后端继续原执行的 DL-83，也不取消未被新消息替代的任务按 DL-66、DL-67 暂停和重启恢复的能力。当前尚未实现或验证。

### R37 原任务执行期间修改资源配置（已确认，DL-102，对应核对 O06）

用户确认修改同一资源条目的模型服务配置、MCP 连接配置或 Skill 内容时，已发出的调用沿用发起时的配置完成，不为应用新配置而取消重发；原任务下一次尚未发起的调用或按需读取使用最新配置和内容，不将整条任务链锁定在创建时的旧配置。

资源关闭时，原任务链按 DL-71、DL-73 保留的是该资源的延续使用关系；该链后续使用同一资源时仍按上述规则读取最新配置。已完成结果不重做，实际连接或执行失败按 DL-53 如实处理，不保证外部环境修改后旧服务仍可用，不自动替用户恢复旧配置。

本项仅讨论同一资源条目的配置或内容修改，删除资源及改绑其他资源另行核对，任务结束时在途调用见 DL-103／R38。进程与连接如何在新旧调用间交接、Skill 实际读取时机等接口需验证，不增加用户授权、审批或内容预检。当前尚未实现。

### R38 任务链结束时的在途调用（已确认，DL-103，对应核对 O06）

用户确认角色按 DL-72 判断原任务链完成或终止后，结束该链的后续调用及对已关闭资源的延续使用；已发出的工具调用不因链结束而强制取消或重发，继续接收并按原任务、原调用保存实际结果。晚到结果不自动重启已结束任务，仍可供后续角色决策读取。

接收在途调用的结果不允许原链继续派生新调用，也不将未返回结果擅自标为成功。连接等资源在相关在途调用结束且无其他任务使用后再释放，具体释放范围取决于资源实现，不直接终止其他任务共用的连接或进程。

本规则沿用 DL-53 的结果未知规则，不保证所有外部调用都能成功返回；应用退出仍按 DL-29、DL-30 处理，不承诺退出后后台外部操作必定存活。超时、失联、晚到结果的持久关联和释放接口仍待验证，当前尚未实现。

### R39 自主活动统一额度（已确认，DL-104，对应核对 O08）

用户要求采用一项统一自主活动额度，模型与工具共用，不分别设置额度。此前两项独立额度的候选不采用，以便用户管理和使用。额度用尽时保存进度并等待后续预算或安排，沿用 DL-52；用户主动聊天继续单独统计。

本项确认一项额度的形式；具体扣减后续已在 DL-105／R40 确认为每次实际模型或工具调用扣 1 点，不采用此前两项独立额度候选。

预算周期及恢复方式已按 DL-106／R41 确认，默认额度与无限制模式见 DL-107／R42，耗尽处理见 DL-108／R43，后台记忆维护归属见 DL-109／R44，任务及混合调用归属见 DL-110、DL-111／R45、R46；具体接口仍待细化，不增加新的用户审批或逐次调用确认。当前尚未实现或验证。

### R40 统一额度的扣减方式（已确认，DL-105，对应核对 O08）

用户确认第一版使用统一点数，每实际发起一次自主模型调用扣 1 点，每实际发起一次自主工具调用也扣 1 点，共用同一个余额；不要求用户分别管理模型和工具权重。例如两次模型调用及两次工具调用共扣 4 点。

同一调用转后台、接收流式分片或重连读取已有结果不重复扣点，实际发起的新重试另扣 1 点；此点数控制调用量，不表示精确费用。周期及恢复见 DL-106／R41，默认额度及无限制见 DL-107／R42，耗尽处理见 DL-108／R43，后台记忆维护归属见 DL-109／R44；具体接口仍待实现验证。

### R41 自主活动额度的恢复周期（已确认，DL-106，对应核对 O08）

额度恢复后，等待预算的未完成活动按既有规则结合当前情况重新评估，不虚构离线经历或直接重放全部旧操作。用户仍只管理一项总额度，默认值及无限制见 DL-107／R42；日期时区、周期切换与余额持久化接口仍待验证，当前尚未实现。

### R42 自主活动默认额度与无限制模式（已确认，DL-107，对应核对 O08）

用户确认每个角色默认每天 200 点，并要求可以修改总额度或设为“无限制”。有限额度按 DL-105 共用余额、每次实际调用扣 1 点，每日恢复沿用 DL-106；无限制不因点数用尽暂停，仍保留实际调用记录及去重统计。用户主动聊天仍单独统计。

### R43 有限额度耗尽时的在途调用与暂停（已确认，DL-108，对应核对 O08）

用户确认首轮以一个 TypeScript 后端进程承载本地 HTTP API／SSE、角色管理与调度、LangGraph 执行、后台记忆整理及业务存储访问；各职责保持模块分离、依赖显式，不按角色或记忆职责分别部署独立服务。首轮仍只验证单角色，不因进程布局扩充原型范围。

同进程不等于同一条同步执行链：后台记忆整理与角色回复独立调度，实时回复不逐轮等待整理，角色决策仍按既有规则串行，独立工具任务可并行。启动、关闭、连接管理及实际响应性需验证，是否需要内部工作线程等实现细节由证据决定，当前尚未实现。

### R59 后台记忆整理的模型选择（已确认，DL-124，对应核对 O10）

用户确认后台记忆整理默认沿用该角色的对话模型，无需用户必须再配一个模型；需要时可按 DL-15 为该角色单独绑定记忆整理模型，从全局已配置模型服务中选择。

复用的是模型服务配置和调用实现，不复用角色当前聊天的模型上下文；后台整理仍根据自身的待整理记录、相关事件及整理职责构造输入，按既有条件独立触发，不直接替角色更新当前状态或写日记。自主额度归属继续遵循 DL-109，模型选择不增加额外审核模型或固定三模型槽位。

本项确认默认继承及按需覆盖方式，具体绑定字段与开关、任务链资源关系仍待接口验证；失败进度和重试原则见 DL-125／R60，当前尚未实现。

### R60 后台记忆整理失败后的进度与重试（已确认，DL-125，对应核对 O03、O04）

用户确认模型请求、整理结果保存等步骤失败时，保留原始记录及未完成内容的待整理状态，记录实际错误，不推进尚未成功处理范围的完成标记。只有对应记忆结果、来源及索引成功保存后，才记录该范围已处理；已成功提交的部分保留，重试不重复创建事件。

失败内容由后台稍后调度重试，不在实时回复链中立即反复调用或阻塞聊天；连续失败时逐渐延后重试，具体间隔及次数由后续实现方案和验证确定。配置恢复或重启后可继续调度待处理内容，不要求先产生新的 30 条或 50 条消息；不自动切换其他模型服务。

重试前读取当前已保存进度和最新相关记忆，仍遵循 DL-100 的旧结果不覆盖新版本规则；实际保存顺序、处理标记和去重约束待验证，当前尚未实现。不将后台维护不扣自主额度解释为失败时无限紧密重试。

### R61 同角色后台记忆整理的批次调度（已确认，DL-126，对应核对 O03、O04）

用户确认同一角色同一时间只运行一个后台记忆整理批次，消息积累、交流停歇、活动结束等触发同时到来时合并调度请求，不并行启动多份整理处理相同记录。保留每个触发的来源和范围，不因此混并不同窗口的原始对话。

批次开始时固定本次输入的记录范围；执行期间新增记录保留待处理，按既有触发条件在后续批次处理。结束后检查排队请求及待整理范围；失败范围按 DL-125 调度重试，成功范围不重复处理。容量分批原则见 DL-127，具体预算值仍待验证，不将触发阈值自动等同于硬切分容量。

该串行仅约束同角色的后台记忆整理，不占用角色实时决策的位置或要求聊天等待；后台整理与角色纠错仍按 DL-100 协调。不同角色独立调度，去重标记、调度与范围保存接口仍待验证，当前尚未实现。

### R62 后台整理的单批容量与超长记录（已确认，DL-127，对应核对 O03）

用户确认单批容量按整理模型的可用上下文预算控制，综合整理说明、相关事件和待处理记录，为结果输出预留容量；不另外按固定消息条数硬切，也不把 DL-94 的 50 条触发阈值当作每次必须一次读完的容量。

待整理范围超出容量时，按原始顺序分批处理；单条消息或活动记录过长时可分段输入，保留所属原记录及分段顺序，原始记录完整保存，不通过截断丢弃剩余内容。只有对应范围实际处理且结果保存后才推进完成标记，未处理部分继续保留待整理状态。

同一事件可跨批继续补充，沿用 DL-96，不因容量分批自动新建事件；后台单批串行及失败处理继续遵循 DL-126、DL-125。模型预算来源、分段策略、处理位置和实际容量由实施验证确定，不新增需要用户逐次管理的批次设置，当前尚未实现。
