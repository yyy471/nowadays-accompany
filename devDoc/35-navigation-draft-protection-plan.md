# 下一阶段：入口收尾与统一草稿保护方案

日期：2026-10-23。输入：33号前端执行记录、34号独立复核。性质：待实施方案与任务包，不代表实现或验收已完成。

## 1. 本阶段目标与范围

完成阶段A最后的入口定位验收，并实施阶段B：用户编辑模型、角色绑定、展示资料、插件或连接设置后，不会因为切换页面、账号、关闭设置或正常退出应用而无提示丢失草稿。

本批只做两件事：**入口定位闭环；统一离开编辑上下文的规则**。不调整暖色设计语言，不拆分设置分类，不新增模型管理、资源导入、人设记忆功能，不改账号数据schema，也不重构后端主体。

开始实施时的已知事实：

- App内`navigate`、hashchange直接更新页面，能够绕开编辑器保护；部分账号切换又各自使用局部确认。
- SettingsDialog已经接收ModelsPage、SnowLumaSetup的dirty/busy上报，并使用公共useConfirm；不要重复实现第二套设置确认。
- 模型配置已有policy/draft基线比较；展示资料已有按账号的profiles/drafts；插件有编辑中的启用列表；角色绑定是一次性新增表单。这些状态定义不同，不能用“任意输入非空”作为全站dirty判断。
- `desktop/main.ts`关闭主窗口时执行hide，托盘退出及before-quit走requestQuit，然后Core.stop、销毁窗口、退出。当前requestQuit在开始时就设置quitting，需要把用户退出确认放到真正关闭流程之前。
- F4定位代码目前已出现useAccountEntryFocus及对应测试。A0应复核当前代码，不重复按旧报告返修；本计划不据文件存在宣称F4已独立验收。

## 2. 用户可见规则

| 动作 | 处理 |
| --- | --- |
| 页面干净时切页、切账号 | 直接执行 |
| 有草稿且动作会丢弃它 | 弹一次确认：继续编辑 / 放弃修改并继续 |
| 相关保存或提交正在进行 | 暂停该离开动作，说明“正在保存，请稍后再试”；不自动重放离开动作 |
| 只是打开设置，底层页面仍挂载 | 不丢草稿，不提示放弃 |
| 切换设置标签，表单保持挂载且草稿保留 | 直接切换；关闭设置时统一检查所有设置草稿 |
| 设置关闭按钮、遮罩、Esc | 共用一次关闭判断；有草稿确认，有相关请求在途则等待用户稍后操作 |
| 点击主窗口X，隐藏到托盘 | 保留窗口及草稿，不提示放弃，不启动退出 |
| 托盘退出、正常应用退出 | 检查全部编辑上下文；用户同意后才执行既有关闭流程 |
| 刷新、关闭浏览器承载页 | dirty/busy时提供beforeunload兜底，使用浏览器允许的原生提示 |

不自动保存，不把输入草稿写入正式配置；不承诺进程崩溃、强制结束或断电后的恢复。本批不做磁盘草稿恢复，API Key和管理密码也不得写入localStorage、sessionStorage、日志或确认内容。

确认文案用业务名称，例如“账号10002的模型配置尚未保存”；不得显示API Key、管理密码、完整提示词或配置JSON。用户取消后，原页面、账号、表单、基线和滚动位置保持不变；键盘焦点回到原操作入口。

## 3. 技术方案

### 3.1 一处准入，多处登记

保留页面现有草稿状态，只新增一个轻量注册与离开协调层，不引入Redux/Zustand等新框架，不把业务表单状态搬进公共控件库。

建议落点（名称可随项目规范微调，职责不可合并回页面）：

| 模块 | 职责 |
| --- | --- |
| `renderer/src/lib/drafts/registry.ts` | 注册、更新、注销编辑器元数据；按离开范围查询dirty/busy；不持有表单内容 |
| `renderer/src/lib/drafts/transition-controller.ts` | 单飞协调确认、二次校验和执行；可用纯逻辑测试 |
| `renderer/src/components/DraftProtectionProvider.tsx` | 将注册器与现有useConfirm连接，供App及编辑器使用 |
| `renderer/src/lib/use-draft-registration.ts` | 稳定注册编辑上下文并清理，适配React生命周期 |
| App及hash适配层 | 所有页面跳转都通过同一离开请求 |
| desktop/preload、main | 正常退出的窄IPC适配；不传递业务草稿或密钥 |

按钮、Modal、ConfirmProvider继续使用现有`ui/index.ts`。如果需要增加通用视觉组件才放入ui；账号模型、插件、草稿登记等业务规则不放入基础控件库。

登记项最少包含：

```ts
type DraftRegistration = {
  id: string;                         // 稳定唯一，如policy:10002
  owner: 'page' | 'settings';
  accountId?: string;
  label: string;                      // 短业务名称，不含用户输入正文
  dirty: boolean;
  busy: boolean;
  revision: number;                   // 草稿或基线变化时推进
  discard: () => void;                // 只清本地草稿，绝不发保存/删除请求
};
```

登记API必须具有稳定身份与幂等cleanup。异步保存结束、账号切换、隐藏标签均不得留下错误的dirty/busy登记。状态应在输入/提交动作边界及时发布，不能只靠一个滞后的effect，导致同一事件批次内“刚编辑→立即离开”绕过保护；注册器在执行前重新读取最新快照。

### 3.2 按会丢失的范围拦截

不能对每次导航都检查全系统草稿。

- 切换工作台页面：检查实际将被卸载或重置的页面编辑器。
- 切换账号：检查将被重置的当前账号编辑器。若某编辑器完整保留该账号草稿，允许直接切换，但必须仍登记该草稿，并在真正离开页面时保护它。
- 角色页与账号插件页共用Accounts组件，切换view也要按被隐藏/重置表单定义范围，不能只判断React是否卸载。
- 关闭设置：只检查设置范围；不丢弃底层页面草稿。
- 设置打开时发生外部导航且会关闭设置：检查页面与设置范围的并集，合并为一次确认。
- 正常退出：检查所有仍持有草稿或在途请求的登记项，包括隐藏设置标签。

### 3.3 离开流程与并发规则

1. 请求离开时，只记录目标动作，不先改hash、账号、focusDisplay、表单或弹窗可见性。
2. 计算受影响登记项；相关busy直接拒绝本次离开并给出提示。
3. 无dirty则进入最终校验并执行；有dirty则使用现有确认框。
4. 确认期间只允许一个离开请求。后续请求不排队、不替换目标；原确认结束后用户可重新点击。
5. 用户取消时不调用discard、不改变URL，也不清理入口定位请求。
6. 用户确认后重新核对登记项、revision、busy及当前上下文。若期间发生新编辑、保存或基线变化，原确认失效，取消本次离开并提示重新操作，不能把旧确认套用到新草稿。
7. 校验通过后调用本地discard，再提交目标动作；路由状态/hash由同一提交路径更新。不要在discard里请求服务端。

确认框存在期间，主UI由现有Modal隔离输入；仍需检查异步结果引起的revision变化。保存失败保持草稿及dirty；保存成功使用服务端返回结果更新基线，不能清除请求发出后新产生的编辑。最小实现可在保存期间禁用对应编辑器，优先保证行为清楚。

页面组件卸载注销只能发生在已获准离开或正常销毁时；不能先卸载再让注册器检查一个空集合。React开发模式重复挂载/清理不能误删另一代登记。

### 3.4 URL、前进后退与深链接

保留当前hash路由，不趁本批迁移路由库。

- 顶栏、侧栏、快捷按钮：先requestTransition，获准后才更新hash和page；入口账号/锚点请求与导航一起提交。
- `#/settings*`、旧路由重定向、程序性跳转都走适配层，不能在hashchange里直接setPage/setSettingsOpen绕过保护。
- 浏览器前进后退会先改变URL。对应用创建的历史项在`history.state`保存自有序号和canonical route，保留其他已有state字段。受阻时补偿回原历史位置，再询问用户；同意后只重放一次原历史移动。使用带ID的补偿标识，避免hashchange/popstate循环和重复确认。
- 未带应用序号的外部hash或历史项，取消时恢复原canonical URL，保留当前页面和草稿；无法可靠推导历史delta时不要猜测history.go。对此回退行为单独测试，避免承诺保留所有外部历史项结构。
- 相同页面的“回顶部”不卸载表单，不弹放弃提示；正在处理的账号定位入口只有在导航获准后建立。

验收重点是URL、可见页面和编辑上下文一致，取消不跳到错误账号。不要用setTimeout掩盖导航竞态。

### 3.5 各编辑器的dirty与基线

| 编辑器 | dirty定义与保留策略 | busy范围 |
| --- | --- | --- |
| 账号模型配置 | 现有policy/draft规范化比较；保存成功返回的新policy为基线 | 保存、账号暂停/恢复、能力测试及会覆盖基线的重读 |
| 新增角色绑定 | 相对空白表单基线比较，成功新增后重置；仅切私聊/群聊且无目标/卡片不视为有效草稿 | 保存、解除绑定；重新读取不能触发旧结果覆盖新输入 |
| 展示资料 | 沿用profiles/drafts的按账号基线；初载成功后才可编辑；隐藏账号的已保留草稿仍登记 | 保存及头像处理；避免未完成头像转换在离开后写回旧草稿 |
| 账号插件 | 规范化后的启用集合与开始编辑时基线比较，不能因数组顺序不同误判；继续使用mergeAccountPlugins | 保存、应用到实例等会改变该编辑上下文的请求 |
| 模型服务设置 | 复用ModelsPage每能力草稿与基线；新密钥非空参与dirty，不回显已保存密钥 | 保存、验证、模型发现等相关操作 |
| SnowLuma设置 | 复用现有dirty，包含新密码与连接字段；不重复创建第二个判断器 | 保存、连接验证及选择流程中会重置上下文的动作 |
| 外观设置 | 当前即时生效的设备偏好不作为未保存草稿 | 沿用现有即时保存规则 |

查询轮询只更新查询快照，不悄悄覆盖正在编辑的draft。远端配置变化时显示提示，显式重新读取才更新基线；有草稿时重新读取也走同一离开/重置判断。角色绑定删除属于独立业务确认，保留其现有说明，不拿“放弃草稿”代替“解除绑定”确认。

插件开始编辑另一个账号、取消编辑、撤销模型修改、恢复头像等主动丢弃操作要检查实际影响；没有dirty时不弹无意义确认。现有按钮行为如有不同，按此统一，不能每处追加自己的window.confirm。

### 3.6 隐藏窗口与真正退出

**隐藏窗口**：保持当前win.hide逻辑，不销毁renderer、不重置登记项，也不因为dirty阻止隐藏。恢复窗口后，页面、设置标签、账号与草稿都在。

**正常退出**：在现有requestQuit之前增加退出预检，形成`idle → checking → shuttingDown → exited`；取消/失败回到idle。不要在checking阶段设置quitting=true，否则窗口close和before-quit会误绕过保护。

建议退出协议：

1. 托盘退出和before-quit都调用同一个主进程退出协调入口，合并重复请求。
2. 主进程向唯一主窗口发送带requestId的退出预检；renderer冻结离开动作，通过登记器检查全部草稿和busy。窗口隐藏且需要确认时先显示/聚焦主窗口。
3. busy时拒绝本次退出并说明原因；dirty时使用公共确认框。确认通过后暂时锁定编辑，回复允许退出；取消后解除锁定。
4. main只接受当前主窗口主frame、匹配requestId的一次响应，忽略重复/过期/其他sender响应。确认有效后才设置quitting及shutdown Promise，调用原Core.stop等关闭逻辑。
5. renderer超时、崩溃或不可用时不静默假定同意。主进程使用原生对话框提示“无法确认未保存修改”，默认取消；用户明确选择继续退出才走既有关闭流程。迟到响应不可复用。
6. 正常退出开始后不再接收新的编辑/导航请求。保留既有Core.stop语义，不在本批增加强制跳过排空或绕过dataRoot锁的路径。

IPC只传requestId、状态及少量安全业务标签，不传草稿JSON、API Key或密码，不暴露任意channel调用器。preload增加明确的订阅/响应方法与注销函数，并同步renderer bridge类型；复用现有sender验证方式。

beforeunload用于浏览器刷新等兜底，不能依赖其自定义文案或异步确认。应用已确认的正常退出使用一次性放行标识，避免再次提示；应用启动失败退出、renderer未建立的退出路径需单独保留，不让保护机制阻塞错误处理。操作系统强制关机/杀进程无法保证确认，作为边界披露。

## 5. 验收用例

### 5.1 自动化：测决策与实际入口，避免只测纯函数

1. 干净、dirty、busy、多编辑器、不相干scope；同一请求只确认一次。
2. 取消时不调用discard/commit；同意时只调用一次；相关busy时不执行离开。
3. 确认期间revision变化、账号消失、保存完成、组件注销，旧确认失效。
4. 快速连续点击A/B、hash补偿及重放，不重复确认、不循环、不执行过期目标。
5. 各编辑器修改后恢复原值变干净；保存失败保持dirty；新增密钥有dirty但提示/日志无密钥。
6. A/B账号往返及隐藏设置标签仍有正确登记；开始编辑另一插件账号不会直接覆盖前一草稿。
7. 在途头像处理、查询重读、保存响应晚到，不覆盖新草稿或恢复已放弃草稿。
8. 退出协议检查请求ID、sender、重复响应、取消、超时以及已确认关闭；确认前Core.stop不执行。
9. 确认框嵌套于设置时Esc只作用于最上层；取消后焦点与草稿保留。

继续使用现有Vitest及公共Modal；纯逻辑测试不能替代至少一条App→页面编辑器→离开入口的集成验证。现有hook harness只适合生命周期时序，不将其称为真实DOM或视觉验收。临时fixture、截图和报告置于test-results，不纳入Git；测试源码进入test。

### 5.2 操作验收矩阵

对模型配置、角色绑定、展示资料、插件、模型服务设置、SnowLuma设置各执行：

- 修改→离开→取消：原草稿、账号、位置保留；再次离开仍提示。
- 修改→离开→放弃：进入原请求目标，重新进入表单时恢复已保存基线，不偷偷提交。
- 修改→保存失败→离开：仍有草稿提示；成功保存后离开不提示。
- 请求在途→离开：阻止且有反馈；完成后不自动跳走。

单独执行：设置打开不影响页面草稿；两个设置标签都有修改时关闭只弹一次；窗口隐藏再恢复不丢草稿；托盘退出取消后QQ仍按原状态运行；renderer不可用时默认取消。外观即时设置不出现“未保存修改”的误提示。

至少在1280×800和1024×720检查确认弹窗及保存反馈，键盘Tab/Esc可用。其余全站视觉收口仍属于后续阶段E。

- `npm run typecheck`、全量`npm test`、`npm run desktop:build`、`git diff --check`通过。
- 如果遇到Windows原子写入EPERM，保留首次输出与复跑结果，不因为前端用例通过就删除失败记录或宣称根因已修复。
- 提交前检查基础控件仍从公共UI入口使用，业务层没有新增散落confirm窗口或直接设置hash的旁路。
- 形成执行报告：任务包状态、变更文件、测试数量、关键操作证据、未验证边界。只记录核验过的事实。
