## 2. R1 / P1：字符预算与六条门槛冲突，提取会永久堵在最早文本

位置：`src/application/memory/extraction/coordinator.ts:271`，关联`src/application/memory/extraction/input.ts`的字符预算截断。

协调器用`batch.messages.length >= 6`判定是否允许提取。但这里的batch是已按24000字符截断的模型输入，并不是全部未处理的合格用户文本计数。当前缀长消息导致一批只能容纳1～5条时，协调器直接返回；它最多把水位推进到第一条合格文本之前，下一次仍读取完全相同的前缀。继续增加短消息、等待超过5分钟都不能解决。

### 实际复现

使用真实Core、JsonlStore、内置Agent及FakeChannel/FakeProvider，明确激活后依次发送：

1. 六条13000字符文本，每条均未超过单条24000字符限制。
2. 再发送六条短文本，每轮将可控时钟推进6分钟，排除最小间隔影响。

结果：

```json
{"name":"long-text-prefix","sent":12,"extractionCalls":0,"throughSeq":0,"status":"active","accountUsed":0}
```

普通回复已成功发送12次，自动提取仍显示active，调用0、水位0。第一条13000字符消息放入后，第二条无法装入本批，batch长度始终1；后续消息永远无法参与提取。这是确定性停滞，不是等待更多消息即可恢复的延迟。75号提到的“扫描窗口前部只有1～5条文本”也应与这一类活性问题一并解决。

### 修复任务 M3-FIX1

- 将“是否已累计至少六条未处理合格文本”的准入判断与“本次模型批次能装多少条”分离。
- 只有确认达到六条门槛后，才允许按字符预算处理一个较小的连续前缀批次；不要简单降低门槛，让只有一条新消息也开始付费调用。
- 准入统计本身也必须有界。对扫描上限前只有1～5条文本、后面仍有积压的情况，需要能够继续统计或保存安全的扫描进度，不能每次从相同前缀重新开始。
- 水位只在成功处理实际前缀后推进；不得通过跳过这些合法长消息来解除堵塞，不得直接跳到最新触发seq。
- 保持新的合格完成通知触发、5分钟间隔、配额和失败冷却，不增加后台周期补跑。

### 验收

覆盖1～5条长文本填满预算、总待处理文本达到6条、后续追加短文本，以及扫描上限前有少量合格文本的场景。证明只有1～5条待处理文本时调用仍为0；累计达到门槛后可处理有界前缀，成功水位推进，后续触发最终能越过旧前缀，无跳过合格文本或无限重复扫描。实际记录调用次数、每批seq、字符数和水位。对应I04/I05/Q01。

## 3. R2 / P1：自动提取仍继承Provider重试/回退，失败后未直接进入冷却

位置：`src/core/core.ts:254`，关联`src/providers/router.ts:644`的fallback与`:725`的重试循环。

Core将提取请求直接交给普通`providers.chat`，没有提取专用的单次执行策略。一次协调器配额准入后，Router仍按照服务配置自动重试，必要时还会继续尝试fallback；协调器只有在整段Router调用最终失败后才记录10分钟冷却。

73号要求网络/超时/鉴权等失败不进行Provider自动重试。75号虽然将该偏差记录为P2，但仅记录偏差不能替代既定行为：自动提取的调用限制及冷却承诺目前没有落实到实际Provider调用边界。

### 实际复现

真实Core与ProviderRouter，服务配置`retry.maxAttempts=2`。前六轮普通文本回复均成功；Fake提取Adapter第一次抛出可重试的限流错误，第二次成功返回空facts。

```json
{"name":"provider-retry","sent":6,"extractionCalls":2,"throughSeq":11,"status":"active","accountUsed":1}
```

没有新的用户完成通知，提取Adapter已被调用两次；本地配额只记一次，水位推进到11，状态active且无失败冷却。这不代表实际产生两笔费用，但证明了实际调用次数与方案要求不同。

### 修复任务 M3-FIX2

- 在统一ProviderRouter增加或复用显式的调用执行策略，允许提取指定单次调用、禁用自动重试及自动fallback；普通Agent原有重试行为保持原语义。
- 继续复用统一路由、权限、凭据、限流、配置代际和执行guard检查，不另写一套Provider客户端，也不要为提取全局修改用户服务的retry配置。
- 一次提取Provider调用失败后交回协调器记录至少10分钟冷却，不推进成功水位；必须等冷却结束且出现新的合格完成通知才再考虑。
- 针对真实Router链路补测试，不能只在FakeExtractionChatPort上模拟一次最终失败。

### 验收

在服务配置允许多次重试及显式fallback的条件下：提取首次遇到可重试错误后Adapter调用1次、fallback调用0次、配额占用1次、水位不变、进入至少10分钟冷却；冷却内新完成通知不调用；到期后没有新通知仍不调用。另证明普通Agent重试与回退未退化。对应Q03/Q05。
