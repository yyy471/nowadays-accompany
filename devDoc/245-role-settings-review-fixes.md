| 编号 | 问题 | 修法 |

| RS-R02 | 声音地址改动后旧探测结果仍被当成当前结果 | 探测结果绑定发起时的地址与协议，变化即失效并丢弃晚到响应；能力声明按来源解析 |

## 2. RS-R01 · 跨站点不再沿用旧密钥

- 新增 `serviceIdentityOf`：把资源身份定义为「协议 + origin」。同站点换路径（例如换 API 版本前缀）仍算同一个服务，允许保留已存密钥；换域名、换端口或换协议都算换服务。[resource-service.ts](../backend/src/application/resource-service.ts)
- `update` 在原有「直填密钥与 `credentialRef` 二选一」检查之后增加一层：协议或 origin 变化、请求未给 `secret`、且该资源仍持有已存密钥时，抛 400 `RESOURCE_CREDENTIAL_STALE`，提示重新填写密钥或显式清除。[errors.ts](../backend/src/domain/errors.ts)
- 三条放行路径：同时提交新密钥（替换）、显式 `secret: null`（清除）、原本就没有已存密钥。这样既不会把旧密钥发到未确认的新服务，也不影响同站点常规编辑。
- 测试覆盖服务层与 HTTP 层：同 origin 换路径保留 `stored`；换端口、换协议分别被拒；带新密钥换站点成功；显式清除后可自由换站点；没有密钥时换站点不需要确认。

## 3. RS-R02 · 探测结果跟随地址与协议

- 纯逻辑新增 `normalizeBaseUrl`、`isProbeCurrent`、`resolveCapabilities`（[voice-config.js](../desktop/desk-preview/renderer/src/voice-config.js)）。地址比较只忽略首尾空白与末尾斜杠，与后端规范化一致。
- 页面用 `probeSource` 记录发起探测时的地址与协议。响应回来时若当前表单已改地址或协议，直接丢弃并提示「地址已修改，刚才的探测结果已丢弃」；探测期间切换角色也一并丢弃。
- 能力声明按来源解析：表单仍指向已保存服务时用已保存配置的 `capabilities`；换了地址则用同一地址的探测结果；两者都不匹配时返回 `null`，宁可跳过能力校验也不拿旧声明去校验新服务。预置音色列表同样只在探测来源匹配时展示。
- `validateVoiceForm` 区分「没传 capabilities」与「显式无能力」：显式传 `null` 时不再回落到表单里的旧声明。

## 4. RS-R03 · 角色切换令牌

- 面板按 `roleId` 维护单调递增的 `roleToken`，切换角色即递增。探测、试听、保存、上传、删除与参考音频列表刷新在发起时捕获令牌，回调先比对再写状态。
- 试听在播放前比对令牌：切到别的角色后，晚到的音频既不播放也不写入 `notice`；切角色时同步停止播放并回收 Blob URL。
- 切角色时重置 `busy`、`probeBusy`、`previewBusy` 与探测状态，避免上一个角色的进行中状态卡住新页面。

## 5. RS-R04 · 参考文本随录音清理

- 新增 `withReferenceAudio`：换到不同录音时清空 `referenceText`，选中同一段录音时保持已填文本。下拉切换与上传新录音都走这条路径。
- `toVoicePayload` 增加保护：没有 `referenceAssetId` 时不提交参考文本，避免出现「新录音配旧原文」或孤立文本。
- 后端原有行为保持不变：音频变化且请求未提供新文本时，后端本来就会清空旧文本；本轮修的是页面不该主动发送旧值。

## 6. RS-R05 · 导入完成不切回旧角色

- 设置页的 `onChanged` 不再把当前角色作为首选角色传给全局刷新，改为无参调用：刷新角色列表并递增修订号，保持用户当前选择。
- 外观面板引入与声音面板相同的角色令牌：导入与补差分在完成后比对令牌，过期回调不再写衣柜列表、提示、错误或扫描状态，也不触发全局刷新。上传本身仍正确归属原角色。

### 9.1 RS-R01 · 引用凭据同样要求重新确认

- 判断从「是否仍持有已存密钥」扩展为「是否仍沿用原凭据」：`keepsStoredSecret` 之外增加 `keepsReference`，即请求没有提供新密钥、且 `nextConfig.credentialRef` 与当前配置完全相同时视为沿用。
- 放行路径相应扩展为四条：同时提交新密钥、把 `credentialRef` 换成不同的引用、移除引用、原本就没有凭据。`secret: null` 只清除直填密钥，不能替代「重新确认引用」，因此沿用引用时仍拒绝。
- 错误文案改为「请重新确认凭据：填写新密钥，或把 credentialRef 换成新的引用」，覆盖两种凭据形式。
- 测试覆盖 `env:` 与 `file:` 两条路径：同站点换路径可沿用；换站点沿用原引用被拒；换站点同时换引用放行；`secret: null` 但引用不变仍被拒；移除引用后换站点放行；HTTP 层同样生效。

### 9.2 RS-R02 · 换服务即清空服务专属音色

- 新增 `withVoiceService`：把地址或协议变化统一收敛成一次表单更新，变化时清空 `voiceId` 与 `capabilities`。
- 地址比较用 `normalizeBaseUrl`，只差末尾斜杠不算换服务；同站点换路径算地址变化，同样清空音色——这条比 RS-R01 的凭据标准更严，因为音色 ID 是服务方分配的，跨路径不保证仍然存在。
- 参考音频与参考文本不受影响：它们是角色本地素材，换服务后仍然可用。
- 页面的地址与协议输入改走这条路径，并在地址字段提示「换地址或协议会清空预置音色」。

### 9.3 RS-R03 · 离开设置页后不再播放

- 过期判定从「角色令牌」扩展为「角色令牌 + 挂载标记」：`isStale` 在组件卸载后恒为真，挂起的试听、探测、保存、上传、删除回调全部作废。
- 卸载时同时停止已经开始的播放并回收 Blob URL；挂载标记在 effect 里每次挂载重置，兼容 StrictMode 的挂载—卸载—再挂载。

### 9.4 RS-R05 · 忙碌状态只由当前操作清理

- 外观面板与声音面板的 `finally` 改为条件清理：令牌失效时不写 `busy`，也不清文件输入框。
- 角色切换时由角色 effect 重置 `busy`、`probeBusy`、`previewBusy`，因此不会因为跳过清理而卡住新页面。

## 10. 244 第 4 节补修：换服务时参考模式失效

2026-11-10，[244 第 4 节](244-role-settings-independent-review.md#4-245-第-9-节补修独立复验) 确认 RS-R01、RS-R03、RS-R04、RS-R05 关闭，RS-R02 的预置音色场景通过，但克隆音色仍沿用旧服务的参考模式。

### 10.1 缺口

`withVoiceService` 换服务时只清空 `voiceId` 与 `capabilities`，`referenceMode` 留在表单里。能力未知时页面不渲染参考模式选择，旧模式因此完全隐形，随新地址一起提交；后端在能力未知时无法判断这个模式属于旧服务，保存返回 200，配置继续带着旧模式。

### 10.2 修法

- `withVoiceService` 一并清空 `referenceMode`。预置音色与参考模式都是服务方分配的标识，换地址或协议后必须由新服务的能力重新决定；只差末尾斜杠不算换服务，同站点换路径算换服务，与音色同一标准。
- 参考录音与参考文本保留：两者属于角色本地素材、与录音绑定，不随服务变化。
- 能力未知时参考模式选择不渲染，补一条提示——能力未知提示「先点测试连接，再选择参考模式」，服务确实未声明模式时提示「不能使用参考音频音色」。否则清空后用户既看不到入口，也看不到原因。旧 IndexTTS 协议没有探测接口，不显示这条提示。
- 后端不额外拦截：能力未知时它无法区分「旧服务的模式」与「用户刚探测新服务后选的模式」，加限制会误伤正常保存；能力已知时 `assertSourceSupported` 已经拒绝不在声明范围内的模式，合成前也会再校验一次。
- 语言、语速、情感强度不随服务清空：它们是通用参数而非服务分配的标识，服务能力已知时按声明校验，未知时保留用户选择。

### 10.3 测试与验收

- 桌面端用例扩展为「换服务后预置音色与参考模式失效，参考音频保留」：地址变化、同站点换路径、换协议都清空模式；只差末尾斜杠保留；改其他字段不动；换服务后未重选模式时载荷 `referenceMode` 为 `null` 而不是旧值。
- 桌面端 87／87 通过，`renderer` 下 `tsc --noEmit` 与 `npx vite build` 通过。
- 本轮只改桌面端（`voice-config.js`、`VoicePanel.tsx`、对应测试），后端源码未改；仍跑了一次完整离线验收确认无连带影响：21／21 步、300／300 项，`realServiceCalls=0`、`sourceUnchanged=true`，目录 `backend/test-results/p5-2026-11-10T07-10-16-286Z-99736e2a/`。

## 11. 244 第 5 节补修：能力来源与不支持来源

2026-11-10，[244 第 5 节](244-role-settings-independent-review.md#5-245-第-10-节补修独立复验) 确认 RS-R01～RS-R05 在已验范围关闭，RS-R02 原问题关闭；同时新增 RS-R06、RS-R07 两项，都落在声音配置页。

### 11.1 RS-R06 · 当前探测优先于已保存的能力声明

- `resolveCapabilities` 的来源顺序改为「当前地址的探测 → 已保存配置 → null」。已保存配置的声明可能为空（旧配置，或换服务后保存的配置）或过期，不能挡住刚探测到的结果。
- 探测结果仍要求地址与协议都匹配（`isProbeCurrent`）；探测没有带回声明时回落到已保存配置，两者都不匹配才返回 `null`。
- 换服务后保存地址再点「测试连接」：探测摘要与模式选择器现在来自同一份声明，不会再出现「摘要说有 1 种模式，表单说缺少能力声明」。

### 11.2 RS-R07 · 已知不支持与能力未知要分开处理

- `validateVoiceForm` 在能力已知时区分两种情况：`referenceModes` 为空表示服务明确不支持参考音频，报 `REFERENCE_UNSUPPORTED` 并阻止保存与试听；能力未知时不校验，仍允许保存地址等配置。
- 对称补上预置音色：`presetVoices === false` 时报 `PRESET_UNSUPPORTED`。
- `toVoicePayload` 在能力已知时携带 `capabilities`。后端据此拒绝服务不支持的音色来源（`VOICE_REFERENCE_MODE_UNSUPPORTED`、`VOICE_PRESET_UNSUPPORTED`），并把声明随配置保存下来，重新打开页面不必再探测一次；能力未知时不带该字段，让后端沿用同地址已保存的声明。
- 错误文案补上这两个码的翻译；页面提示同步说明「请改用预置音色／参考音频音色」。

### 11.3 测试与验收

- 桌面端新增 1 项用例「服务明确不支持某种音色来源时拒绝保存，与能力未知区分开」；「能力声明」用例改写为探测优先，并覆盖「已保存声明为空」「探测没有声明时回落」；载荷用例断言能力已知时提交 `capabilities`、未知时不提交。
- 后端新增 1 项用例「capabilities sent with a save are validated and persisted」：带空 `referenceModes` 的声明保存参考音色返回 400 `VOICE_REFERENCE_MODE_UNSUPPORTED`；声明支持时保存成功且能力随配置持久化。
- 桌面端 88／88 通过，后端 301／301 通过；`renderer` 下 `tsc --noEmit` 与 `npx vite build` 通过。

## 12. 244 第 6 节补修：请求与校验使用同一份能力声明

2026-11-10，[244 第 6 节](244-role-settings-independent-review.md#6-245-第-11-节补修独立复验) 确认 RS-R06、RS-R07 在已验范围关闭，新增 RS-R08（P3）。

### 12.1 缺口

探测 B 成功后把地址临时改到 C 再改回 B：页面重新采用 B 的探测结果，展示与校验都用它，但表单里的 `capabilities` 在改到 C 时已被清空，`toVoicePayload` 读的是表单，于是保存与试听请求都不带声明。对首次保存的服务，这会让能力声明丢失，重新打开还要再探测一次。

根因是「展示与校验读解析出的有效声明，请求读表单里的副本」，两处来源不一致。

### 12.2 修法

- `toVoicePayload` 增加可选的 `capabilities` 参数：调用方传入校验用的那份有效声明；不传时仍读表单，保持既有调用方行为。
- 声音页的保存与试听都改为 `toVoicePayload(form, { capabilities: activeCapabilities })`，与 `validateVoiceForm` 用同一个来源。
- 能力确实未知（解析结果为 `null`）时不带该字段，让后端沿用同地址已保存的声明，行为与第 11 节一致。
- `voice-config.d.ts` 同步第二个参数的类型。
