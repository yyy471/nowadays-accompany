# 401 · 新角色首次思考、网页阅读与单角色迁移

## 1. 范围与起点

依据[已确认的 DL-161～DL-166](../../161-digital-life-direction-decisions.md#dl-161-新角色首次启用时获得一次自主思考机会)，基线为 `f080c77`。本专项由主进程先写方案，多名 Astra 独立审查后分给 Sol 实施。实施后的独立复核记录在本文末尾。仓库使用角色业务库、图检查点和全局资源库，既有[存储与自主执行规范](../../specs/storage-memory-and-autonomy.md)继续适用。

基线版本中新角色创建后处于停止状态，恢复活动会重新调度已有工作。实时主链取最近 30 条消息，拼接人设、状态、任务简报与工具回执后调用模型。MCP 原始回执此前已作为工具事实入库。整套安装已有冷备份说明，单角色迁移需要独立入口。

## 2. 方案初稿

**首次自主思考（DL-161）。** 新建角色时在角色业务库登记待首次启用。一次显式启用后，活动中且对话模型具备调用条件时，在已有自主调度队列登记一个有稳定去重键的唤醒。首次标记与入队使用同一事务，后续认领、额度、用户抢占、停止与重启复用既有机制。没有可用模型时保留资格，调度或资源恢复后再检查。历史库升级不能把已有角色批量重新当成新生。迁移应保留资格或已消费状态。首次提示允许等待、安排以后活动和使用已启用能力，用户对话只由已有分享入口接收自主消息。

**网页阅读（DL-162、DL-163）。** 走现有 MCP 入口。支持带来源 URL 和可定位原文的网页结果，包括浏览器提供的结构化片段或标准文本资源。保留页面版本或内容摘要、段落或源偏移、原文及角色和工具调用归属。任意工具回显中出现网址不能单独证明是网页原文。预取进入工具事实库存储，已读事实以最终送给角色模型的原文为准。请求组装应携带可序列化的来源定位；发送前被裁剪、只剩摘要、后台工具尚未交付、预算拒绝和本地取消均不得前移游标。重试／重复读取按稳定来源范围去重，页面版本变化和跳读能区分。提供按角色回查已读原文和位置的入口，记忆形成、事件回查及后续续读都能获取真正送达的片段。工具原始回执仍可追溯。

**单次上下文（DL-164）。** 在 AgentGraph 每轮模型调用前选择输入，覆盖实时回复、办事续行和含工具结果的下一轮。依据绑定现有容量字段及输出预留计算预算，计入系统提示、消息、工具描述与协议续轮材料。保留必要人设和状态、本轮全部已提交要求、任务目标，再选当前步骤依赖的原文。较早材料可按原消息／工具／证据 ID 定向取回，不受最近 30 条的固定窗口限制。其余材料用简短摘要和可执行的回查引用，完整事实保存在角色库。多工具结果与发出调用的助手消息保持成组，保留厂商续轮块。容量不足以容纳最小请求时返回明确原因，不发超限请求。自主额度、用户任务累计用量及后台记忆分批仍沿用各自规则。

**单角色迁移（DL-165、DL-166）。** 提供可实际操作的本地导出、导入预检、服务映射与冲突选择入口。包有版本、角色实例 ID、有效载荷清单与校验，包含角色身份、窗口、经历、记忆及证据、角色状态、自主安排、笔记和所引用受管素材。绑定清单记录来源服务标识、类别及用途，目标安装通过显式映射使用现有本地资源及其密钥。丢失映射须保持可见且不可误用。全局库、主密钥、资源凭据、MCP 环境值、源安装运行配置及可执行恢复授权均不能作为绑定配置导入。分开处理历史业务事实和可恢复执行，保护预置身份、角色隔离与目录边界。

同一 ID 根据两端持久化事实及可验证的共同基线，区分相同、单向发展、分化和无法证明的关系。禁止按更新时间或记录数量覆盖。双方均有独有经历时预检返回冲突，本机与包保持可用。用户可选择保留本机或采用包，确认时重验本机和包的版本，发生变化需重新选择。导入先在隔离位置验证再发布，失败／重启须恢复到完整状态。幂等导入保留选定时间线、角色 ID、文件与关联关系。此操作使用本地用户入口，测试只对临时安装执行。

## 4. 三方审查后的实施约束

运行时、模型上下文与角色迁移分别由一名 GPT-6.2 Astra（medium）独立对照现有实现。初审发现以下问题，主进程已纳入方案。

1. **首次资格可恢复。** 资格随新角色身份在同一业务库事务创建。新版本向已有角色缺省赋予“历史角色”的兼容语义。全局活动状态与业务库不能共用事务，在活动恢复、启动收尾和模型服务恢复时重新检查资格，对已激活而尚未入队的角色完成补偿。模型就绪包含绑定、启用、维护和本机凭据解析，匿名模型和注入的离线适配器依现有约定工作。检查本身不发送模型请求。用真实旧 schema 验证升级，旧聊天测试夹具可明确构造已度过首次启用的角色，另用尚未启用的新角色验证实际默认行为。
2. **请求与证据有明确交接点。** 接纳来源为 HTTP(S) 的 MCP 嵌入文本资源，以及有 URL、版本或可稳定计算版本和可定位原文的结构化结果。重复表示只处理一份，错误、二进制、单独链接及普通文字里的 URL 仍按普通回执。上下文选取传递可序列化的工具调用和原文位置。协议完成序列化、生成请求被提供方接受后才确认送达，离线模型也要有真实消费的确认。发送前失败、认证失败或明确拒绝均不推进，接受后中断保留已送达事实，无法确认接收的请求保守等待可确认的重试。持久化须幂等，可追溯到模型调用。已读查询支持跳读区间和重新打开的页面版本。记忆登记、启动回填、形成、事件／活动取证和模型工具回查统一使用已送达的投影，未送达的预取原文只保存在原始工具事实。
3. **容量基于实际出站格式。** 使用绑定的字符容量和同单位的输出预留，给无显式配置的模型一个有文档的缺省值。投影纳入协议编码、工具定义、附件和签名续轮块。先验证容量，再计费和发出调用。优先保留可辨认的必要人设、状态、本轮所有要求和任务目标。步骤需要的原文优先于额外人设、回忆摘要和旧聊天。旧事实可按角色和窗口／任务搜索定位并分页读取，包括 30 条消息或 40 次调用之外的事实。持久化恢复时没有合法原生续轮块的旧事实应走有引用的事实材料。实际活跃的同轮多调用须保留配对，不能伪造签名，也不能跨模型重放。四种协议各自检查最终请求。
4. **单角色迁移采用本地维护命令。** 通过 Node 24 的本地 CLI 向指定安装导出、预检、应用，服务和维护命令共用可在进程退出后自动释放的排他锁。选择采用包是显式操作，不能由模型自主触发。目标先用本项目 schema 创建暂存角色库，按版本化数据清单导入，不接受外来 DDL。保留角色历史、执行与用量事实、自主额度和业务笔记。重新建立执行检查点文件，明确区分已保存的事实、未来安排和不可安全恢复的在途执行。只携带角色工作空间与受管素材，覆盖历史仍引用的素材。对外部链接、越界路径、Windows 路径别名及重复条目拒绝发布。
5. **目标凭据与历史副本分别处理。** 服务映射按类别及用途校验目标资源。待映射的源绑定不得在目标安装误命中同名／同 ID 服务，目标用自己的凭据。排除全局服务配置、主密钥、源 MCP 环境、运行授权、原站点连接快照。管理工具的调用参数、嵌套 JSON、模型原始输出及其派生事实也可能含明文密钥，须对凭据字段和值处理；不能保真迁移时可返回记录位置，不回显秘密。用户自写笔记仍属角色资料。用已知测试密钥扫描解码后的包，再由目标接收一次实际请求，验证两端密钥隔离。
6. **时间线选择与发布。** 使用可验证的共同快照及规范化持久化事实，排除本机绑定、派生索引、导出时刻等环境差异。无法证明单向发展时保守进入选择。选本机不写入，采用包前重验包摘要、本机事实、目标映射和身份。目标已有同 ID 的孤留历史参与比较，有待清理记录或初始化未结束时阻止替换。预置身份按内置键校验，禁止覆盖另一安装中身份不同的夏澄或以普通角色冒充预置。发布采用同卷暂存、持久化日志及确定的恢复顺序，启动时先恢复导入，再创建预置、清理待删除数据和调度任务。验收应模拟两侧分化、确认变旧及换名各阶段中断，并核对迁移前后任务累计用量。

实施分为首次启用、上下文选择、网页证据、迁移包读写、迁移预检与发布五份。共享业务 schema 由主进程合并为一次顺序升级，模型入参和交付证据的接合点须运行同一条端到端用例。专项失败直接回到相应实现修正。

三名审查者在修订后分别重读本节，均确认所提阻断项已纳入，可以派工。实现使用 GPT-6.2 Sol（medium），离线复验由主进程执行。

## 6. 主进程独立复核

主进程使用 Node 24、独立的临时安装、本机 HTTP 模型端点和真实 stdio MCP 进程。下表记录独立构造的业务场景。专项测试另外覆盖四种协议、旧库升级和发布中断。

| 复验 | 观测结果 |
| --- | --- |
| 首次启用与重启 | 无凭据时模型收到 0 个请求。补入本机凭据并重启后收到 1 个鉴权请求，扣 1 个自主点。主窗口消息数为 0，反复启停后活动数仍为 1 |
| 较早对话原文 | 整段对话共 40 条消息，最后要求找回最近 30 条之外的图书馆取件凭条。真实出站请求含最早消息中的独有原文。设置总量 22,800、输出预留 1,300，每个请求都守住额度 |
| 单条超长旧记录 | 一条约 3.5 万字符的历史记录含深处的交接封签。首次复核只能返回开头摘要。补修后在 1,500 字符容量中，1,150 字符出站请求保留了对应的连续原文及回查位置，另留 350 字符给输出 |
| 网页预取与实际送达 | MCP 预取十段，模型只收到前三段。初次复核时记忆接口可查十段。补修后，逐字符比对出站原文与库内记录完全相同，截止 UTF-16 偏移 7,419。角色从另一窗口可查同一位置，另一角色看到空列表。原始工具回执仍能核对十段 |
| 密钥轮换与历史副本 | 使用预置角色实际执行服务创建，再通过 HTTP 轮换凭据。检查序列化迁移包及 40 个解码后的素材，现用和轮换前的测试密钥均未出现，用户消息仍可查 |
| 两套安装的时间线 | 导入后身份、窗口、聊天与手写笔记可读。重复导入同一包返回 `unchanged`。之后源端和目标端分别聊天且源端改写笔记，预检返回 `diverged`，漏选被拒。保留本机、拒绝变旧的令牌、明确采用包均得到预期结果。目标请求只使用目标密钥，运行中的后端持锁时维护命令被拒 |
| 已读证据随角色迁移 | 将读过上述网页的角色用 CLI 导入另一安装，保留完整原文、7,419 的截止位置、源工具和模型调用 ID。目标记忆 API 可按原证据 ID 回查相同文字，角色已消费的首次思考资格也随身份保留 |

复核还发现四处需要修正的行为。中断重试曾把助手半句排到原问题之前，现按窗口序号合并本轮要求与历史。普通 MCP 环境值曾让笔记中相同单词被误筛，现能保留普通文字同时剔除嵌套凭据。映射生图服务时已保留角色自己的模型选择。时间线比较现能以两端共有、且有各自新增的已提交用户消息证明分化，即使笔记已改写也能识别。专项另覆盖九次真实子进程退出，核对了恢复后的角色索引、目录和业务数据。

既有 P4 崩溃恢复场景亦按真实提供方请求体核对。恢复后同一条事实保留原业务步骤 ID、工具名、`unknown` 状态与 `PROCESS_INTERRUPTED` 诊断。并发纠错仍由两个独立 OS 进程在同一文件屏障读取版本 1，再调用生产 `MemoryQueryService` 竞争更新。成功方的正文与索引一致，另一方收到 `MEMORY_VERSION_CONFLICT`，原始证据可查。

本机运行证据位于 `backend/test-results/401-main-review/`。前六条的退出状态见 `independent-results.json`，逐字符与跨窗口检查见 `web-result.json`，迁移后回查见 `migrated-reading-result.json`。模型容量以 UTF-16 字符约束实际请求体。线上厂商的 token 上限和计费、Windows 断电时的磁盘行为仍需各自环境验证。
