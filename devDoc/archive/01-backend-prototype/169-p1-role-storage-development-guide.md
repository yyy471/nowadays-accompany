## 1. 本阶段交付

按照 DL-86，通过独立 CLI 和本地 HTTP API 完成一个角色的创建、设定更新、状态和消息存取、资源配置及绑定，并证明停止后重启数据仍连续。修改设定保持原角色身份、历史和工作空间。

P1 的完成边界是数据与配置可持久保存、读取。Agent 回复、模型服务实际调用、Skill／MCP 调用、完整事件记忆在 P2 接入；持续调度在 P3，组合恢复在 P4。正式桌面界面、QQ、网页访问、视频和电脑控制不进入本阶段。不迁移旧主线历史或 P0 测试数据，不增加角色设定冲突处理、内容预检或授权审批。

任务、执行及调用的数据关联在本阶段定清并验证仓储约束；这不等于在 P1 提前实现角色规划、图调度和完整任务执行。

## 2. 工程边界与目录草案

正式后端建议位于独立的 `backend/`，有自己的 `package.json`、锁文件和配置；根目录旧 `node_modules` 不作为依赖来源。`prototypes/p0/` 保留为技术回归样例，不直接扩展成正式业务工程，也不批量复制旧 `dev` 代码。

沿用 DL-123 的单个 TypeScript 后端进程，分为下列职责，依赖显式注入：

| 模块 | 职责 |
| --- | --- |
| bootstrap | 确定应用目录、打开存储、组装服务、启动和关闭本地 API |
| domain／application | 角色、消息、资源、任务的业务契约与应用服务 |
| storage | 应用配置库、角色业务库、检查点库工厂及显式 schema 版本 |
| http | 本地 HTTP 请求／响应映射，不在处理器中重复业务规则 |
| cli | 连接已启动的后端，调用同一 HTTP API；不另行直接写数据库 |
| tests | 临时数据目录、离线样例、重启与失败证据 |

Node.js 24.22.2 是 P0 实测起点，SQLite 候选版本见 166。P1 应声明与实际验证一致的运行时范围、记录直接依赖和完整锁文件；不能把 P0 较宽的 `engines` 声明当作其他 Node 版本通过证据。HTTP 框架、测试工具及构建方式在 P1-01／P1-02 实测后留证，不直接沿用旧项目选型。

建议新的默认运行目录如下，`appRoot` 来自启动入口或显式配置，不根据当前工作目录漂移，也不默认为系统用户数据目录：

```text
appRoot/data/
  app.sqlite
  roles/<roleId>/
    business.sqlite
    execution.sqlite
    workspace/
```

工作空间默认位于 Nowadays 所在目录下，遵循 DL-14；笔记后续采用 Markdown。路径由稳定 roleId 推导，不用可变角色名作目录身份。P1-01 固定实际目录和命名后，写入启动说明；此处没有创建正式运行目录。

## 3. 数据契约草案

### 3.1 应用配置与角色业务数据

建议 `app.sqlite` 保存角色目录索引、模型／MCP／Skill 配置条目；角色业务库保存角色自身绑定和经历。全局保存配置定义不代表共享 MCP 连接实例；实际连接生命周期在 P2 接入时设计。跨文件数据不声称具备单笔 SQLite 原子事务。

| 记录 | 最小内容与约束 |
| --- | --- |
| 角色目录索引 | roleId、相对目录、初始化状态；未初始化完成的角色不能报告为可用 |
| 角色设定 | 稳定 roleId、显示名、设定正文／原始载荷、设定修订号；修订不创建新角色，也不清空状态或历史 |
| 当前状态 | 状态内容及状态版本；不以设定修订号代替状态版本，不自动分析设定冲突 |
| 对话窗口 | windowId、所属 roleId、类型与来源关联；不同窗口消息独立查询 |
| 消息 | messageId、windowId、发送者、正文、来源平台、保存顺序、时间及完成状态；先保存输入，再由后续阶段触发决策 |
| 模型服务 | 稳定服务编号、协议、地址、凭据引用或本地存储位置、启用状态；模型名可手动保存，不能只接受内置列表 |
| MCP 配置 | 稳定资源编号、stdio 启动参数／环境或后续传输配置、启用状态；本阶段不建立连接或试运行 |
| Skill 配置 | 稳定资源编号、内容位置或资源引用、启用状态；不在保存时执行脚本或审查其内容和依赖 |
| 角色资源绑定 | roleId、能力、资源编号／模型名及必要开关；记忆整理模型缺省时继承对话绑定，支持单独覆盖 |

第一轮只验收一个角色，但 roleId／windowId 的关联必须明确，不能依赖“当前只有一条记录”。保存角色资料和资源配置时检查基本请求结构及关联完整性，不引入用户已排除的内容审查、环境预检或额外审批。

消息来源当前默认 `nowadays`；外部平台名称作为数据来源保留，不因此实现 QQ 连接。消息字段需承接 `generating`／`completed`／`interrupted` 等语义，最终枚举与 P2 流式契约一起定清；P1 不伪造模型生成中的数据。按窗口稳定顺序读取，避免仅用毫秒时间戳排序。

资源配置保存与真实验证分开。模型列表、测试连接是已确认的后端能力，放入 P2 模型适配工作包实际实现；P1 不能把“配置已保存”返回为“连接测试成功”。凭据不回显到普通列表、错误正文或测试报告。

### 3.2 持续任务、图执行与工具调用

本节承接 DL-66、DL-69～DL-73、DL-101～DL-103 及 168 的 L04／L05，防止正式表结构继续绑定 P0 的最小假设。

| 身份 | 数据职责 |
| --- | --- |
| taskId | 一项具体持续目标、进度、任务状态、结束原因；不以图完成或单次工具 success 自动认定目标完成 |
| executionId | 一次决策／图执行，对应相同 `thread_id`；记录触发来源、窗口、状态和独立的加载／提交版本 |
| 任务与执行关联 | 支持原 taskId 被后续执行接续，替代旧回复不删除或重建原任务；是否采用关联表及具体基数在 P1-01 定清 |
| toolCallId | 一次实际调用的稳定身份，关联任务、发起执行及逻辑调用步骤；恢复不会因相同参数就新建或合并另一调用 |
| 工具调用与结果 | 调用的 pending、running、success、failed、unknown 五态继续沿用；实际返回及错误按原调用保存，不以模型描述代替实际效果 |
| 运行模式 | 前台／后台独立记录，不以转后台改变调用编号、伪造失败或重发；承接已有模式及切换记录的查询需求 |
| 资源延续关联 | 原任务链已有的资源延续资格可持久表达；关闭后阻止新任务使用，原链按 DL-71 继续到结束，不把资格锁成永远使用旧配置 |

`stateVersionLoaded` 表示本次判断加载到的状态版本，`stateVersionCommitted` 表示该执行已提交的版本；提交重入返回后者。设定修订、资源配置修订各自保存，不混用同一个版本字段。

当前模型每轮只有一个工具请求。未来一次模型响应多个调用时使用稳定 callId／轮内序号；相同工具和参数的两次有意操作仍是两次调用，不能只按参数摘要去重。

正式调用记录应能保留原始工具响应与供模型使用的适配结果。明确工具错误、发出前失败、发出后失联及本地适配错误分别记录原因，沿用既有五态；普通文本、结构化结果和多内容块不能仅因不是 JSON 文本就记为执行失败。P0 的样例格式适配不等于所有 MCP 输出已验证。

### 3.3 保存与初始化

角色创建按“分配稳定身份并登记初始化 → 建立角色目录／两份存储及默认窗口 → 提交角色初始资料 → 标记可用”处理。中途失败要返回明确错误，保留可追查状态；重复恢复初始化时沿用同一身份，不自动创建第二个角色，不在失败时递归清除已有工作空间。

每份数据库有独立 schema 版本；首次创建和重开均须验证。P1 不实现旧主线或 P0 数据导入。正式回复／局部状态／执行完成标记的业务原子性、工具结果优先落库和提交重入规则继续承接 P0，后续 P2 接图时必须使用这些正式存储接口。

## 4. HTTP 与 CLI 契约草案

本地 HTTP 默认监听回环地址，CLI 连接后端，未来桌面复用入口，遵循 DL-121／DL-123；本阶段不开发网页页面。端口、启动参数、实际路由和错误结构在 P1-01 固定，并在 P1-05 通过真实进程验证。

| 操作 | HTTP 草案 | CLI 对应能力 |
| --- | --- | --- |
| 启动状态 | `GET /v1/health` | 查询后端状态 |
| 角色创建、查询 | `POST /v1/roles`、`GET /v1/roles/:roleId` | 创建及读取角色 |
| 设定修订 | `PATCH /v1/roles/:roleId/definition` | 更新同一角色的设定 |
| 状态读取／保存 | `GET/PUT /v1/roles/:roleId/state` | 保存和查询当前状态 |
| 窗口及消息 | `POST/GET /v1/roles/:roleId/windows`、`POST/GET .../windows/:windowId/messages` | 创建窗口、保存输入、按窗口读取历史 |
| 服务／资源配置 | `POST/GET /v1/resources`、`GET/PATCH /v1/resources/:resourceId` | 新增、查询、修改配置及启用／停用 |
| 角色能力绑定 | `GET/PUT /v1/roles/:roleId/bindings` | 保存／读取初始绑定及记忆模型继承／覆盖 |

任务及执行仓储可以先通过内部服务和测试验证，不为尚未实现的调度器提供假成功路由。消息写入接口接纳稳定的客户端提交编号，沿用 DL-122：同一次提交重试不产生重复消息，用户主动再发使用新编号；不得只按正文内容去重。P1 只保存消息，不自动调用模型。

响应区分资源不存在、请求结构错误、存储失败和成功保存；错误码使用清晰英文，必要说明使用中文。CLI 不吞掉错误，不在后端不可用时悄悄改写数据库。数据分页使用稳定顺序／游标，具体参数在契约定稿时记录。

P1 暂不提供资源删除、运行中删除或改绑的生命周期行为，也不在角色卡导入、Skill 安装格式尚未讨论时自行锁定协议。模型、MCP、Skill 可用性仍只由既有开关及任务延续规则管理，不增加确认弹窗或逐次授权。

## 6. 离线验收与证据

| 场景 | 必须证明 |
| --- | --- |
| 创建并重启 | roleId、设定、初始状态、默认窗口、数据库及工作空间均在新进程中恢复 |
| 更新设定 | 修订后仍为原角色，已有消息、状态、工作空间内容保留；不执行设定冲突处理 |
| 多窗口数据隔离 | 每个窗口只读到自己的消息，同一角色关联清晰；来源字段保存不改变正文 |
| 消息重试 | 同一提交编号得到同一消息，主动重复发送相同正文但新编号产生新消息 |
| 配置与绑定 | 资源定义、启用状态、角色绑定重开后相同；记忆模型继承／单独覆盖按配置解析 |
| 无外部执行 | 保存模型／MCP／Skill 配置，不发真实请求、不执行命令、不加载或试运行 Skill |
| 任务连续性仓储 | 原任务关联两次执行，替代旧回复不结束任务；显式结束保存原因；工具成功不自动结束目标 |
| 调用记录 | 五态与前后台模式分开；切换模式保留 toolCallId 及实际结果，既有任务资源延续记录重启保留 |
| 版本语义 | 更新角色及再次加载不会改写旧执行的已提交版本；提交重入不重复写消息或覆盖最新状态 |
| 初始化／保存失败 | 不报告半成品角色可用；业务事务失败没有半提交；失败后不误清用户工作空间 |
| CLI／API 共用服务 | 独立 CLI 调用实际后端，新进程读取一致；后端不可用返回明确错误而非直接写库 |

每次验收使用唯一 runId 和隔离的数据目录；汇总校验报告归属、缺失、不可解析及清理失败，不能沿用旧报告。日志／数据库可被 Git 忽略，但实施记录保存执行者、时间、命令、源码提交或摘要、报告文件名及必要结果。

P1 实施记录建议另建文档并登记导航，分别记录实现方自验与独立复核。真实模型服务在 P2 完整链路具备后按 DL-116 验证，本阶段不消耗用户服务额度。
