# 后端收口核验与架构治理计划

日期：2026-10-23。核验基线：本地提交`3071154`（包含`6bea256`之后的收口改动）。本文只提供核验与计划，没有执行业务代码重构、提交或打包。

## 1. 核验结论

本轮收口方向正确，未在已检查的替换点发现确定的新回归。`npm run typecheck`通过；`npm test`的46个文件、289项测试通过。但这不等于所有并发和失败路径已覆盖，补充复现发现了两处原有问题，建议在扩大公共基础能力前优先处理。

### 已完成且建议保留

- `storage/atomic-write.ts`集中处理同目录临时文件、唯一文件名、权限、rename替换和失败清理。配置、档案、插件状态、任务/媒体索引、监听记录、槽位、桌面凭据等调用点已接入，消除了多份底层实现。
- 原有各Store的写入链未因迁移而被整体移除；这点正确，因为写文件原子性和业务操作顺序是两种职责。
- `ManualInjectionService.#eligibleCandidates()`同时支持恢复执行与候选展示，`/slots.resumable`由后端输出。前端不再独立猜测恢复资格。这里的“候选”仅表示本地记录满足资格，是否存在已注入QQ仍需恢复执行时核验。
- `Core.listAccounts()`返回本地昵称与签名，减少页面独立拼装展示资料；本地头像与QQ头像已有共用解析入口。
- 新增原子写入测试覆盖JSON替换、二进制、失败清理、并发下文件完整性；配置失败测试不再依赖旧临时文件命名，避免测试绑定内部实现。

### 本次没有证明的保证

`writeFileAtomic()`只保证一次完整文件替换；它不保证读改写事务、多个写入者的业务合并、多个文件共同提交，也未提供fsync意义上的断电持久性。不能因为都用了这个函数，就删除业务级串行与版本校验。

## 2. 已复现问题：均在本轮之前存在

### [P2] 信号量交接时可以突破并发上限

位置：`src/core/concurrency.ts:23`及`:40`。

`#release()`先减少active、唤醒等待者；等待者在下一轮微任务才增加active。此时新请求可以看到空位并直接进入，随后被唤醒的等待者又进入。配置上限1时实际active达到2。

确定性复现：先取得唯一名额 → 第二个请求排队 → 释放第一个名额 → 同一轮立即提交第三个请求 → 等待后两个acquire，观察active为2。

影响：该类被实例启动/重启、OneBot动作以及媒体任务共用。它不是本轮原子写入迁移引入的问题，但在继续扩大复用前应修复。修复要求：名额直接交接给排队者、排队者不被新请求越过、release幂等；为取消/排空明确约定。

### [P2] 展示资料并发PATCH会丢失更新

位置：`src/profiles/display.ts:43`至`:58`。

两个请求分别更新昵称、签名时，都可能先读取同一旧快照，再各自写回完整文件。UUID临时文件避免临时文件名碰撞，但不能合并字段更新。临时数据复现10轮，10轮最终缺少其中一个更新；本机还观察到一次并发替换的EPERM失败。EPERM次数与系统调度有关，不把它视为稳定复现条件。

对照提交前的`saveAccountDisplay()`，相同的未加锁读改写结构已存在，故不归因于本次公共写入函数。应让同一账号的“读取当前值→校验/合并→落盘→发布结果”进入同一串行域；不同账号仍可并行。

复现脚本：`test-results/backend-review/repro.mts`，只使用系统临时目录，按仓库规则不纳入Git。需要将以上两个场景转成正式回归测试，再修业务代码。

## 3. 当前结构为什么仍容易重复

问题主要是能力归属和调用边界，单纯改目录名无法解决。

| 现状证据 | 后果 | 调整方向 |
| --- | --- | --- |
| Core约1895行，同时装配依赖、管理账号目录、QQ接入、模型配置、制品部署与查询 | 新功能容易继续塞进Core，或在旁边另写相似流程 | 保留Core公共门面，逐个提取应用服务 |
| HTTP server约1312行，既承载HTTP基础处理又定义CoreView、DTO和全部路由 | 核心从HTTP实现模块导入契约，边界方向不清 | 契约独立、HTTP处理与路由分离 |
| 多处Promise链、按键Map、drain和错误恢复 | 容易漏清理、吞掉错误或误用锁粒度 | 统一小型串行原语，业务决定串行键与策略 |
| OpenAI、视频、模型发现、SnowLuma、头像分别处理网络请求和响应体 | 超时、读取上限、取消和错误脱敏容易漂移 | 抽取底层有界读取/请求能力，保留各类端点策略 |
| 账号目录定位、展示资料与头像组装散落Core多个分支 | 根目录与自定义账号目录可能使用不同路径规则 | AccountDirectory与AccountPresentation单一入口 |
| MediaError、JobError放在providers/errors.ts | 非模型模块依赖模型模块的错误定义 | 公共错误基类下沉，业务错误回到所属模块 |
| `#scanProcesses()`既查询又停止/移除失联实例 | 页面轮询会触发生命周期操作，拆分时容易改行为 | 显式ProcessReconciler负责清理，查询层读取其状态 |

行数仅用于定位职责集中，不作为为了拆分而拆分的验收指标。

## 4. 建议目标：继续单体，建立清晰模块边界

保留Electron内嵌Core和每账号worker的现有部署方式，不引入微服务或为治理重复而迁移数据库。先保留现有领域目录，通过增量迁移调整依赖。

```text
src/
  bootstrap/                 # create-core：创建、注入依赖、启动与关闭顺序
  core/core.ts               # 保留公开Core接口，逐步成为委托门面
  application/
    accounts/                # 账号资料、目录定位与展示查询
    qq-connections/          # 接入用例、进程收敛、监听记录协调
    model-settings/          # 全局服务配置、凭据与账号配置用例
    deployments/             # 制品部署用例与结果
  platform/
    fs/                      # 原子写文件、JSON文档读写基础设施
    async/                   # SerialExecutor、KeyedSerialExecutor、并发闸门
    http/                    # 有界响应读取、取消与超时基础能力
    security/                # 公共脱敏能力；不含业务授权判定
  contracts/                 # 纯TypeScript API DTO、事件与应用端口
  service/
    server.ts                # HTTP生命周期
    http/                    # 鉴权、JSON、响应、错误映射、SSE
    routes/                  # accounts、injection、models、artifacts等
  agent/ channels/ instances/ injection/ providers/
  profiles/ policy/ jobs/ media/ artifacts/ host/ storage/ work/
                             # 现有领域模块继续保留，逐步澄清公开入口
```

依赖方向：HTTP路由→应用服务→领域模块→平台基础能力。bootstrap负责装配具体实现。平台不导入Core或领域服务；领域代码不导入HTTP路由、Electron或前端。

迁移公共错误/基础函数时，旧导出路径先做兼容重导出；错误类必须保持同一构造器，避免破坏`instanceof`和错误映射。不要在应用服务中再复制Core原方法，迁移后Core直接委托。

## 5. 哪些应统一，哪些应保留差异

### 应统一的能力及唯一归属

| 能力 | 唯一实现/规则所有者 | 调用方保留的责任 |
| --- | --- | --- |
| 原子文件替换 | 现有atomic-write，后续可迁至platform/fs | 数据格式、备份、错误码与恢复策略 |
| 串行执行机制 | 每Core持有的SerialExecutor/KeyedSerialExecutor | 决定账号/文件/进程键，以及是快照覆盖还是字段更新 |
| 账号路径定位 | AccountDirectory | 账号标识校验、是否存在、允许创建与否 |
| 昵称/头像等展示 | AccountPresentation | 真正登录身份仍由接入/通道流程校验 |
| 恢复监听资格 | 现有ManualInjectionService | UI只消费候选及原因，不复制判断 |
| 有界响应读取与中止 | platform/http | 协议解析、重试判定、允许访问的端点 |
| API DTO与错误响应 | contracts与HTTP错误映射 | 领域内部类型不直接暴露敏感字段 |

### 不建议强行合并

- 会话FIFO、按进程的注入串行、模型端点限流、长期媒体任务都使用异步机制，但业务语义不同。共享原语即可，不改成一个全局任务队列。
- 普通配置、角色绑定、任务状态、插件状态不能塞进一个万能Repository。领域Store继续拥有schema与状态迁移，复用底层文档和文件机制。
- `LayeredConfig`服务旧插件配置，`ConfigStore`服务模型/账号策略，不应只因都叫配置而合并文件和覆盖规则。
- SnowLuma仅本地端点、模型服务允许显式配置本地地址、消息附件下载限制非受信地址。这些网络策略不同；不能共享一个宽松URL校验器。
- 生图/语音请求被中止时，远端结果可能未知，不能让公共HTTP客户端默认重试，造成重复付费生成。
- 授权与凭据版本在执行前再次校验，是防止排队期间配置变化，不能当作重复校验删除。
- `slots.json`、desired状态、listening记录及实际observed状态分别表示规格、用户意图、历史监听和当前事实，应明确状态归属，不直接合并。
- worker内联脚本的超时工具有进程/打包边界，不能未经验证就替换成宿主路径导入。

## 6. 分阶段工作包与验收

### 阶段0：先修共享基础能力中的已知问题

工作：修复Semaphore名额交接与幂等release；按账号串行化展示资料读改写；将两份复现转为正式测试。

验收：上限1时任意插队时序active始终不超过1；重复release不能放出额外名额；并发更新昵称与签名同时保留；账号A的操作不阻塞账号B；失败任务不毒化后续任务。原有289项测试继续通过。

### 阶段1：完成持久化与账号基础能力治理

工作：保留atomic-write单点；添加每Core范围的串行执行原语、AccountDirectory，优先接入展示资料、角色绑定与配置提交。逐个审计Store的内存修改和落盘失败语义。

验收：读改写锁覆盖完整操作，不只覆盖rename；配置写失败时API、内存和磁盘状态符合明确约定；自定义账号目录与默认目录得到同一资料；关闭Core等待在途写入；没有模块级全局写入队列导致跨Core/跨账号串行。

注意：不能简单把所有Store套进同一个基类。对快照型Store与字段更新型Store分别定义提交语义；需多文件一致性时另列补偿/恢复方案，不宣称atomic-write已提供事务。

### 阶段2：提取应用服务和查询边界

顺序：AccountService/AccountPresentation → QqConnectionService/ProcessReconciler → ModelSettingsService → DeploymentService。先迁移一条完整用例及其测试，再继续下一条。

验收：Core门面、CLI和HTTP调用同一应用用例；查询接口不再暗含未声明的停止/删除操作，原失联检测转为明确周期收敛；多账号隔离、PID复用/换号、恢复监听资格、角色卡逐会话绑定和暂停行为不变。先明确依赖和锁顺序，再移动文件，避免重复加锁导致死锁。

### 阶段3：统一网络基础、契约和防退化检查

工作：抽取有限大小JSON/二进制读取与统一取消；按端点类别传入访问策略；迁移API契约与路由；逐步整理错误归属和日志脱敏。

验收：响应体超限提前取消；超时覆盖响应体读取；中止不再等待满任务；生成结果未知不自动重提；DTO不泄露凭据；HTTP/CLI处理同一业务错误一致。先保持现有依赖，确有收益再增加运行时schema或构建工具。

新增架构约束检查：领域模块不得导入HTTP/Electron；跨领域尽量经公开入口或注入端口；普通JSON覆盖写不能绕开公共原子写入入口；锁文件、JSONL追加、诊断日志等例外明确列出。用检查约束新增重复，不以全量文本相似度或目录数量作为质量指标。

## 7. 建议下一步

先分配阶段0和阶段1，不同时启动大规模文件迁移。每个工作包独立评审和提交；存储路径、HTTP接口、公开Core接口及账号数据格式暂保持兼容。完成后再决定是否推进阶段2，而不是一次性重写整个后端。
