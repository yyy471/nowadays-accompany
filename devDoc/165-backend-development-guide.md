## 1. 开发从哪里开始

正式开发的第一阶段为 P0：使用真实 LangGraph、本地 stdio MCP 和两份 SQLite，配合可控离线模型，验证最小的执行、中断及恢复链。核心验收是已保存成功的工具操作不重做、旧输出不覆盖新结果、恢复后的新判断使用最新资料，依据 DL-85、DL-128。

P0 要交付能实际运行的小样和可复现证据。完整角色管理归 P1，完整记忆及 Agent 回复归 P2；不以只搭目录、安装依赖或演示一段模型文字作为 P0 完成。

当前只展开 P0。P1～P5 保持文档 164 的顺序，在各阶段实现前补齐当期契约；首轮范围和已有功能要求不因暂未展开而取消。

## 2. 工作区与工程起步

- 从新主线 `master` 创建 `codex/` 开发分支，首个分支建议为 `codex/p0-runtime-spike`；旧代码继续保留在 `dev`。该分支已创建，本轮按用户要求纳入一次本地提交，源码版本以该提交为准。
- 在新分支建立源码、依赖清单和锁定文件。现有被忽略的 `node_modules`、构建产物和日志不算新依赖或验证证据，不能直接沿用其版本宣称选型成立。
- 候选运行时、LangGraph、MCP SDK、业务 SQLite 驱动与检查点驱动由实施方按 DL-128 选择并实测。普通同职责库的兼容性替换直接处理并留证；改变已确认架构或用户行为时先讨论。
- 小样运行数据放在项目内的专用目录，按用例分开，业务库和检查点库分文件。实际位置为 `prototypes/p0/data/<case>/`，已被忽略；提交源码、配置样例及复现说明，不提交数据库、运行日志或真实密钥。
- 小样代码从独立的 `prototypes/p0/` 起步。该路径当前已实现，后续可复用的代码在后续阶段根据验证结果整理，不先复制旧项目目录或创建未用的兼容层。

## 4. 最小职责与记录契约

### 4.1 职责

| 部分 | 责任 |
| --- | --- |
| 小样入口及用例控制器 | 准备输入、操作暂停点、触发中断或恢复，读取结果；不代替业务库伪造成功。 |
| 角色执行及 LangGraph | 一轮有界思考与工具使用，关联执行编号，按需暂停或恢复，提出回复与局部状态。 |
| 业务存储 | 保存最小角色资料、输入、执行、任务、调用及结果，执行正式回复与状态的业务提交。 |
| 检查点存储 | 独立 SQLite 文件中的图进度，使用实际检查点接口；不当作角色全部历史或当前业务状态。 |
| 本地 MCP 样例 | 通过真实 stdio 连接执行确定性操作，提供可核对的实际效果及调用次数。 |
| 离线模型 | 可控地产生工具请求、回复和迟到输出，用于复现流程；不进行真实服务推理。 |

各部分依赖显式传入，不引入模块级可变业务单例。具体函数签名和表字段在 P0-02 实现前结合实际 SDK 确定，记录到对应工作包，不预设正式 P1 数据模型。

### 4.2 必须区分的关联

- 角色身份、对话窗口与原始输入：说明资料和消息属于谁、来自哪里。
- 决策执行编号：对应一次图执行及其 `thread_id`；同次恢复沿用，新决策新建，依据 DL-66。
- 业务任务编号：表示持续目标，不因为回复中断或图暂停就结束，依据 DL-69、DL-72。
- 工具调用编号及实际结果：关联一次已登记操作，成功、失败和未知状态必须能分辨，依据 DL-64、DL-70。
- 已输出文字及完成状态：部分输出与正式完成分别记录，未提交的状态不视为已更新，依据 DL-77、DL-78。

P0 只实现小样需要的最小记录。正式消息提交编号、完整 API、角色资源配置等契约在 P1／P2 落实，但不得用同一个编号混代身份、任务和执行进度。

### 4.3 保存与恢复规则

输入先保存，工具调用先登记，实际结果先保存再回到图。正式回复、局部状态及本轮完成标记在同一角色业务库事务内提交，成功后才报告完成，依据 DL-64。

恢复保留已完成步骤和结果，后续判断刷新最新角色资料及状态；旧检查点不能回退最新业务状态。被新消息替代的旧回复不自动续写，已发工具的实际结果仍保存，依据 DL-67、DL-101。

业务库、检查点和外部工具不是一笔跨系统事务。若工具已经产生效果，但业务库未能确认其结果，按 DL-53 核查或保留未知，不能直接当作未执行并重做。

## 5. P0 必须留下证据的场景

| 用例 | 操作及检查点 | 实际通过依据 |
| --- | --- | --- |
| P0-C01 正常执行 | 输入后模型请求工具，保存结果并完成回复 | MCP 实际效果、调用记录及保存结果一致，正式回复与状态提交成功。 |
| P0-C02 同次暂停恢复 | 在工具结果已保存的边界暂停，再恢复同次执行 | 沿用原执行编号，读取已保存结果，工具实际执行次数不增加。 |
| P0-C03 重启恢复 | 结果保存及检查点形成后停止小样进程，再以新进程打开原数据恢复 | 业务数据及检查点确实跨进程恢复，已保存成功操作不重做；不只靠进程内缓存。 |
| P0-C04 新消息与迟到输出 | 旧回复已输出部分文字后用可控模型阻塞后续输出，提交新消息进入新决策，再释放旧输出 | 旧部分回复有未完成标记，迟到文字及未提交状态不能覆盖新回复或当前状态；已发工具不因切换重发。 |
| P0-C05 最新资料 | 暂停期间修改小样保存的角色设定和当前状态，再恢复后续判断 | 新判断能证明读到了最新资料，已有实际结果仍保留，旧快照不回退状态。 |
| P0-C06 结果未知 | 工具产生可核对效果后模拟响应丢失 | 不把未收到响应直接当成失败未执行；可核查则补实际结果，无法确认则保留未知，不盲目重做。 |
| P0-C07 提交失败 | 在正式回复与局部状态的提交处注入保存失败 | 不报告正式完成，不留下正文与状态一半成功的业务提交；已有真实工具结果继续保留。 |

用可控暂停点、屏障和确定性样例复现关键时序，避免只依靠固定等待时间碰巧通过。工具样例宜以项目内文件或计数记录提供实际效果，不能只断言离线模型说“已执行”。

P0 的结果用于决定执行基础是否可行。完整输入状态、资源关闭后的任务链延续、额度、记忆并发及其他组合用例仍按 P1～P4 的既定范围接入与验收，不因本节存在而提前标记完成。

## 6. 证据与问题记录

每个工作包的记录至少包含：环境及依赖版本、源码提交、安装与运行命令、输入和用例、实际结果、数据或日志位置、失败与限制。日志和数据库可保留在被忽略的运行目录，文档中记录可复现步骤与必要的脱敏摘要。

实施记录使用以下模板；P0 的实际记录已建立在[文档 166](166-p0-implementation-record.md)。

```markdown
## 工作包及范围
- 编号：
- 实现状态：未开始／进行中／待复核／已完成
- 依据的 DL 决定：
- 源码提交与运行环境：

## 实现与运行
- 实际依赖及版本：
- 安装、启动及验证命令：
- 实际用例、输出和持久数据证据：
- 已知限制及未覆盖事项：

## 实现方自验
- 结论与证据：

## 独立复核
- 复核者、范围及复现结果：
- 问题、修正及复验：
- 最终结论：通过／未通过／未验证
```

“已有文档”“代码已提交”“测试脚本存在”均不单独等于通过。没有实际证据的条目标为未验证；实现方自验不能替代独立复核，文档自检也不能标为实现复核。
